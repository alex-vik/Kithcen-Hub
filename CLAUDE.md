# Домашний склад продуктов — правила проекта

Личное PWA для учёта домашних запасов продуктов. Один пользователь, один дом, 150–200 позиций.
Полная спецификация: `docs/spec.md`. Визуальная система и прототипы: `docs/design/`. Вопросы на решение владельца: `docs/questions.md`. Архитектурные решения: `docs/adr/`. Задачи: `docs/tasks/`.

Требование с пометкой `[Q-NN]` реализуется по значению по умолчанию из спеки, пока вопрос не закрыт. Параметры — в разделе 15 спеки, в коде они живут как конфигурация, а не как константы в логике.

## Инварианты, которые нельзя нарушать

Эти правила важнее любой задачи. Если задача требует их нарушить — остановись и сообщи.

1. **Остаток никогда не хранится числом.** Он вычисляется как сумма событий журнала (BR-01).
2. **События не удаляются и не редактируются.** Отмена — компенсирующее событие (BR-02).
3. **Остаток и норма живут в расходной единице.** Упаковка пересчитывается через коэффициент (BR-03).
4. **Разная расходная единица — разные позиции.** Разный размер упаковки — одна позиция (BR-04, BR-05).
5. **Система не выставляет норму и не отключает позицию без подтверждения пользователя** (BR-10, BR-16).
6. **Минус в остатке — сигнал калибровки, а не ошибка.** Не блокировать, не валидировать запретом (BR-15).
7. **Распознанный приход пишется сразу, без экрана подтверждения** (BR-17).
8. **Мягкая деградация.** Пропуски отметок снижают точность, но никогда не ломают работу (NFR-07).

## Чего нет в первой версии

Не добавлять, даже если кажется полезным: сроки годности, места хранения, открытые/закрытые упаковки,
сезонность, стоимость списка, офлайн, многопользовательский режим, интеграция с календарём, автооплата.
Интеграция с Barbora — вторая фаза, в первой версии код для неё не пишется.

## Порядок сборки

1. Журнал событий и вычисление остатка
2. Синтетический дом (симулятор, `tests/sim/`)
3. Автосписание, прогноз, статусы
4. Калибровка и пересмотр
5. API
6. Экраны: киоск → список покупок → пересмотр → инвентарь → карточка → журнал → рецепты → меню

Экраны не начинаются, пока симулятор не показывает приемлемые метрики G-1 и G-2 на ядре.

## Команда агентов

Главная сессия работает как `delivery-lead` (задано в `.claude/settings.json`). Он оркестрирует, остальные — субагенты.

| Агент | Когда вызывать | Пишет в |
| --- | --- | --- |
| `delivery-lead` | Главная сессия, не субагент | `docs/` |
| `analyst` | Черновик задачи из FR, трассировка | `docs/tasks/` |
| `architect` | Черновик ADR, API-контракт, изменение инварианта | `docs/adr/`, каркас `src/` |
| `tester` | Задача в `ready`; изменения прогноза; симулятор | `tests/` |
| `backend-dev` | Задача в `impl`, домен и сервер | `src/domain/`, `src/server/` |
| `frontend-dev` | Задача в `impl`, экраны | `src/web/` |
| `reviewer` | Задача в `review` | ничего; своя память в `.claude/agent-memory/` |

Границы записи проверяет хук `.claude/hooks/guard-paths.sh`, а не только текст промптов. Разработчики не могут завершить работу при красных тестах: Stop-хук `.claude/hooks/require-green-tests.sh` читает команду тестов из `.claude/test-command` — её создаёт архитектор вместе с ADR-001.

## Поток задачи

```
analyst: FR → docs/tasks/T-NNN.md (draft)
   ↓ delivery-lead: согласование, при необходимости — с владельцем → ready
tester: падающие тесты → tests
   ↓
backend-dev / frontend-dev: тесты зелёные → review
   ↓
reviewer: APPROVE / CHANGES
   ↓
delivery-lead: done или обратно в impl
```

## Поручение субагенту

Субагент не видит разговор главной сессии. Каждое поручение содержит:

```
Цель: <что должно стать правдой после работы>
Задача: docs/tasks/T-NNN-<slug>.md
Контекст: <решения владельца и замечания, которых нет в файлах>
Границы: <что не трогать>
Отчёт: <формат из промпта агента>
```

## Вопросы

Субагенты не могут спросить владельца напрямую — они возвращают вопросы оркестратору в отчёте. Оркестратор решает: технический порог — в реестр параметров (раздел 15 спеки), решение владельца — в `docs/questions.md`, блокирующее — владельцу сейчас.

## Параллельная работа

По умолчанию задачи идут последовательно. Параллельно — только задачи без общих файлов, например задача бэкенда и экран, работающий по уже принятому контракту. Два агента никогда не правят один файл одновременно.

## Общие правила кода

- Минимум кода под задачу. Никакой «гибкости на будущее».
- Трогать только то, что требует задача. Чужой код не «улучшать».
- Предположения — вслух, в отчёте. Неясность — стоп и вопрос, а не молчаливый выбор.
- Каждое изменение ссылается на ID задачи и FR/BR.
