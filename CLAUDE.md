# Домашний склад продуктов — правила проекта

Личное PWA для учёта домашних запасов продуктов. Один пользователь, один дом, 150–200 позиций.
Полная спецификация: `docs/spec.md`. Визуальная система и прототипы: `docs/design/`. Вопросы на решение владельца: `docs/questions.md`. Карта задач по шагам: `docs/backlog.md`. Архитектурные решения: `docs/adr/`. Задачи: `docs/tasks/`.

Требование с пометкой `[Q-NN]` реализуется по значению по умолчанию из спеки, пока вопрос не закрыт. Параметры — в разделе 15 спеки, в коде они живут как конфигурация, а не как константы в логике.

## Инварианты, которые нельзя нарушать

Эти правила важнее любой задачи. Если задача требует их нарушить — остановись и сообщи.

1. **Остаток никогда не хранится числом.** Он вычисляется свёрткой событий журнала (BR-01).
2. **События не удаляются и не редактируются.** Отмена — компенсирующее событие (BR-02).
3. **Остаток живёт в единице счёта позиции** — штуки, пачки, бутылки. Граммов, коэффициентов и порций нет (BR-03).
4. **Разный размер упаковки — одна позиция** (BR-04).
5. **Система не меняет карточку и не отключает позицию без подтверждения пользователя** (BR-08, BR-10).
6. **Минус в остатке — признак пропущенной отметки, а не ошибка.** Не блокировать, не валидировать запретом (BR-15).
7. **Распознанный приход пишется сразу, без экрана подтверждения** (BR-17).
8. **Мягкая деградация.** Пропуски отметок снижают точность, но никогда не ломают работу (NFR-07).

## Чего нет в первой версии

Не добавлять, даже если кажется полезным: сроки годности, места хранения, открытые/закрытые упаковки,
сезонность, стоимость списка, офлайн, многопользовательский режим, интеграция с календарём, автооплата.
Интеграция с Barbora — вторая фаза, в первой версии код для неё не пишется.

## Порядок сборки

Разбиение по задачам и какие вопросы нужны к каждому шагу — `docs/backlog.md`.

0. Каркас: ADR-001…005, структура репозитория, `.claude/test-command`
1. Журнал событий и остаток
2. Темп расхода, оценка остатка, статусы, список покупок
3. API и сервисы
4. Экраны: киоск → список покупок → инвентарь → карточка → журнал → рецепты и меню

Симулятор (`tests/sim/`) — инструмент проверки списка, а не условие начала экранов.

## Команда агентов

Главная сессия работает как `delivery-lead` (задано в `.claude/settings.json`). Он оркестрирует, остальные — субагенты.

| Агент | Когда вызывать | Пишет в |
| --- | --- | --- |
| `delivery-lead` | Главная сессия, не субагент | `docs/` |
| `analyst` | Черновик задачи из FR, трассировка | `docs/tasks/` |
| `architect` | Черновик ADR, API-контракт, изменение инварианта | `docs/adr/`, каркас `src/`, корневые файлы сборки, `.claude/test-command` |
| `tester` | Задача в `ready`; изменения прогноза; симулятор | `tests/` |
| `backend-dev` | Задача в `impl`, домен и сервер | `src/domain/`, `src/server/` |
| `frontend-dev` | Задача в `impl`, экраны | `src/web/` |
| `reviewer` | Задача в `review` | только своя память в `.claude/agent-memory/` |

Границы записи для Write/Edit проверяет хук `.claude/hooks/guard-paths.sh`. Запись через Bash хук не видит — её ловит reviewer по `git status`. Stop-хук `.claude/hooks/require-green-tests.sh` один раз возвращает разработчика к работе при красных тестах; вторая попытка завершиться проходит, и тогда отчёт обязан объяснить, почему тесты красные. Команду тестов хук берёт из `.claude/test-command` — её создаёт архитектор вместе с ADR-001; до этого хук молчит.

## Поток задачи

```
analyst: FR → docs/tasks/T-NNN.md (draft)
   ↓ delivery-lead: согласование, при необходимости — с владельцем → ready
tester: падающие тесты → tests
   ↓
backend-dev / frontend-dev: тесты зелёные → review
   ↓
reviewer: APPROVE / CHANGES
   ↓
delivery-lead: done или обратно в impl
```

## Поручения и вопросы

Формат поручения субагенту и маршрут вопросов владельцу — в промпте `delivery-lead`. Субагент, у которого возник вопрос, не выбирает сам, а возвращает его в отчёте.

## Параллельная работа

По умолчанию задачи идут последовательно. Параллельно — только задачи без общих файлов, например задача бэкенда и экран, работающий по уже принятому контракту. Два агента никогда не правят один файл одновременно. Тесты гоняются целиком, поэтому падающие тесты одной задачи мешают Stop-хуку другой: tester пишет тесты следующей задачи, только когда текущая вышла из `impl`.

## Общие правила кода

- Минимум кода под задачу. Никакой «гибкости на будущее».
- Трогать только то, что требует задача. Чужой код не «улучшать».
- Предположения — вслух, в отчёте. Неясность — стоп и вопрос, а не молчаливый выбор.
- Каждое изменение ссылается на ID задачи и FR/BR.
