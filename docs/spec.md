## 1. Введение

### 1.1 Назначение документа

Документ фиксирует бизнес-требования, функциональные и нефункциональные требования, бизнес-правила и модель данных личного приложения для учёта домашних запасов продуктов. Он служит единой точкой правды для разработки первой версии и планирования второй фазы.

### 1.2 Назначение продукта

Приложение поддерживает домашнюю кухню наполненной нужными продуктами при минимуме ручного учёта. Система ведёт журнал расхода, прогнозирует потребление и к моменту закупки сама формирует список покупок. Ручной ввод со временем смещается от регистрации к корректировке.

### 1.3 Цели и метрики успеха

| ID | Цель | Метрика |
| --- | --- | --- |
| G-1 | Нужный продукт есть дома, когда он нужен | Количество случаев в месяц, когда продукт отсутствовал в момент необходимости |
| G-2 | Список покупок формируется без ручного труда | Доля позиций недельного списка, исправленных вручную |
| G-3 | Учёт не требует дисциплины | Время на еженедельный пересмотр в базовом режиме — не более минуты |

### 1.4 Архитектурный принцип

Система деградирует мягко. Пропущенные отметки делают прогноз менее точным, но не ломают его. Приложение, требующее ежедневной дисциплины, будет заброшено за месяц, поэтому каждая механика проектируется с расчётом на неполные данные.

## 2. Границы продукта

### 2.1 Входит в первую версию

Первая версия реализуется целиком как один выпуск. Приоритеты бэклога определяют порядок сборки, а не границу выпуска.

- Каталог продуктов с нормами, типами списания и единицами измерения
- Журнал событий склада и вычисляемый остаток
- Автосписание, прогноз расхода и самокалибровка
- Киоск на кухне
- Четыре способа оформления прихода
- Список покупок, доступный из магазина
- Еженедельный пересмотр
- Рецепты, планировщик меню на неделю, списание блюд
- Уведомления и колокольчик открытых дел
- Отпуск
- Журнал действий с откатом

### 2.2 Вторая фаза

- Интеграция с сервисом доставки: автоматическая сборка корзины в интернет-магазине (раздел 9)
- Статистика онлайн-заказов на основе накопленных цен

### 2.3 Вне рамок продукта

- Многопользовательский режим, роли, общая база рецептов
- Нативные мобильные приложения
- Сроки годности
- Различение мест хранения, открытых и закрытых упаковок, источников закупки
- Моделирование сезонности
- Офлайн-режим
- Интеграция с внешним календарём
- Автоматическая оплата заказов

## 3. Пользователи и окружение

### 3.1 Пользователи

Система однопользовательская: одна учётная запись владельца дома. Другие члены семьи могут пользоваться киоском, но их действия не различаются. Расхождения, возникающие из-за неотмеченного расхода другими людьми, подбиваются на еженедельном пересмотре.

### 3.2 Точки доступа

| Устройство | Роль |
| --- | --- |
| Планшет на кухне | Киоск: быстрые списания и приход, постоянно включён |
| Телефон | Список покупок в магазине, фото чеков, ввод рецептов, пересмотр |
| Компьютер | Ввод рецептов, детальный пересмотр, работа с каталогом |

### 3.3 Объём данных

Каталог — около 150–200 активных позиций. Один дом, одна кухня.

## 4. Глоссарий

| Термин | Определение |
| --- | --- |
| Позиция, продукт | Запись каталога, для которой ведётся остаток |
| Расходная единица | Единица, в которой продукт потребляется и учитывается (граммы, штуки, миллилитры) |
| Торговая упаковка | Единица, в которой продукт покупается (пачка, коробка, бутылка) |
| Коэффициент пересчёта | Количество расходных единиц в одной торговой упаковке |
| Норма | Ожидаемый расход продукта за сутки, в расходных единицах (решение владельца по Q-25, 2026-10-06) |
| Тип списания | Ритмичный, рывковый или медленный; определяет механику уменьшения остатка |
| Событие | Запись журнала, изменяющая остаток; единственный источник правды об остатке |
| Статус | Светофор позиции: красный, жёлтый, зелёный |
| Уверенность | Оценка системой точности собственного расчёта остатка по позиции |
| Пересмотр | Еженедельная задача сверки списка покупок и калибровки |
| Колокольчик | Список открытых дел, требующих внимания |
| Неактивная позиция | Позиция, исключённая из учёта и списка покупок, но сохранённая в каталоге |
| Порция | Количество расходных единиц, которое снимает одно нажатие «съел порцию» для данной позиции |
| Горизонт закупки | Период от текущей закупки до следующей; на него рассчитывается список покупок |
| Страховой запас | Дополнительный запас сверх расчётного расхода за горизонт, защищающий от ошибки прогноза |
| Фоновый расход | Расход ритмичной позиции вне рецептов; именно его описывает норма |
| Проекция остатка | Кэш вычисленного остатка; всегда пересобирается из журнала и не является источником правды |
| Синоним чека | Запомненное соответствие строки чека позиции каталога |

## 5. Модель данных

### 5.1 Сущности

| Сущность | Ключевые атрибуты | Назначение |
| --- | --- | --- |
| Product | название, категория, тип списания, расходная единица, торговая упаковка, коэффициент пересчёта, размер порции, норма, нижний порог, признак активности, ожидаемый срок жизни упаковки (для медленных) | Что учитываем |
| StockEvent | идентификатор, созданный клиентом; продукт; тип события; количество; дата и время события; время записи; источник; уверенность распознавания (для распознанных) | Журнал — единственный источник правды об остатке |
| Recipe | название, ингредиенты с количеством, число порций | Шаблон списания |
| MealPlan | дата, рецепт, число порций, признак «приготовлено» | Меню на неделю |
| ShoppingList | неделя, позиции, статус позиции, количество | Результат прогноза |
| AbsencePeriod | дата начала, дата окончания | Отключение прогноза на время отъезда |
| ReceiptAlias | текст строки чека, магазин, продукт | Запоминание распознанных строк чека, чтобы не угадывать заново |
| StoreMapping | продукт, ссылка на товар магазина, последняя известная цена | Связь позиции с товаром магазина (вторая фаза) |

### 5.2 Типы событий

| Тип | Влияние на остаток | Учит прогноз |
| --- | --- | --- |
| Покупка | Плюс | Да |
| Потребление порции | Минус | Да |
| Автосписание по норме | Минус | Нет (порождено нормой) |
| Списание по рецепту или блюду | Минус | Да |
| Выброс из-за порчи | Минус | Нет |
| Сигнал «закончилось» | Обнуление | Да |
| Инвентаризация | Установка фактического значения | Да |
| Отмена события | Исключает отменённое событие из расчёта | — |

### 5.3 Правила модели

**BR-01.** Остаток не хранится числом. Он вычисляется из журнала событий позиции в порядке времени события: инвентаризация и «закончилось» устанавливают остаток, остальные события прибавляют или вычитают количество. Без инвентаризации отсчёт идёт от нуля. (Уточнено решением владельца 2026-10-06, ADR-003.)

**BR-02.** Ошибочная отметка отменяется новым событием-отменой со ссылкой на неё. Исходное событие не удаляется и не редактируется, но исключается из расчёта остатка. Для приращений это равносильно компенсации. Отмену можно отменить. (Уточнено решением владельца 2026-10-06, ADR-003.)

**BR-03.** Остаток и норма ведутся в расходной единице. Приход в торговых упаковках пересчитывается через коэффициент.

**BR-04.** Разные размеры упаковки одного продукта (литр и пол-литра молока) — одна позиция. Различается только количество в событии прихода.

**BR-05.** Разная расходная единица означает разные позиции. Кофе в пачке (граммы) и кофе в капсулах (штуки) — две позиции каталога с отдельными нормами и остатками.

**BR-06.** Места хранения не различаются: холодильник, кладовка и морозилка дают один общий остаток.

**BR-07.** Открытые и закрытые упаковки не различаются.

**BR-26.** Каждое событие получает идентификатор на клиенте. Повторная отправка события с тем же идентификатором не создаёт дубль — это защищает от двойного нажатия и повторов при плохой связи.

**BR-27.** Все даты интерпретируются в часовом поясе Europe/Vilnius. Сутки для автосписания — календарные сутки по местному времени; переход на летнее время не создаёт лишних и не теряет списаний.

**BR-28.** Норма ритмичной позиции описывает фоновый расход. Списание по рецепту идёт сверх нормы, а обучение нормы не учитывает рецептурные события, чтобы расход не считался дважды. `[Q-11]`

## 6. Функциональные требования

Приоритет: **M** — обязательно для выпуска, **S** — желательно в первой версии.

### 6.1 Каталог и карточка продукта

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-CAT-01 | Карточка продукта содержит название, категорию, тип списания, расходную единицу, торговую упаковку, коэффициент пересчёта, норму и нижний порог | M |
| FR-CAT-02 | Все атрибуты карточки редактируются вручную | M |
| FR-CAT-03 | Тип списания система выставляет сама по истории; пользователь может его переопределить | M |
| FR-CAT-04 | На карточке есть кнопка «больше не покупаю», переводящая позицию в неактивные | M |
| FR-CAT-05 | Позиция, не покупавшаяся полгода, автоматически становится неактивной. Для медленных позиций порог — удвоенный ожидаемый срок жизни упаковки, но не меньше полугода `[Q-10]` | M |
| FR-CAT-06 | Неактивная позиция находится поиском и возвращается в активные при новой покупке | M |
| FR-CAT-07 | Первый запуск не требует инвентаризации; каталог наполняется по ходу использования | M |
| FR-CAT-08 | Карточка содержит размер порции; по умолчанию он предлагается из нормы и правится вручную | M |

**BR-08.** Отключённая кнопкой и заархивированная по сроку позиция имеют одно состояние — «неактивна». Повод виден в журнале действий; отдельных состояний не вводится.

**BR-09.** Неактивная позиция не списывается автоматически, не попадает в список покупок и не имеет статуса.

### 6.2 Новый продукт

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-NEW-01 | При добавлении новой позиции система предлагает задать норму | M |
| FR-NEW-02 | Предложение можно отклонить без ввода данных | M |
| FR-NEW-03 | Если норма не задана, система наблюдает за расходом и повторно предлагает норму, когда накопит достаточно истории | M |
| FR-NEW-04 | Повторное предложение содержит рассчитанное значение, которое достаточно подтвердить или поправить | M |

**BR-10.** Система никогда не выставляет норму без подтверждения пользователя.

**Критерии приёмки FR-NEW-03**

- Дано: новая позиция добавлена, предложение задать норму отклонено
- Когда: по позиции накоплено достаточно событий для оценки расхода
- Тогда: на экране пересмотра появляется предложение нормы с рассчитанным значением
- И: до подтверждения норма в карточке остаётся пустой

### 6.3 Типы списания и нормы

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-CON-01 | Ритмичные позиции (кофе, молоко, хлеб, корм) списываются автоматически ежедневно по норме | M |
| FR-CON-02 | Рывковые позиции (крупы, соусы, консервы) списываются только по отметке пользователя или по рецепту | M |
| FR-CON-03 | Медленные позиции (соль, масло, специи) не списываются; к концу ожидаемого срока жизни упаковки позиция появляется в колокольчике | M |
| FR-CON-04 | При первом запуске система предлагает проставить нормы для типовых позиций | M |
| FR-CON-05 | Вручную отмечается только отклонение от нормы (например, вторая чашка кофе — отдельной кнопкой) | M |
| FR-CON-06 | Для рывковых позиций система со временем выводит оценку частоты расхода (сколько гречки уходит в месяц) | S |
| FR-CON-07 | Автосписание выполняется раз в сутки после их окончания по местному времени | M |
| FR-CON-08 | Если сервер был недоступен, при восстановлении автосписание догоняет пропущенные сутки; повторный запуск за те же сутки ничего не меняет | M |
| FR-CON-09 | Расход ниже нормы («сегодня кофе не пил») отдельной отметкой не фиксируется; расхождение исправляется калибровкой `[Q-07]` | M |

**BR-11.** Разовые аномальные всплески расхода (приход гостей) система распознаёт сама и не учитывает в обучении нормы. Ручная отметка таких дней не требуется.

**BR-12.** Сезонность не моделируется: норма догоняет фактическое потребление по истории.

**BR-13.** На старте прогноз строится статистически, без машинного обучения.

### 6.4 Статусы

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-STS-01 | Каждая активная позиция имеет статус: красный — покупать, жёлтый — скоро закончится, зелёный — норма | M |
| FR-STS-02 | Статус ритмичных позиций вычисляется из остатка и нормы | M |
| FR-STS-03 | Статус рывковых позиций выставляется вручную на карточке или с киоска | M |
| FR-STS-04 | Для рывковой позиции можно задать явный нижний порог, по которому статус переключается автоматически | M |
| FR-STS-05 | Статус определяет сортировку по срочности в инвентаре и виджете киоска | M |
| FR-STS-06 | Для ритмичных позиций: красный — остатка не хватит до ближайшей закупки; жёлтый — хватит до ближайшей, но не хватит на следующий горизонт; зелёный — в остальных случаях `[Q-08]` | M |
| FR-STS-07 | Нулевой или отрицательный расчётный остаток всегда даёт красный статус | M |

### 6.5 Самокалибровка

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-CAL-01 | Система ведёт оценку уверенности по каждой позиции | M |
| FR-CAL-02 | На раннем этапе система задаёт вопросы об остатке; по мере роста уверенности частота вопросов снижается до нуля | M |
| FR-CAL-03 | После затухания вопрос по позиции возвращается только при аномалии — резком расхождении поведения с ожидаемым | M |
| FR-CAL-04 | За один раз задаётся не более 2–3 вопросов | M |
| FR-CAL-05 | Ответ на вопрос — грубая шкала: «много», «мало», «кончается» | M |
| FR-CAL-06 | Все вопросы калибровки собираются на экране пересмотра, позиции с низкой уверенностью показываются выше | M |
| FR-CAL-07 | Ответ переводится в оценку остатка: «много» — запас больше горизонта закупки, «мало» — меньше горизонта, «кончается» — не больше одной порции. Ответ записывается событием инвентаризации | M |
| FR-CAL-08 | Строки чека, распознанные с низкой уверенностью, записываются сразу, но повышают приоритет позиции на пересмотре | M |

**BR-14.** Вычёркивание позиции из списка покупок трактуется как сигнал «остаток больше, чем рассчитано»: оценка остатка повышается, норма смягчается. Причина вычёркивания не выясняется.

**BR-15.** Отрицательный расчётный остаток — не ошибка данных, а сигнал расхождения с реальностью. Он понижает уверенность, поднимает позицию на пересмотре и служит поводом пересчитать норму. Уход в минус не блокирует работу.

**BR-16.** Если позицию регулярно вычёркивают из списка или она долго не появляется в приходе, на пересмотре появляется предложение: отключить позицию, понизить норму или оставить как есть. Решение принимает пользователь; система ничего не отключает сама.

## 9. Вторая фаза: интеграция с доставкой

### 9.1 Контекст

Открытых API для покупок у литовских магазинов нет. Barbora Express — партнёрский сервис для бизнеса, а не розничная корзина. Любая интеграция держится на неофициальном интерфейсе сайта и может сломаться после обновления магазина.

### 9.2 Решения

**BR-21.** Автооплата исключена. Система доводит процесс до наполненной корзины; оплату подтверждает пользователь на стороне магазина.

**BR-22.** Первый магазин для интеграции — Barbora.

**BR-23.** Технология — браузерная автоматизация (Playwright), а не прямые запросы к внутренним эндпоинтам.

### 9.3 Требования

| ID | Требование |
| --- | --- |
| FR-DLV-01 | После пересмотра пользователь запускает оформление кнопкой «оформить» |
| FR-DLV-02 | Сборка корзины выполняется фоновой задачей; пользователь не ждёт на экране |
| FR-DLV-03 | Для каждой позиции система открывает страницу товара по сохранённой ссылке, добавляет в корзину и выставляет количество |
| FR-DLV-04 | Отсутствующий товар не прерывает сборку: позиция помечается, сборка продолжается |
| FR-DLV-05 | По завершении пользователь получает ссылку на корзину и перечень позиций, которые не удалось добавить |
| FR-DLV-06 | При сбое сохраняется снимок экрана страницы для диагностики |
| FR-DLV-07 | Вход в магазин выполняется вручную один раз; сессия хранится в постоянном профиле браузера |
| FR-DLV-08 | При истечении сессии в колокольчике появляется пункт «перелогиниться в магазине» |

### 9.4 Привязка позиций к товарам магазина

| ID | Требование |
| --- | --- |
| FR-MAP-01 | Позиция каталога связывается с товаром магазина вручную |
| FR-MAP-02 | Привязка выполняется по одной позиции, в момент её первого заказа; массовая привязка не требуется |
| FR-MAP-03 | Система ищет товар в магазине и показывает варианты, пользователь выбирает нужный |
| FR-MAP-04 | Выбранная связь запоминается и больше не запрашивается |

### 9.5 Цены

**BR-24.** Цена товара, известная через привязку, собирается и сохраняется с первого заказа.

**BR-25.** В первой версии цены ни на что не влияют: стоимости списка, бюджета и отчётов нет. Накопленная история служит материалом для будущей статистики онлайн-заказов.

## 14. Стратегия тестирования

### 14.1 Уровни

| Уровень | Что проверяет | Кто пишет |
| --- | --- | --- |
| Юнит | Доменные функции: остаток, прогноз, статусы, калибровка | tester до реализации |
| Приёмочные | Критерии приёмки задач, через API | tester до реализации |
| Симулятор | Качество прогноза на месяцах синтетической жизни дома | tester |
| Золотой набор распознавания | Разбор реальных чеков и фото | tester, на данных владельца |
| Сквозные | Ключевые сценарии в браузере: киоск, список в магазине, пересмотр | tester |

### 14.2 Синтетический дом

Симулятор генерирует реальный расход дома и отдельно — отметки, которые «видит» система. Сравнение даёт метрики G-1 и G-2 без ожидания реальных месяцев.

Обязательные сценарии: идеальный пользователь, пропуск 50% отметок, гости, отпуск с отметкой задним числом, разлюбленный продукт, новый продукт без нормы, неотмеченная готовка, ошибки распознавания чека, редко покупаемая медленная позиция.

Профиль дома для симулятора — состав семьи, питомцы, основные позиции с примерным расходом — предоставляет владелец `[Q-19]`.

### 14.3 Критерии готовности ядра

Экраны не начинаются, пока ядро на симуляторе не укладывается в целевые значения метрик `[Q-18]`:

| Метрика | Цель по умолчанию |
| --- | --- |
| G-1 в сценарии «идеальный пользователь» | 0 случаев за 90 дней |
| G-1 в сценарии «пропуск 50% отметок» | не более 1 случая в месяц |
| G-2 после обучающего периода | не более 20% |
| Вопросы калибровки после 8 недель | не более 1 в неделю |

### 14.4 Правила

- Время в тестах фиксированное и передаётся явно
- Облачные API распознавания в тестах заменяются записанными ответами
- Изменение прогноза сопровождается сравнением метрик симулятора до и после
