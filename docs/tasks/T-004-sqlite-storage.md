## Контекст

Журнал — единственный источник правды о запасах, и его потеря или порча — потеря всей истории. Задача кладёт доменную модель T-001…T-003 в SQLite так, чтобы журнал нельзя было изменить даже ошибкой кода, а повторная вставка того же события не давала дубль. В задаче хранилище (`src/server/storage/`) и правки домена из хвостов ревью. Сценариев `app`, часов и HTTP нет: хранилище проверяется тестами напрямую, на `:memory:`-БД или временном файле; `recordedAt` в тестах задаёт сам тест.

Тесты сервера идут на Node 22.18+. `node:sqlite` печатает `ExperimentalWarning` — это шум, а не ошибка (ADR-002). Глобально предупреждения не глушить.

## Бизнес-правила

- BR-01 / инвариант 1 — остаток не хранится числом и вычисляется из журнала. *(Здесь: в схеме нет таблицы или столбца остатка; хранилище не считает `SUM`, а отдаёт упорядоченные события (ADR-003 §3).)*
- BR-02 / инвариант 2 — ошибочная отметка отменяется событием-отменой со ссылкой на неё. Исходное событие не удаляется и не редактируется. *(Здесь: запрет `UPDATE` и `DELETE` на уровне БД триггерами — ADR-002; проверка ссылки отмены при вставке — ADR-003 §6.)*
- BR-26 — повторная отправка события с тем же идентификатором не создаёт дубль. *(Здесь — уровень хранилища: `id` — первичный ключ, вставка «если такого `id` нет», при совпадении `id` хранилище отдаёт записанное событие. Решение «повтор/конфликт/выполнено» и производный `id` — T-005.)*
- NFR-08 — все изменения остатка прослеживаются через журнал событий. *(Здесь: журнал append-only, `seq` присваивает хранилище, `recordedAt` хранится у каждого события.)*
- NFR-14 — сервер хранит время в UTC. *(Здесь: время — текст `YYYY-MM-DDTHH:mm:ss.sssZ`, хранилище отклоняет всё остальное. Приведение времени клиента к канону — T-005.)*
- BR-15 / инвариант 6 — минус в остатке не ошибка. Хранилище не отклоняет запись из-за того, что остаток уйдёт в минус.
- BR-05 / инвариант 4 — расходная единица меняется, только пока у позиции нет событий. *(Здесь: хранилище даёт признак «у позиции есть события остатка» для `changeUnit`; сама правка карточки через API — B-17.)*
- ADR-003 §6 — отмена ссылается на существующее событие той же позиции и записана позже цели. Это проверка ссылки, а не запрет по остатку.
- ADR-003 §7 — журнал состояний позиции хранится отдельно от журнала остатка, append-only; активность выводится из последнего события.

## Модель хранения (для понимания критериев)

Имена таблиц, столбцов, функций и типов выбирают tester и backend-dev; критерии задают поведение.

| Таблица | Содержимое | Изменяемость |
| --- | --- | --- |
| Каталог | Атрибуты `Product` (T-001): `id`, название, категория, тип списания, единица, название упаковки, коэффициент, норма, нижний порог, порция | Строки правятся (`updateProduct`). Удаления позиции в задаче нет |
| События остатка | Атрибуты `StockEvent` (T-002, T-003): `id` (PK), `seq`, `productId` → каталог, `kind`, `quantity`, `value`, `packs`, `unitsPerPack`, `targetId`, `occurredAt`, `recordedAt`, `source` | Только добавление. `UPDATE`/`DELETE` → `RAISE(ABORT)` |
| События состояния | Атрибуты `StateEvent` (ADR-003 §7, с правкой К32): `id` (PK), `seq`, `productId` → каталог, `state`, `reason`, `refEventId` (необязательный), `occurredAt`, `recordedAt` | Только добавление, те же триггеры |

- Все таблицы `STRICT`. Время — текст в каноне `YYYY-MM-DDTHH:mm:ss.sssZ`.
- `seq` — монотонный номер записи внутри своей таблицы, у каждой таблицы своя последовательность. Присваивает хранилище при вставке, вызывающий его не задаёт.
- `recordedAt` хранилище принимает от вызывающего и не вычисляет само. В T-005 его передаёт `app` из `clock.now()`; в тестах этой задачи — тест.
- Миграции — нумерованные SQL-файлы в `src/server/storage/migrations/`, применяются при открытии в транзакции, версия — `PRAGMA user_version`.
- `operationId` и `recognitionConfidence` (ADR-003 §4) в задаче не появляются — столбцы добавят B-19/B-20 своей миграцией.
- Хранилище даёт транзакцию, внутри которой выполняются несколько чтений и вставок (её использует T-005 для сценария клиента и пакета). Отдельного критерия здесь нет: атомарность пакета проверяет К28 в T-005.

Предсказуемые отказы (неизвестная позиция, плохая ссылка отмены, неканоническое время, повторный `id` позиции) — результат, а не исключение. Исключение допустимо только при прямом SQL в обход хранилища (К5, К6, К15).

## Критерии приёмки

Время в критериях — UTC. «Прямой SQL» — запрос к той же БД в обход репозиториев: так тест проверяет защиту на уровне БД. Номера критериев сохранены из общего черновика: К19–К29 перенесены в T-005 без перенумерации.

### Часть А. Хранилище (`src/server/storage/`)

**К1. Открытие БД с настройками ADR-002.**
- Дано: путь к новому файлу во временном каталоге
- Когда: БД открывается модулем хранения
- Тогда: `journal_mode` = `wal`, `synchronous` = 2 (FULL), `foreign_keys` = 1, `busy_timeout` = значению параметра (по умолчанию 5000, спека раздел 15)
- И: БД `:memory:` открывается с `foreign_keys` = 1, и к ней применяются те же миграции

**К2. Миграции на пустой БД; остатка в схеме нет.**
- Дано: пустая БД
- Когда: БД открывается
- Тогда: `user_version` равен номеру последнего файла миграции; есть ровно три пользовательские таблицы — каталог, события остатка, события состояния; у всех трёх в `PRAGMA table_list` признак `strict` = 1
- И: таблицы или столбца с остатком нет (инвариант 1)

**К3. Повторное открытие не применяет миграции заново и не теряет данные.**
- Дано: файловая БД после К2, в которой записаны позиция и два события
- Когда: БД закрывается и открывается снова
- Тогда: ошибки нет, `user_version` тот же, позиция и события читаются без изменений

**К4. Сбой миграции откатывается целиком.**
- Дано: набор из двух миграций: первая корректна, вторая сначала создаёт таблицу, затем содержит ошибочный SQL
- Когда: набор применяется к пустой БД
- Тогда: открытие завершается ошибкой; `user_version` = 1; таблицы из второй миграции нет
- И: после замены второй миграции на корректную повторное открытие поднимает `user_version` до 2
- *(Набор миграций для теста подставляется в механизм применения; как именно — решает разработчик.)*

**К5. Журнал остатка нельзя изменить даже прямым SQL (BR-02, NFR-08).**
- Дано: записанная порция −100
- Когда: прямым SQL по отдельности: `UPDATE` количества; `UPDATE` времени события; `UPDATE` вида; `DELETE` строки; `INSERT OR REPLACE` с тем же `id` и другим количеством
- Тогда: каждый запрос завершается ошибкой или не меняет данных; строка с этим `id` одна и побайтно та же, что до запроса
- *(`INSERT OR REPLACE` при выключенных `recursive_triggers` не вызывает `BEFORE DELETE`, поэтому случай проверяется отдельно.)*

**К6. Журнал состояний защищён так же.**
- Дано: записанное событие состояния `inactive`, повод `user_button`
- Когда: прямым SQL — `UPDATE state`, `DELETE`, `INSERT OR REPLACE` с тем же `id`
- Тогда: как в К5

**К7. Каталог: запись, чтение, правка.**
- Дано: позиция «Гречка», г, упаковка «пачка» 900, категория не задана, норма не задана
- Когда: позиция записывается и читается по `id`; затем правятся норма 40 и коэффициент 800 и позиция читается снова
- Тогда: прочитанное глубоко и строго равно `Product` из `createProduct` (поля без значения — `null`, как в типе `Product`), после правки — равно результату `updateProduct`
- И: список позиций содержит все записанные; чтение по неизвестному `id` даёт «нет такой позиции» без исключения; повторная запись позиции с существующим `id` отклоняется, исходная строка не меняется

**К8. Событие неизвестной позиции не записывается.**
- Дано: в каталоге нет позиции `p-x`
- Когда: в журнал остатка и отдельно в журнал состояний добавляется событие с `productId` `p-x`
- Тогда: отказ, ни одной строки не добавлено

**К9. Событие остатка читается в той же форме, в какой создано (хвост ревью T-003, п. 3).**
- Дано: по отдельности: порция −100; покупка 2 уп × 900 (`packs`, `unitsPerPack`, `quantity` 1800); покупка `quantity` 450 без упаковок; инвентаризация `value` 0; инвентаризация 480; «закончилось»; отмена с `targetId`
- Когда: событие записывается и читается по `id`
- Тогда: прочитанное строго равно записанному событию (`toStrictEqual`): у отсутствующих для вида полей нет ключа (ни `null`, ни ключа со значением `undefined`), `value` 0 сохраняется как 0, числа и строки не меняют тип

**К10. `seq` присваивает хранилище.**
- Дано: пустой журнал, две позиции
- Когда: пять событий записываются вперемешку по позициям и с произвольным временем события
- Тогда: `seq` — целые, строго возрастают в порядке вставки и не зависят от `occurredAt` и от того, что передал вызывающий

**К11. Вставка «если такого `id` нет» на уровне хранилища (BR-26).**
- Дано: записанная порция −100, `id` X, с её `seq` и `recordedAt`
- Когда: в хранилище добавляется событие с тем же `id` X — по отдельности с тем же и с другим содержимым
- Тогда: вторая строка не появляется, первая не меняется; хранилище сообщает, что `id` уже есть, и отдаёт записанное событие с исходными `seq` и `recordedAt`

**К12. События позиции читаются в порядке `(occurredAt, seq)` (ADR-003 пример 1).**
- Дано: гречка: инвентаризация 400 (12.10 09:00), инвентаризация 1900 (13.10 10:00), рецепт −250 (13.10 20:00), покупка +1800 (12.10 18:00) — записаны в этом порядке; плюс события другой позиции и два события гречки с одинаковым `occurredAt`
- Когда: читаются события гречки
- Тогда: только события гречки, по возрастанию `occurredAt`, при равном — по `seq`; `stockBalance` по прочитанному = 1650; `stockLedger` у инвентаризации 1900 даёт неявное −300

**К13. Проверка ссылки отмены (ADR-003 §6; хвост ревью T-003, п. 4).**
- Дано: у гречки записана порция E1; у риса — порция E2; в журнале состояний гречки есть событие S1
- Когда: в журнал гречки добавляется отмена по отдельности: (а) на `id`, которого нет нигде; (б) на E2 (другая позиция); (в) на `id` S1 (событие состояния, а не остатка); (г) на E1; (д) отмена отмены из (г)
- Тогда: (а)–(в) — отказ, ничего не записано; (г) и (д) записаны
- И: в журнале после любого набора записей у каждой отмены цель существует, относится к той же позиции и имеет меньший `seq`

**К14. Минус не блокируется (BR-15, инвариант 6).**
- Дано: новая позиция без событий
- Когда: записываются порция −100, затем рецепт −50
- Тогда: оба события записаны; `stockBalance` по прочитанному = −150

**К15. Время в хранилище только в каноне (NFR-14).**
- Дано: событие, у которого (по отдельности) `occurredAt` или `recordedAt` равно `2026-10-12T09:00:00Z` (без миллисекунд), `2026-10-12T12:00:00.000+03:00`, `2026-10-12 09:00:00.000Z`
- Когда: событие передаётся в хранилище в обход `createStockEvent` (приведение типа в тесте) или вставляется прямым SQL
- Тогда: отказ, строка не добавлена
- И: то же для `occurredAt` и `recordedAt` события состояния
- *(Лексикографический порядок `ORDER BY occurred_at` верен только для канона — ADR-002.)*

**К16. Журнал состояний: запись, чтение, повтор.**
- Дано: позиция «Кефир»
- Когда: записываются `inactive`/`user_button` (12.10 10:00), `active`/`user_restore` (12.10 10:00, позже по `seq`), `inactive`/`auto_archive` (11.10 09:00, записано последним); затем событие с уже записанным `id`
- Тогда: события читаются в порядке `(occurredAt, seq)` и строго равны записанным, без ключа `refEventId`, где ссылки нет; `isActive` по прочитанному = `true`; повтор `id` не добавляет строку и отдаёт записанное событие
- И: событие с `refEventId` читается с этим полем

**К17. Признак «у позиции есть события остатка» (для `changeUnit`, BR-05).**
- Дано: позиция без событий
- Когда: признак запрашивается до и после записи одной порции, а также после её отмены
- Тогда: `false`, затем `true` и `true` (отменённое событие остаётся в журнале)
- И: события состояния признак не меняют

**К18. Драйвер не виден за пределами хранилища (ADR-002).**
- Дано: исходники `src/`
- Когда: тест разбирает импорты
- Тогда: `node:sqlite` импортируется только из файлов в `src/server/storage/`

### Часть В. Домен (`src/domain/`)

**К30. Конфликт по `value` инвентаризации (хвост ревью T-003, п. 1).**
- Дано: записанная инвентаризация `value` 500; входящая с тем же `id` и `value` 480, остальное совпадает
- Когда: `resolveEventWrite`
- Тогда: исход «конфликт»

**К31. Список полей содержимого полон (хвост ревью T-003, п. 2).**
- Дано: образец события, где заполнены все поля `StockEvent` (тип `Required<StockEvent>`)
- Когда: для каждого поля по отдельности меняется значение и вызывается `resolveEventWrite`
- Тогда: изменение `seq` или `recordedAt` даёт «повтор», изменение любого другого поля — «конфликт»
- И: список полей содержимого объявлен так, что `npm run typecheck` падает, если в `StockEvent` появилось поле, которого нет ни в списке, ни среди `seq`/`recordedAt` (`satisfies` + `Exclude<…>` → `never`). Эта часть проверяется `npm run typecheck` — его запускает reviewer, Stop-хук типы не проверяет (ADR-001)

**К32. У события состояния есть `recordedAt` и необязательная `refEventId` (ADR-003 §7; решение НВ-1).**
- Дано: тип `StateEvent` с обязательным `recordedAt` и необязательным `refEventId`
- Когда: тесты `isActive` из T-001 запускаются с событиями, у которых есть `recordedAt`
- Тогда: результаты `isActive` те же, что в T-001; `recordedAt` и `refEventId` на активность не влияют
- *(tester дополняет фикстуры `tests/domain/catalog.test.ts` полем `recordedAt`.)*

## Не входит в задачу

- Сценарии `app`: запись события от клиента, исходы «новое»/«повтор»/«конфликт», приведение времени клиента к канону, проверка клиентского `id`, пакетная запись системных событий, UUIDv5 и `NS`, реальные часы `src/server/clock.ts` — **T-005**.
- HTTP, маршруты, коды ответа на повтор, конфликт и отказ, отсечение неизвестных ключей JSON, ограничение `occurredAt` из будущего — **B-16, B-17**.
- Чтение конфигурации из окружения и сборка `src/server/main.ts`: модуль хранения получает путь и `busy_timeout` параметрами, путь по умолчанию `data/kitchen.sqlite` (ADR-002) — **B-17**.
