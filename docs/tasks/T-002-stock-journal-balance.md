## Контекст

Остаток — единственное число, на котором держатся автосписание, статусы, список покупок и калибровка, и он никогда не хранится: его выводят из журнала событий позиции. Задача даёт доменную модель события остатка (семь типов из 5.2, без отмены) и чистые функции: остаток позиции и лента остатка (до/после каждого события). Приход в упаковках пересчитывается в расходную единицу в момент записи.

Задача только доменная: `src/domain/`, чистые функции, время — параметром (ADR-004, NFR-16). Хранение, `seq`, `recorded_at` от часов сервера, append-only на уровне БД — B-03a. Все критерии проверяются юнит-тестами домена.

## Бизнес-правила

- BR-01 — Остаток не хранится числом. Он вычисляется из журнала событий позиции в порядке времени события: инвентаризация и «закончилось» устанавливают остаток, остальные события прибавляют или вычитают количество. Без инвентаризации отсчёт идёт от нуля.
- BR-03 — Остаток и норма ведутся в расходной единице. Приход в торговых упаковках пересчитывается через коэффициент.
- BR-04 — Разные размеры упаковки одного продукта — одна позиция. Различается только количество в событии прихода. *(Пересчёт сделан в T-001; здесь — фиксация в событии.)*
- BR-06 — Места хранения не различаются: холодильник, кладовка и морозилка дают один общий остаток.
- BR-07 — Открытые и закрытые упаковки не различаются.
- BR-15 — Отрицательный расчётный остаток — не ошибка данных. Уход в минус не блокирует работу. *(Инвариант 6: ни одна функция задачи не отклоняет событие из-за остатка и не обрезает результат снизу.)*
- NFR-08 — Все изменения остатка прослеживаются через журнал событий. *(Здесь — доменная часть: лента остатка. Неизменяемость журнала в хранилище — B-03a.)*
- NFR-14 — Сервер хранит время в UTC. *(Здесь — формат `Instant`, хвост ревью T-001.)*
- ADR-003 §4 — количество в событии фиксируется в расходной единице в момент записи; у прихода в упаковках дополнительно хранятся `packs` и `unitsPerPack`, `quantity = packs × unitsPerPack`. Правка коэффициента в карточке историю не переписывает.
- ADR-003 §5.1 — порядок свёртки `(occurredAt, seq)`; граница `asOf` включительно; начальное значение 0; результат не ограничивается снизу; лента с неявным приращением значений-событий.

## Модель события (для понимания критериев)

Имена функций и типов выбирают tester и backend-dev; критерии задают поведение. Атрибуты — по ADR-003 §4 в той части, которая нужна сейчас.

| Атрибут | В T-002 | Смысл |
| --- | --- | --- |
| `id` | да, обязателен | Непрозрачная непустая строка. Домен его не генерирует и не разбирает (ADR-003 §8) |
| `seq` | да, обязателен у записанного события | Порядок записи; присваивает хранилище (B-03a). В тестах передаётся явно |
| `productId` | да | Позиция |
| `kind` | да | `purchase`, `portion`, `auto_writeoff`, `recipe`, `spoilage` — приращения; `inventory`, `depleted` — значения. `cancel` — B-03 |
| `quantity` | у приращений | В расходной единице, конечное число больше нуля; знак задаёт тип |
| `value` | у `inventory` | В расходной единице, конечное число не меньше нуля. У `depleted` не хранится |
| `packs`, `unitsPerPack` | у `purchase`, если приход в упаковках | Сколько упаковок и по какому коэффициенту; `quantity = packs × unitsPerPack` |
| `occurredAt` | да | `Instant` в каноническом формате (К18) |
| `recordedAt` | да, обязателен у записанного события | `Instant`; значение даёт сервер (`clock.now()`, B-03a). Домен его только переносит |
| `source` | да | Источник отметки, см. НВ-1 |
| `targetId` | нет — B-03 | Ссылка отмены |
| `operationId` | нет — B-19/B-20 | Общий для строк операции (рецепт, чек, фото стола) |
| `recognitionConfidence` | нет — B-20 | Уверенность распознавания |

**Почему так разделено с B-03.** `id` и `seq` вводятся сейчас: `seq` нужен для порядка при равном времени (К10), `id` — чтобы лента ссылалась на событие (К12), а B-03 ссылался на цель отмены. Тип `cancel` и `targetId` вводятся в B-03 вместе с правилом «действующих событий» (ADR-003 §5.1 шаг 1): без него их нельзя проверить, а добавление нового варианта события и шага фильтрации перед упорядочиванием не меняет критериев T-002. `operationId` и `recognitionConfidence` добавляются необязательными полями в задачах, где появляются их источники; на свёртку они не влияют.

Разделение «новое событие» (без `seq` и `recordedAt`, которые назначает хранилище и сервер) и «записанное событие» — на усмотрение разработчика; критерии К1–К7 проверяют содержимое, которое задаёт домен.

## Критерии приёмки

### Создание событий (5.2, BR-03, BR-04, BR-06, BR-07)

**К1. Приход в упаковках по коэффициенту позиции.**
- Дано: позиция «Гречка», единица «г», коэффициент 900
- Когда: создаётся событие покупки 2 упаковок
- Тогда: `kind = purchase`, `quantity = 1800`, `packs = 2`, `unitsPerPack = 900`, `productId` — идентификатор позиции

**К2. Приход упаковкой другого размера — та же позиция.**
- Дано: позиция «Молоко», единица «мл», коэффициент 1000
- Когда: создаётся событие покупки 1 упаковки с явным коэффициентом 500
- Тогда: `quantity = 500`, `packs = 1`, `unitsPerPack = 500`, `productId` — той же позиции; коэффициент позиции остаётся 1000

**К3. Приход сразу в расходных единицах.**
- Дано: позиция «Гречка»
- Когда: создаётся событие покупки на 450 без упаковок
- Тогда: `quantity = 450`; `packs` и `unitsPerPack` у события отсутствуют (пусты)

**К4. Приращения и значения всех типов 5.2.**
- Дано: позиция «Рис»
- Когда: создаются по одному событию `portion` 100, `auto_writeoff` 20, `recipe` 250, `spoilage` 300, `inventory` со значением 1200, `depleted`
- Тогда: каждое событие создано с переданным `kind`; у приращений `quantity` положительное и равно переданному; у `inventory` `value = 1200`; у `depleted` нет ни `quantity`, ни `value`

**К5. Недопустимые величины отклоняются, исключение не выбрасывается.**
- Дано: по отдельности — `quantity` 0, −5, `NaN`, `Infinity` у любого приращения; `value` −1, `NaN` у инвентаризации; `packs` 0, −1, `NaN` `[НВ-2: и 1,5]`; явный `unitsPerPack` 0 или −500; пустой `id`; пустой `source`
- Когда: создаётся событие
- Тогда: результат — ошибка с указанием атрибута (по образцу `Result` из T-001), событие не создаётся
- И: `inventory` со значением 0 создаётся без ошибки

**К6. В событии нет мест хранения и признака открытой упаковки (BR-06, BR-07).**
- Дано: событие каждого типа из К4 и событие покупки из К1
- Когда: перечисляются его атрибуты
- Тогда: набор ключей события — подмножество атрибутов, отмеченных «да» в таблице модели; атрибутов места, открытости упаковки, срока годности нет

**К7. Создание события не меняет позицию и входные данные.**
- Дано: позиция «Гречка» из К1
- Когда: создаются события К1 и К2
- Тогда: объект позиции не изменился (глубокое сравнение с копией до вызова)

### Остаток как свёртка (BR-01, BR-15)

**К8. Пустой журнал — ноль.**
- Дано: у позиции нет событий
- Когда: вычисляется остаток
- Тогда: 0

**К9. Приращения без значения-события — от нуля, минус допустим.**
- Дано: покупка +1800 (12.10 10:00, seq 1), порция −100 (12.10 20:00, seq 2), рецепт −250 (13.10 19:00, seq 3), порча −300 (14.10 09:00, seq 4), автосписание −20 (15.10 00:00 по Вильнюсу = 14.10 21:00Z, seq 5)
- Когда: вычисляется остаток
- Тогда: 1130
- И: для позиции только с порцией −100 остаток −100: ошибки нет, результат не обрезается до 0

**К10. Порядок по `(occurredAt, seq)`, а не по порядку в массиве и не по `seq` отдельно.**
- Дано: в перемешанном порядке переданы: инвентаризация 1000 (09.10 10:00, seq 1), покупка +900 (10.10 12:00, seq 2), рецепт −300 (11.10 19:00, seq 3), порция −100 (11.10 21:00, seq 7 — внесена задним числом)
- Когда: вычисляется остаток
- Тогда: 1500; при любой перестановке массива результат тот же
- И: при совпадении `occurredAt` у инвентаризации 500 (seq 9) и покупки +200 (seq 8) остаток 500; при обратном соотношении seq — 700

**К11. Значения-события устанавливают остаток (BR-01).**
- Дано (а): покупка +1000, порция −1500 (остаток −500), затем «закончилось», затем покупка +900
- Тогда (а): остаток 900 — «закончилось» обнуляет и отрицательный остаток
- Дано (б): покупка +1000, инвентаризация 400, порция −100
- Тогда (б): 300 — приращения до инвентаризации на результат не влияют
- Дано (в): инвентаризация 400 (seq 1), затем два события с одним `occurredAt`: «закончилось» (seq 2) и покупка +900 (seq 3)
- Тогда (в): 900

**К12. Событие задним числом раньше инвентаризации не меняет текущий остаток (ADR-003, пример 1).**
- Дано: гречка; инвентаризация 400 (Пн 12.10 09:00, seq 1), инвентаризация 1900 (Вт 13.10 10:00, seq 2), рецепт −250 (Вт 13.10 20:00, seq 3)
- Когда: добавляется покупка 2 уп × 900 = +1800 с `occurredAt` Пн 12.10 18:00 и seq 4, и остаток вычисляется до и после добавления
- Тогда: остаток в обоих случаях 1650
- И: в ленте (К14) неявное приращение инвентаризации seq 2 до добавления +1500, после добавления −300

**К13. Граница `asOf` включительно.**
- Дано: журнал из К9
- Когда: вычисляется остаток с `asOf` = 13.10 19:00 (ровно время рецепта)
- Тогда: 1450 (рецепт учтён, порча и автосписание — нет)
- И: с `asOf` раньше первого события — 0

### Лента остатка и прослеживаемость (NFR-08)

**К14. Лента: до, после и неявное приращение.**
- Дано: журнал из К11 (а)
- Когда: строится лента остатка
- Тогда: по строке на каждое событие в порядке `(occurredAt, seq)`, каждая строка ссылается на `id` события: покупка 0 → 1000, порция 1000 → −500, «закончилось» −500 → 0 (неявное +500), покупка 0 → 900
- И: у приращений неявного приращения нет (пусто, не 0); у значений-событий оно равно «после − до», в том числе 0, если значение совпало с расчётным

**К15. Каждое изменение остатка объяснено событием.**
- Дано: журналы из К9, К10, К11 (а–в), К12
- Когда: строятся лента и остаток
- Тогда: «до» первой строки = 0; «до» каждой следующей = «после» предыдущей; «после» последней = остаток; у приращения «после − до» = ±`quantity` по знаку типа; число строк = числу событий

**К16. Функции не изменяют журнал.**
- Дано: массив событий в перемешанном порядке
- Когда: вычисляются остаток и лента
- Тогда: массив и каждое событие в нём глубоко равны копии до вызова (порядок элементов тот же)

### Коэффициент и время (ADR-003 §4, NFR-14)

**К17. Правка коэффициента историю не переписывает.**
- Дано: позиция «Гречка», коэффициент 900; событие покупки из К1 (+1800)
- Когда: коэффициент позиции правится на 800 (`updateProduct` из T-001), остаток вычисляется заново по тому же журналу
- Тогда: остаток 1800; у события `quantity = 1800`, `unitsPerPack = 900`
- И: новая покупка 1 упаковки после правки даёт `quantity = 800`, остаток 2600

**К18. Время события — только канонический `Instant`.**
- Дано: `occurredAt` (и `recordedAt`, если он передаётся в домен) по отдельности: `2026-10-12T09:00:00Z` (без миллисекунд), `2026-10-12T12:00:00.000+03:00`, `2026-10-12 09:00:00.000Z`, `2026-02-30T09:00:00.000Z`, пустая строка
- Когда: создаётся событие
- Тогда: ошибка с указанием атрибута времени; событие не создаётся
- И: `2026-10-12T09:00:00.000Z` принимается без изменений

## Не входит в задачу

- Тип `cancel`, `targetId`, правило действующих событий, отмена отмены, отмена значения-события — **B-03**.
- Идемпотентность по `id`, «вставить, если такого `id` нет», конфликт содержимого — **B-03** (правило) и **B-03a** (первичный ключ).
- Хранение в SQLite, присвоение `seq`, `recordedAt = clock.now()`, append-only на уровне БД (триггеры, запрет UPDATE/DELETE), чтение событий позиции упорядоченно, константа NS для UUIDv5 — **B-03a**. Эта часть NFR-08 («журнал нельзя изменить») без хранения не проверяется и переносится туда.
- Приведение времени от клиента к каноническому `Instant` (нормализация) — сервер, **B-03a/B-17**. Домен только отклоняет неканоническую строку (К18).
- Граница «что система знала к моменту T» (`recordedAt ≤ T`) — фильтрует вызывающий; сценарий симулятора — **B-04**.
- Колонка «Учит прогноз» таблицы 5.2 и использование неявного приращения для обучения и калибровки — **B-08, B-13**.
- Количество для «съел порцию» из размера порции позиции, кнопки киоска — **B-17, B-24**; генерация автосписаний, их метка времени и строка-ключ — **B-06**; списание по рецепту и `operationId` — **B-19**; распознанный приход, `recognitionConfidence`, время с чека — **B-20**; ответ калибровки → инвентаризация — **B-13**.
- Журнал состояний позиции и возврат неактивной позиции покупкой — **B-12**.
- Лента журнала действий (события остатка + события состояния), экран — **B-17, B-30**.
- Проекция-кэш остатка и тест производительности на 500 тыс. событий — не вводится (ADR-003 §3); замер — **B-04**.
- Проверка, что все переданные события относятся к одной позиции: функции получают события одной позиции, это обязанность вызывающего (хранилище отдаёт события по `productId`).
- Остаток всех позиций одним проходом — по необходимости в B-10/B-17.
- Округление количеств (BR-18): дробные значения допустимы, тесты с дробями сравнивают с точностью, а не строго.
- Всё из «Чего нет в первой версии»: места хранения, открытые/закрытые упаковки, сроки годности, стоимость.

## Открытые вопросы

**Закрыты 2026-10-06 по варианту (а):** НВ-1 (`source` — непустая непрозрачная строка, закрытый список — в API-контракте B-16) — решение команды, домен по источнику ничего не решает; НВ-2 → Q-30 (владелец: число упаковок — только целое ≥ 1, дробное вводится в расходных единицах).

Нумерация «НВ» — внутренняя для этого черновика. Критерии написаны по рекомендации.

- **НВ-1. Набор значений `source`.** Спека (5.1) и ADR-003 §4 требуют источник, но перечисляют его примерно («киоск, телефон, чек, фото стола, голос, автосписание, калибровка, отпуск и т. п.»). Варианты: (а) в T-002 — непрозрачная непустая строка, закрытый список фиксируется в API-контракте B-16; (б) закрытый список сейчас: `kiosk`, `phone`, `receipt`, `table_photo`, `voice`, `auto_writeoff`, `calibration`, `absence`, `strike_out` — дополняется по задачам; (в) не вводить `source` до B-03a. Рекомендация — (а): домен по источнику ничего не решает, а список зависит от решений шага 5 (B-14 «вычёркивание», B-20, B-21); при (б) список пришлось бы менять несколько раз. Риск дрейфа значений («kiosk»/«киоск») закрывается в B-16. Критерий К5 (пустой `source`).
- **НВ-2. Может ли число упаковок быть дробным.** Спека молчит. Варианты: (а) только целое ≥ 1 — торговая упаковка дискретна, весовой товар и «полпачки» вводятся сразу в расходных единицах (К3); (б) любое конечное число больше нуля, как у коэффициента. Рекомендация — (а): FR-SL-07 и так оперирует целыми упаковками, а дробное число упаковок чаще опечатка, чем факт; приход в единицах покрывает остальное. Критерий К5 (`packs` 1,5).
