## Контекст

Экраны «все позиции» (киоск, список покупок, пересмотр) должны показывать остатки быстро и на 10-м году. Замер T-008 показал, что свёртка всего журнала из SQLite на каждый запрос занимает 2,6–3,4 с при пороге 100 мс. Задача вводит кэш остатков в памяти процесса. Позиции, которые изменились, кэш находит по знаку `seq` и пересобирает целиком через неизменённую `stockBalance`. Прогрев переносит пересборку с первого запроса экрана в фон. Правило свёртки остаётся одно, остаток числом на диске не хранится (инвариант 1).

## Бизнес-правила и требования

- BR-01 / инвариант 1 — остаток не хранится числом, а вычисляется из журнала. *(Здесь: кэш — производное в памяти, пересобираемое из журнала. Пересборка идёт только через `stockBalance(storage.listStockEvents(id))`, без приращений поверх кэша и без второй копии правил свёртки. ADR-003a §4.1.1, §4.1.3.)*
- BR-02 / инвариант 2 — отменённое событие исключается из расчёта, отмену можно отменить. *(Здесь: отмена, в том числе отмена значения-события и отмена отмены, получает новый `seq`, и её позиция пересобирается целиком. ADR-003a §4.1.2.)*
- BR-15 / инвариант 6 — отрицательный остаток не ошибка. *(Здесь: кэш хранит минус как есть, без обрезки и без отказа.)*
- ADR-003 §3 в редакции ADR-003a §4.2 — кэш по позиции, полная пересборка позиции, без частичной инвалидации. Изменения ищутся по `seq > w` при следующем чтении вне транзакции. Кэш можно выбросить в любой момент, при старте он прогревается.
- ADR-003a §4.1.4 — порядок чтения «все остатки»: знак `m = MAX(seq)` читается до пересборки. Пустой кэш — пересобрать все позиции каталога. `m > w` — пересобрать позиции из `productsChangedBetween(w, m)`. `m < w` — сбросить кэш целиком. Позиция без записи в кэше считается при обращении. `w := m` ставится только после того, как пересобраны все позиции шага.
- ADR-003a §4.1.5 — внутри открытой `storage.transaction` кэш не читается и не пополняется, остаток считается напрямую из журнала.
- ADR-003a §4.4 — `warm()` проходит путь `all()` и отбрасывает результат. Внутри транзакции он ничего не делает. Ошибку прогрева перехватывает вызывающий, знак при этом не сдвигается.
- NFR-07 — если прогрев не случился или упал, правильность не страдает.
- NFR-16, ADR-004 — домен (`src/domain/`) не меняется. Кэш живёт в `src/server/app/`, хранилище из домена импортирует только типы.
- `[Q-02]` — целевой сервер не выбран, поэтому замер К18 — сигнал, а не окончательный вердикт.

## Критерии приёмки

Критерии С1–Ш4 входят в общий набор `npm test` и не зависят от времени. Критерии К17-кэш.1–К17-прогрев.13 нумеруются по шагам ADR-003a §6.1 и идут на уменьшенном журнале К16 (20 тыс. событий), загруженном во временную файловую БД. К18 и «утро» выполняются только в `npm run perf`. Файлы, имена тестов и вспомогательные функции выбирает tester.

### Хранилище: узкие методы чтения

**С1. `maxStockSeq`.**
- Дано: новая БД.
- Когда: вызывается `maxStockSeq()` на пустом журнале, затем после записи нескольких событий, в том числе отмены.
- Тогда: на пустом журнале — 0, после записи — `seq` последнего записанного события. Повтор с тем же `id` (исход `exists`) и отказ (`rejected`) знак не меняют.

**С2. `productsChangedBetween`.**
- Дано: события позиций A, B, C с известными `seq`, среди них отмена события позиции B.
- Когда: вызывается для нескольких диапазонов.
- Тогда: возвращается множество различных позиций с `afterSeq < seq ≤ uptoSeq`, каждая один раз. Граница `afterSeq` исключена, `uptoSeq` включена. Отмена относит к позиции цели (B). Для пустого диапазона (`afterSeq ≥ uptoSeq`) и для диапазона без событий возвращается пустой список.

**С3. `inTransaction`.**
- Дано: открытое хранилище.
- Когда: признак читается вне транзакции, внутри `fn` транзакции, внутри вложенной транзакции, после фиксации и после отката исключением.
- Тогда: `true` внутри внешней и вложенной транзакции, `false` во всех остальных случаях. Вставка через `addStockEvent` вне явной транзакции после завершения оставляет `false`.

### Кэш: правильность (ADR-003a §6.1, К17-кэш)

Дано для всех шагов 1–10: журнал К16 уменьшенного объёма загружен во временную файловую БД, кэш создан и построен вызовом `all()`. Шаги выполняются последовательно на одной БД. После каждого шага `cache.all()` совпадает со свёрткой по всем позициям каталога.

**К17-кэш.1.** Приращение задним числом раньше последней инвентаризации позиции. Тогда: совпадает со свёрткой, а остаток этой позиции не изменился (ADR-003, пример 1).

**К17-кэш.2.** Приращение задним числом позже последней инвентаризации той же позиции. Тогда: совпадает со свёрткой, остаток позиции изменился на величину приращения.

**К17-кэш.3.** Отмена последнего действующего значения-события позиции. Тогда: совпадает со свёрткой, остаток пересчитан от предыдущего значения-события (ADR-003, пример 2).

**К17-кэш.4.** Отмена отмены из шага 3. Тогда: совпадает со свёрткой, остаток позиции равен остатку после шага 2.

**К17-кэш.5.** Отмены автосписаний нескольких позиций одним `recordSystemBatch` на поддельных часах (ретро-отпуск, ADR-003, пример 3). Тогда: совпадает со свёрткой по всем позициям пакета.

**К17-кэш.6.** Новая позиция добавлена в каталог после построения кэша, событий у неё нет. Тогда: `all()` содержит её с остатком 0, `balance(id)` = 0.

**К17-кэш.7.** Запись в `storage.transaction`, которая затем бросает исключение. Тогда: исключение проброшено, `all()` совпадает со свёрткой, остаток позиции, в которую писали, не изменился.

**К17-кэш.8.** Событие записано через второе соединение `openStorage` к тому же файлу и зафиксировано. Тогда: `all()` кэша первого соединения видит запись и совпадает со свёрткой.

**К17-кэш.9.** Внутри `storage.transaction` записано событие в позицию P, затем вызваны `balance(P)` и `all()`.
- Тогда: оба значения уже включают незафиксированную запись и равны прямой свёртке внутри транзакции.
- И: транзакция откатывается исключением, затем зафиксированной записью в другую позицию Q занимается тот же `seq`. После этого `all()` совпадает со свёрткой: у P нет откаченного события, у Q есть новое (ловушка ADR-003a §4.1.5).

**К17-кэш.10.** Среди остатков после шагов 1–9 есть отрицательные (если журнал их не даёт, шаг записывает расход больше остатка). Тогда: отрицательные значения кэша совпадают со свёрткой, без обрезки до 0 и без исключения.

### Кэш: прогрев (ADR-003a §6.1, К17-прогрев)

Дано: БД и кэш как выше. Хранилище, переданное кэшу, обёрнуто счётчиком вызовов `listStockEvents`.

**К17-прогрев.11.**
- Когда: зафиксированы автосписания по нескольким позициям (k позиций), затем вне транзакции вызван `warm()`, затем `all()`.
- Тогда: `all()` не вызывает `listStockEvents` ни разу и совпадает со свёрткой.

**К17-прогрев.12.**
- Когда: внутри `storage.transaction` после записи в этой транзакции вызывается `warm()`.
- Тогда: `warm()` не вызывает `listStockEvents`, а последующий `all()` вне транзакции ведёт себя так, будто `warm()` не вызывался.
- И: если транзакция затем откатывается, `all()` совпадает со свёрткой, откаченного события в нём нет.

**К17-прогрев.13.**
- Дано: изменены не меньше трёх позиций. Обёртка бросает исключение на `listStockEvents` после того, как пересобрана хотя бы одна из них, а хотя бы одна ещё не пересобрана.
- Когда: вызывается `warm()`, затем обёртка становится исправной и вызывается `all()`.
- Тогда: `warm()` пробрасывает исключение. `all()` совпадает со свёрткой по всем позициям, в том числе по тем, которые до сбоя не были пересобраны (знак не сдвинут, правило 4.1.4.6).

### Кэш: инвалидация по знаку (ADR-003a §4.1.4)

**Ш1. Без изменений журнал не перечитывается.**
- Дано: кэш построен.
- Когда: `all()` вызывается повторно без записей.
- Тогда: `listStockEvents` не вызывается, результат прежний.

**Ш2. Пересобираются только изменённые позиции.**
- Дано: кэш построен.
- Когда: зафиксированы события в k разных позиций (одна из них — отмена), затем вызван `all()`.
- Тогда: `listStockEvents` вызван ровно k раз, по одному на каждую из этих позиций. Результат совпадает со свёрткой.

**Ш3. Журнал стал короче (`m < w`).**
- Дано: кэш построен на БД с журналом длиной N. Обёртка хранилища затем начинает отдавать данные другой БД с той же структурой каталога, журнал которой короче N и отличается по остаткам (имитация подмены файла).
- Когда: вызывается `all()`.
- Тогда: результат совпадает со свёрткой второй БД по всем позициям.

**Ш4. Пустой кэш строится целиком.**
- Дано: новый кэш над БД К16.
- Когда: первый вызов `all()`.
- Тогда: `listStockEvents` вызван по одному разу на каждую позицию каталога, результат совпадает со свёрткой.

### Синтетический журнал: хвосты повторного ревью T-008 (общий набор и `npm run perf`)

**К16-доп.1. Период журнала выровнен по позициям.**
- Дано: журнал К16 (уменьшенный в `npm test`, полный в `npm run perf`).
- Тогда: у каждой из 200 позиций первое событие по `recordedAt` лежит в первых α периода журнала, а последнее — в последних α (параметр α). Остальные проверки К16 из T-008 выполняются без изменений.

**К16-доп.2. Позиции чередуются по всему журналу.**
- Тогда: в трёх окнах по 1000 событий подряд в порядке `seq` — в начале, в середине и в конце журнала — в каждом окне больше 20 различных позиций. Пороги — прежние из проверки T-008.

**К16-доп.3. Объекты событий для пути (а) пересоздаются по позиции.**
- Дано: журнал К16.
- Когда: строится вход пути (а) для К18.
- Тогда: для каждой позиции это новые объекты, созданные подряд по позиции. По значению они равны событиям журнала (`toEqual`), но это не те же ссылки. Остатки пути (а) по ним совпадают со свёрткой К17.

### Порог (только `npm run perf`, ADR-003a §6.2)

**К18 (новый путь (в) через кэш).**
- Дано: БД К17 полного объёма открыта заново, кэш создан. Холодное построение (первый `all()` на пустом кэше) замеряется отдельно и выводится, но не проверяется.
- Когда: прогрев 3 и замер 10 повторов. В каждом повторе, включая прогревочные, **вне замера** в самую тяжёлую позицию (больше всего событий) пишется одно событие через `createStockEvent` и `addStockEvent`. Повторы чередуют приращение задним числом раньше её последней инвентаризации и отмену её последнего действующего значения-события. **В замере** — `cache.all()`.
- Тогда: медиана ≤ 100 мс (порог прежний, без правки).
- И: в каждом замеренном повторе `listStockEvents` вызван ровно один раз — значит, замер измеряет пересборку, а не попадание в кэш.
- И: после замера остаток самой тяжёлой позиции из кэша равен `stockBalance(listStockEvents)` по ней.
- И: при провале текст: «сработало условие ADR-003 §3: кэш не укладывается, см. ADR-003a §7 (медиана … мс > 100 мс)».

**К18-утро.**
- Дано: та же БД и кэш после К18.
- Когда: вне замера — «ночной пакет», то есть по одному `auto_writeoff` в каждую из 60 ритмичных позиций одной транзакцией. Затем `warm()` (его время замеряется), затем одна отметка в самую тяжёлую позицию. В замере — один `cache.all()`.
- Тогда: время ≤ 100 мс. Остатки кэша после замера совпадают со свёрткой по 60 ритмичным позициям и по самой тяжёлой.

**К18-вывод (без проверки).**
- Тогда: в выводе есть путь (а) по объектам К16-доп.3 и путь (б), как в T-008, для тренда. Также выводятся медиана, p90, min и max пути (в), холодное построение, время `warm()` после «ночного пакета» и время «утра». Добавлены версия Node и пометка «замер в среде разработки, не на целевом сервере (Q-02)».
- И: если медиана (в) больше 50 мс или `warm()` после ночного пакета дольше 2 с, выводится строка «триггер D1 (ADR-003a §7)». Проверка от этого не падает.
- И: файлы К18 по-прежнему не попадают в `npm test`.

## Не входит в задачу

- Вызовы `warm()` из `main.ts` и из тика планировщика, логирование ошибок прогрева — см. таблицу выше.
- Узкое чтение колонок свёртки, лёгкое отображение строк вместо `toStock` (D1), покрывающий индекс (D2), прогрев порциями (D3) — отложено по ADR-003a §7. Триггеры видны в выводе К18.
- Изменения домена (`src/domain/`), в том числе `stockBalance` (M2): по ADR-003a §5 домен не меняется.
- Хранимая проекция (M6), частичная инвалидация и приращения (M4), снимок от значения-события (M3).
- Встраивание кэша в пути записи (`recordEvent`, `recordSystemBatch`): пути записи о кэше не знают (ADR-003a §4.2).
- Другие значения в записи позиции (прогноз, статусы — правило 4.1.8) — задачи шага 3 (B-08, B-10, B-11).
- Отдельная команда пересборки кэша — её роль играет рестарт (4.1.6).
- API и экраны «все позиции» — шаг 5 и далее.
- Замер на целевом сервере — после Q-02.
- Правка текста T-008 и ADR — делает delivery-lead.

## Открытые вопросы

- **НВ-7. Имена интерфейса.** ADR-003a §5 называет свой интерфейс эскизом: «имена окончательно выбирает задача backend-dev». Но тесты пишутся раньше реализации.
  - (а) Имена §5 (`maxStockSeq`, `productsChangedBetween`, `inTransaction`, `createBalanceCache`, `balance`, `all`, `warm`) фиксируются в этой задаче как контракт.
  - (б) Имена выбирает tester, backend-dev подстраивается.

  Рекомендация — (а): имена уже согласованы в принятом ADR, и не придётся решать это ещё раз.
- **НВ-8. Какая задача создаёт `src/server/main.ts` и проверку «старт → `warm()`».** В бэклоге нет строки, которая явно вводит `main.ts`. ADR-003a §10 относит вызов при старте к «новой задаче» кэша, но в T-009 вызывать его неоткуда.
  - (а) B-18 (планировщик): старт планировщика и так стоит в последовательности старта.
  - (б) B-16/B-17 (API): `main.ts` нужен прежде всего, чтобы слушать порт.
  - (в) Первая из B-06, B-16, B-18, которой понадобится `main.ts`.

  Рекомендация — (в), с пометкой в бэклоге у всех трёх строк: «при создании `main.ts` — `warm()` после открытия порта и проверка ADR-003a §6.1 о старте».
- **НВ-9. Кто запускает `npm run perf` до ревью.** Stop-хук его не запускает, а приёмка T-009 по ADR-003a §10 включает зелёный К18.
  - (а) backend-dev после зелёного `npm test` и записывает цифры в журнал задачи. reviewer запускает повторно.
  - (б) Только reviewer.

  Рекомендация — (а): если К18 окажется красным, это сразу видно в `impl`, и при медиане > 50 мс можно решать вопрос D1 до ревью.
