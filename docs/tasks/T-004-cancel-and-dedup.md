## Контекст

Ошибочную отметку нужно уметь отменить так, чтобы остаток стал таким, будто её не было, и вернуть отменённое, если ошиблись с отменой. Двойное нажатие на киоске и повтор запроса при плохой связи не должны удваивать покупку или расход.

### Граница задачи

Домен и хранение, без HTTP — как в T-001…T-003.

- **Отмена.** Новый тип события `cancel` со ссылкой на отменяемое событие той же позиции (ADR-003 раздел 2). Свёртка не учитывает аннулированные события — их нет ни в остатке, ни в шагах. Отмена отмены восстанавливает событие. Исходная строка не меняется (инвариант 2).
- **Повтор.** Событие с уже записанным `id` не пишется повторно; запись возвращает уже записанное событие без ошибки (BR-26, ADR-002: `ON CONFLICT(id) DO NOTHING`).
- **Хранение.** Одна новая колонка `target_id` — новой миграцией `0003-stock-event-cancel.sql` (`ALTER TABLE stock_events ADD COLUMN target_id TEXT`). Миграцию 0002 не переписываем. `group_id` не вводится (ADR-003 раздел 2: не нужен без отмены группы).

### Принятые решения (предложение analyst, на усмотрение команды)

- Р-1. Ввод отмены: `{ id, productId, type: 'cancel', targetId }`. `productId` обязателен, как у остальных событий; цель должна существовать и принадлежать этой позиции, иначе ошибка по полю `targetId`. «Чужое событие» — событие другой позиции. Количество у отмены не хранится (`qty` пусто), переданные `qty` и `occurredAt` игнорируются.
- Р-2. Время отмены: `occurred_at = recorded_at = now` (ADR-003 раздел 3). На свёртку оно не влияет: отмена действует в точке времени цели.
- Р-3. **Повтор с тем же `id` (решение команды).** Если событие с таким `id` уже записано, запись возвращает `{ ok: true, event }` с уже записанным событием и ничего не пишет — независимо от содержимого повтора (другой тип, количество, позиция или даже недопустимый ввод). Проверка «уже записано» идёт до проверки ввода. Признака «это повтор» в ответе нет. Сравнение содержимого и ошибка «тот же id, другое содержимое» не делаются — по принципу простоты.
- Р-4. Отменить можно любое событие позиции, в том числе уже отменённое (ещё одна отмена ничего не меняет — ADR-003: несколько действующих отмен как одна) и саму отмену (восстанавливает цель). Ограничений по давности нет. Окно 5 секунд на киоске (FR-KSK-11) — только показ кнопки, это экран.
- Р-5. `getStockEvents` возвращает все строки позиции, включая отмены и отменённые события; у события появляется поле `targetId` (`null` у не-отмен). «Действующее/аннулированное» в чтение не добавляется — это нужно ленте позиции (B-29), не этой задаче.
- Р-6. Решение Р-4 из T-002 (смена единицы зависит от событий) не применяется: с T-003 единица меняется всегда.

### Что меняется в тестах T-003

- К4: колонки `stock_events` — ровно `seq, id, product_id, type, qty, occurred_at, recorded_at, target_id`; перечень типов в домене — `purchase, used, ran_out, recount, cancel`.
- К9: `cancel` убирается из списка недопустимых типов.

## Бизнес-правила

- BR-02 — отмена ошибочной отметки выполняется компенсирующим событием отмены, которое ссылается на исходное и аннулирует его в свёртке; исходное событие не удаляется. Отмена отмены восстанавливает исходное событие.
- BR-26 — каждое событие получает идентификатор на клиенте. Повторная отправка события с тем же идентификатором не создаёт дубль.
- BR-01 — остаток не хранится числом, это свёртка действующих событий по времени события (ADR-003 раздел 1).
- BR-15 — минус в остатке, в том числе после отмены (например, отменили покупку), не ошибка и не блокирует запись (инвариант 6).
- FR-LOG-02 — любое событие в журнале можно отменить. Здесь — события остатка; отмена изменений позиции (`product_changes`) — B-17 / B-30.
- NFR-07 — повтор и отмена не ломают работу: повтор не даёт ошибки.
- NFR-08 — отмена видна в журнале как отдельное событие.

## Критерии приёмки

Доменные проверки — без базы, хранение — на `openDb(':memory:')` с фиксированными часами. «Молоко» — позиция с единицей «бутылка». Идентификаторы событий задаёт тест.

**К1. Отмена отметки возвращает остаток как без неё (BR-02, FR-LOG-02).**
- Дано: «Молоко»: покупка 6 (id `e1`), использовал 1 (id `e2`); остаток 5
- Когда: записывают отмену `c1` с целью `e2`
- Тогда: запись успешна; остаток 6; `getStockEvents` возвращает три события, `e2` прочитан без изменений, у `c1` тип `cancel`, `targetId` = `e2`, количество пусто, `occurred_at` и `recorded_at` равны часам записи
- И: если вместо этого отменить покупку `e1`, остаток −1, запись без ошибки (BR-15)

**К2. Отмена события-значения — остаток как без якоря (ADR-003 разделы 2–3).**
- Дано: «Молоко»: 03.10 10:00 покупка 6; 04.10 08:00 использовал 1; 04.10 21:00 пересчитал 3 (id `r1`); 05.10 09:00 использовал 1; остаток 2
- Когда: отменяют `r1`
- Тогда: остаток 4 (6 − 1 − 1); в шагах свёртки нет ни `r1`, ни отмены
- И: то же для «закончилось»: покупка 3, «закончилось», покупка 2 → остаток 2; после отмены «закончилось» — 5

**К3. Отмена отмены восстанавливает событие.**
- Дано: К1 после отмены `c1` (остаток 6)
- Когда: записывают отмену `c2` с целью `c1`
- Тогда: остаток снова 5; в журнале четыре события, ни одно не изменено
- И: повторная отмена уже отменённого события (`c3` с целью `e2` при действующей `c1`) записывается без ошибки, остаток остаётся 6

**К4. Повтор с тем же id не создаёт дубль (BR-26, Р-3).**
- Дано: «Молоко»; часы 12:00; записана покупка 2 с id `p1`
- Когда: в 12:05 повторно отправляют покупку 2 с id `p1`; затем с id `p1`, но «использовал» 5
- Тогда: оба раза `{ ok: true }` и возвращается событие, записанное в 12:00 (тот же `seq`, тип, количество, `recorded_at`); в `stock_events` одна строка с `p1`; остаток 2
- И: повтор отмены (тот же id, та же цель) тоже даёт одну строку, остаток не меняется

**К5. Недопустимая отмена отклоняется по полю без записи.**
- Дано: «Молоко» с событием `e1`; «Хлеб» с событием `b1`
- Когда: по одному прогону пишут отмену для «Молоко»: без `targetId`; с `targetId` несуществующего события; с `targetId` = `b1` (событие другой позиции); для несуществующей позиции
- Тогда: ошибка с полем `targetId` (в последнем случае — `productId`); в `stock_events` ничего не записано, остатки не изменились

## Не входит в задачу

- Отмена группы событий и колонка `group_id` (приход по чеку, пересчёт по фото) — с первой задачей, где группа нужна.
- Отмена изменений позиции (`product_changes`, `reverts_id`) — B-17 / B-30.
- Лента позиции и журнал действий: признак «аннулировано», зачёркивание, порядок по времени записи — B-29 и экран журнала.
- Кнопка «отменить» на киоске и её окно 5 секунд (FR-KSK-11) — экран.
- HTTP-маршруты, коды ответов на повтор — B-16 / B-17.
- Проверка, что повтор совпадает по содержимому с записанным (Р-3).
- Темп и оценка с учётом отмен — B-06 (берут шаги свёртки, где аннулированных уже нет).
