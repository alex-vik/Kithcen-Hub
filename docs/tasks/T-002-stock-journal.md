## Контекст

Остаток позиции — единственное, ради чего ведётся учёт, и он должен выводиться из журнала того, что произошло, а не храниться числом. Задача даёт журнал событий остатка всех типов из 5.2 (кроме отмены), запись прихода в упаковках с пересчётом в расходную единицу и вычисление остатка свёрткой, на которую дальше опираются автосписание, прогноз, статусы и калибровка.

### Граница задачи (предложение, как в T-001)

Домен **и** хранение, без HTTP.

- `src/domain/`: типы событий остатка и их класс (дельта «+», дельта «−», значение); проверка ввода события; пересчёт прихода в расходные единицы (через `packagesToUnits` из T-001); чистая функция свёртки: на вход — события одной позиции с `seq`, на выход — остаток и шаги `{eventId, before, after}` (ADR-003, раздел 1, «Последствия»); доменная проверка запрета смены расходной единицы при наличии событий. Без времени, базы и случайности (ADR-004).
- `src/server/db/`: миграция `0002-…` — таблица `stock_events` с триггерами append-only (ADR-002) и индексом `(product_id, occurred_at)`; функции «записать событие», «прочитать события позиции», «остаток позиции» (чтение + доменная свёртка, на лету, без проекции — ADR-003, раздел 6); `updateProduct` учитывает запрет смены единицы.
- Идентификатор события приходит извне (ADR-004: клиент, BR-26); `seq` и `recorded_at` назначает хранение; `recorded_at` = переданное `now`.
- HTTP-маршрутов нет — они в B-17 по контракту B-16.

### Типы событий (5.2, ADR-003, раздел 1)

| Тип | Класс | Что хранится |
| --- | --- | --- |
| Покупка | дельта + | количество в расходных единицах; при вводе в упаковках — ещё число упаковок и коэффициент этой покупки (указанный во вводе, иначе коэффициент позиции на момент записи) |
| Потребление порции | дельта − | количество |
| Автосписание по норме | дельта − | количество |
| Списание по рецепту / блюду | дельта − | количество |
| Выброс из-за порчи | дельта − | количество |
| «Закончилось» | значение | ничего (значение 0 по типу) |
| Инвентаризация | значение | фактическое значение |

Отмена (5.2, последняя строка) — B-03. Количество дельт хранится положительным, знак задаёт тип (ADR-003, `signedQty`).

### Принятые решения

- Р-1 (бывш. В-1, источник — [Q-28], открыт у владельца, P3, к шагу 6 и B-20). Реализуется значение по умолчанию: покупка в упаковках, когда коэффициента нет ни у позиции, ни во вводе покупки, отклоняется с ошибкой по полю `packageFactor`, ничего не пишется. Приход в расходных единицах доступен всегда. Распознанные чеки (BR-17) — B-20. Критерий К14.
- Р-2 (бывш. В-2, источник — BR-04). Во вводе покупки можно указать коэффициент этой покупки — он используется для пересчёта и сохраняется в событии; если не указан, берётся коэффициент позиции. Коэффициент позиции при этом не меняется. Критерий К13.
- Р-3 (бывш. В-3, источник — решение команды). Проверка ввода события, а не остатка — остаток не ограничивается (инвариант 6, BR-15):
  - количество дельты > 0; значение инвентаризации ≥ 0;
  - покупка — количество или число упаковок > 0;
  - остальное не проверяется: лишние поля игнорируются (упрощено 2026-10-06 по принципу владельца).
  - Критерий К23.
- Р-4 (бывш. В-4, источник — решение команды, следует из инвариантов 3–4). Смену расходной единицы блокирует любое событие позиции в журнале, включая отменённые. В B-02 отмен нет, критерий К24 от решения не зависит. **Для B-03:** запрет смены единицы проверяет наличие любых строк `stock_events` позиции, а не только действующих событий.
- П-1 (принято). Время события (`occurred_at`) не передано — равно `recorded_at`. Время события позже `recorded_at` заменяется на `recorded_at` без допуска (ADR-003, раздел 3); допуск, если нужен, — в API-контракте B-16.
- П-2 (принято). События пишутся и для неактивной позиции, активность при этом не меняется: FR-CAT-06 требует, чтобы покупка неактивной позиции была возможна; сам возврат в активные — B-12.
- П-3 (принято). Событие для несуществующей позиции отклоняется ошибкой по полю позиции, ничего не пишется.

## Бизнес-правила

- BR-01 — Остаток не хранится числом. Он вычисляется свёрткой событий журнала по позиции в порядке времени события: события-приращения (приход, расход, списание) складываются, события-значения (инвентаризация, «закончилось») задают остаток заново. Событие задним числом раньше последнего события-значения не меняет текущий остаток, а только историю для обучения нормы. (Решение владельца 2026-10-06, ADR-003.)
- BR-02 (только часть «исходное событие не удаляется») — события не удаляются и не редактируются; механизм отмены — B-03.
- BR-03 — Остаток и норма ведутся в расходной единице. Приход в торговых упаковках пересчитывается через коэффициент.
- BR-04 — Разные размеры упаковки одного продукта — одна позиция. Различается только количество в событии прихода. (Здесь: коэффициент покупки во вводе — Р-2.)
- BR-05 — Разная расходная единица означает разные позиции (здесь: остатки позиций независимы; единица позиции с событиями не меняется — решение команды из T-001).
- BR-06 — Места хранения не различаются: холодильник, кладовка и морозилка дают один общий остаток.
- BR-07 — Открытые и закрытые упаковки не различаются.
- BR-15 — Отрицательный расчётный остаток — не ошибка данных, а сигнал расхождения. Уход в минус не блокирует работу (инвариант 6).
- NFR-08 — Все изменения остатка прослеживаются через журнал событий.
- NFR-07 — мягкая деградация: позиция без событий имеет остаток 0, а не ошибку (FR-CAT-07 — первый запуск без инвентаризации).

## Критерии приёмки

Доменные проверки — без базы, события подаются массивом с явными `seq` и `occurred_at`. Проверки хранения — на `openDb(':memory:')` с фиксированными часами (ADR-002, 14.4). «Позиция кофе» — из T-001 (г, коэффициент 250, норма 20). Времена — UTC.

### Свёртка (домен) — BR-01, BR-15

**К1. Позиция без событий.**
- Дано: пустой список событий
- Когда: вызывают свёртку
- Тогда: остаток 0, шагов нет

**К2. Дельты складываются со знаком по типу.**
- Дано: покупка 500, порция 10, автосписание 20, списание по рецепту 30, выброс 40 — в порядке времени
- Когда: вызывают свёртку
- Тогда: остаток 400; шагов 5, у каждого `eventId` своего события и `before`/`after`: 0→500, 500→490, 490→470, 470→440, 440→400

**К3. «Закончилось» обнуляет, следующая покупка прибавляется к нулю.**
- Дано: покупка 500, порция 10, «закончилось», покупка 250
- Когда: вызывают свёртку
- Тогда: остаток 250; шаг «закончилось» — 490→0

**К4. Инвентаризация задаёт значение, неявная дельта видна в шагах.**
- Дано (кофе, ADR-003 раздел 3): 03.10 10:00 покупка 500; 04.10 00:00 автосписание 20; 04.10 21:00 инвентаризация 450; 05.10 00:00 автосписание 20
- Когда: вызывают свёртку
- Тогда: остаток 430; шаг инвентаризации — 480→450 (неявная дельта −30); неявная дельта нигде не задана во входе

**К5. Событие задним числом до последнего значения не меняет остаток.**
- Дано: события К4 и ещё порция 10 с `occurred_at` 04.10 08:00 и `seq` больше всех остальных
- Когда: вызывают свёртку
- Тогда: остаток 430 (как в К4); шаг инвентаризации — 470→450 (неявная дельта −20); шаг порции стоит между автосписанием 04.10 и инвентаризацией

**К6. Событие задним числом после последнего значения меняет остаток.**
- Дано: события К4 и ещё порция 10 с `occurred_at` 05.10 08:00 и `seq` больше всех остальных
- Когда: вызывают свёртку
- Тогда: остаток 420

**К7. Порядок — по `(occurred_at, seq)`, а не по порядку во входе.**
- Дано: (а) одинаковое `occurred_at` у инвентаризации 100 (`seq` 1) и покупки 50 (`seq` 2); (б) то же с `seq` наоборот; (в) события К5, поданные в обратном и в перемешанном порядке
- Когда: вызывают свёртку
- Тогда: (а) 150; (б) 100; (в) результат и шаги совпадают с К5

**К8. Минус не блокируется (BR-15, инвариант 6).**
- Дано: покупка 100, порция 150; затем отдельно: те же события + инвентаризация 200; те же события + «закончилось»
- Когда: вызывают свёртку
- Тогда: остаток −50 без ошибки и исключения; с инвентаризацией — 200 (шаг −50→200); с «закончилось» — 0 (шаг −50→0)

**К9. Свёртка чистая.**
- Дано: массив событий К5 (глубокая копия сохранена)
- Когда: вызывают свёртку дважды
- Тогда: результаты равны; входной массив и объекты событий не изменились (сравнение с копией)

### Приход в упаковках — BR-03, инвариант 3

**К10. Приход в упаковках пересчитывается и хранит исходные данные.**
- Дано: позиция кофе (коэффициент 250), часы 2026-10-06T10:00:00Z
- Когда: записывают покупку 2 упаковки
- Тогда: в событии количество 500 (в г), число упаковок 2, коэффициент 250; остаток позиции 500

**К11. Смена коэффициента не меняет старые события (инвариант 3).**
- Дано: состояние после К10
- Когда: меняют коэффициент позиции на 1000 (`updateProduct`), затем записывают покупку 1 упаковка
- Тогда: первое событие при чтении — количество 500, упаковки 2, коэффициент 250; второе — 1000, 1, 1000; остаток 1500

**К12. Приход сразу в расходных единицах.**
- Дано: позиция «Сыр» (г, без коэффициента)
- Когда: записывают покупку 300 (в расходных единицах)
- Тогда: событие записано: количество 300, число упаковок и коэффициент пустые; остаток 300

**К13. Разный размер упаковки — одна позиция (BR-04, Р-2).**
- Дано: позиция «Молоко» (мл, коэффициент 1000)
- Когда: записывают покупку 1 упаковка с коэффициентом покупки 500 и покупку 1 упаковка без коэффициента покупки
- Тогда: количества 500 и 1000, сохранённые коэффициенты 500 и 1000; остаток 1500; коэффициент позиции по-прежнему 1000, записей в `product_changes` не добавилось

**К14. Приход в упаковках без коэффициента. `[Q-28]` (значение по умолчанию, Р-1)**
- Дано: позиция «Гречка» (г, без коэффициента)
- Когда: записывают покупку 2 упаковки без коэффициента покупки
- Тогда: ошибка с полем `packageFactor`; в `stock_events` ничего не записано; остаток 0
- И: покупка 2 упаковки той же позиции с коэффициентом покупки 800 записывается — количество 1600, упаковки 2, коэффициент 800; коэффициент позиции по-прежнему пуст

### Журнал и хранение — BR-01, BR-02, NFR-08

**К15. Каждый тип события записывается и читается.**
- Дано: позиция кофе, часы 2026-10-08T12:00:00Z
- Когда: параметризованный тест — по одному прогону на каждый из 7 типов (5.2, без отмены) с идентификатором, заданным тестом, и `occurred_at` 2026-10-08T09:00:00Z
- Тогда: чтение событий позиции возвращает событие с тем же идентификатором, позицией, типом, количеством / значением (у «закончилось» — пусто), `occurred_at` 09:00, `recorded_at` 12:00

**К16. `seq` и время события.**
- Дано: позиция кофе, часы 2026-10-08T12:00:00Z
- Когда: записывают подряд три события: без `occurred_at`; с `occurred_at` 2026-10-08T15:00:00Z (позже часов); с `occurred_at` 2026-10-05T08:00:00Z
- Тогда: `seq` строго возрастает в порядке записи; `occurred_at` первого и второго — 12:00 (П-1), третьего — 05.10 08:00; `recorded_at` у всех — 12:00

**К17. Журнал неизменяем (инвариант 2).**
- Дано: позиция кофе и записанная покупка
- Когда: выполняют прямым SQL `UPDATE` и, отдельно, `DELETE` этой строки `stock_events`
- Тогда: оба запроса завершаются ошибкой, строка не изменилась

**К18. Остаток нигде не хранится; мест хранения и открытости нет (инвариант 1, BR-06, BR-07).**
- Дано: база после миграций
- Когда: читают колонки `products` и `stock_events` (`PRAGMA table_info`) и список таблиц
- Тогда: колонки `products` совпадают с перечнем T-001 К8; колонки `stock_events` совпадают с перечнем, зафиксированным в тесте (идентификатор, позиция, тип, количество / значение, число упаковок, коэффициент, `occurred_at`, `recorded_at`, `seq`); нет колонок и таблиц остатка, накопленного итога, «остатка после события», места хранения, признака открытой упаковки

**К19. Остаток из хранения = свёртка журнала (NFR-08).**
- Дано: позиция кофе; через хранение записаны события К5 (в том порядке `seq`, как там)
- Когда: запрашивают остаток позиции
- Тогда: остаток 430 и шаги совпадают с результатом доменной свёртки над событиями, прочитанными из `stock_events`; каждый `eventId` шагов есть в `stock_events`; повторный запрос даёт тот же результат; остаток позиции без событий — 0; для несуществующей позиции — пусто (не 0)

**К20. Остатки позиций независимы (BR-05).**
- Дано: «Кофе в зёрнах» (г) и «Кофе в капсулах» (шт)
- Когда: записывают покупку 500 зёрен и порцию 2 капсулы
- Тогда: остаток зёрен 500, капсул −2 (без ошибки); события каждой позиции читаются только по ней

**К21. Минус не блокируется при записи (инвариант 6).**
- Дано: позиция кофе с остатком 100
- Когда: записывают порцию 150, затем выброс 10
- Тогда: оба события записаны без ошибки; остаток −60

**К22. Неактивная позиция принимает события (П-2).**
- Дано: позиция кофе, переведённая в неактивные прямым SQL в тесте (смена активности — B-12)
- Когда: записывают покупку 1 упаковка
- Тогда: событие записано, остаток 250; признак активности по-прежнему «неактивна», записей в `product_changes` не добавилось

**К23. Недопустимый ввод события отклоняется без записи (Р-3).**
- Дано: позиция кофе
- Когда: параметризованный тест, по одному прогону на случай:
  - тип вне перечня 5.2 (в том числе «отмена» — до B-03)
  - позиция не существует (П-3)
  - дельта без количества или с количеством 0 / −1
  - инвентаризация без значения или со значением −1
  - покупка без количества и без упаковок; покупка с числом упаковок 0
- Тогда: доменная проверка возвращает ошибку с именем поля; в `stock_events` ничего не записано
- И: инвентаризация 0 и дробные значения (0,5 упаковки, коэффициент покупки 0,5, 12,5 г) принимаются
- И: ни один из отклонённых случаев не связан с остатком — порция больше остатка принимается (К21)

### Расходная единица позиции с событиями — BR-05, инварианты 3–4

**К24. Единицу нельзя сменить, пока у позиции есть события.**
- Дано: позиция кофе (г) с одной записанной покупкой
- Когда: (а) правят расходную единицу на «шт»; (б) в одной правке меняют единицу на «шт» и норму на 25
- Тогда: в обоих случаях ошибка с полем `consumptionUnit`; единица и норма при чтении прежние; новых записей в `product_changes` нет
- И: доменная проверка правки, получив признак «у позиции есть события», возвращает ту же ошибку без базы
- Признак «есть события» — наличие любой строки позиции в `stock_events` (Р-4; с B-03 — включая отменённые)

**К25. Без событий единица меняется; остальное правится и с событиями.**
- Дано: (а) позиция кофе без событий; (б) позиция кофе с одной покупкой
- Когда: (а) меняют единицу на «шт»; (б) меняют норму, коэффициент и название; (б′) сохраняют правку с той же единицей «г»
- Тогда: (а) единица «шт», запись в `product_changes` (как T-001 К4); (б) правка применена; (б′) успех без ошибки и без новой записи (T-001 К9)

## Не входит в задачу

- Отмена события, отмена отмены, «действующие» события в свёртке — B-03 (T-003). В B-02 все события действующие; тип «отмена» отклоняется (К23).
- Идемпотентность по клиентскому идентификатору (BR-26): поведение при повторе идентификатора — B-03. В B-02 идентификатор только принимается и сохраняется.
- Автосписание как механизм (кто и когда пишет, детерминированный id, локальный день) — B-06; здесь только тип события.
