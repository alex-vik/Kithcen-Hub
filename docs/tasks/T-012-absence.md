## Контекст

Когда дома никого нет, ритмичные позиции не расходуются. Если система продолжает их списывать, после возвращения остаток занижен, а инвентаризация показывает ложное «откуда-то взялось». Пользователь задаёт период отпуска датами, заранее или после возвращения. На дни отпуска автосписания не пишутся, а уже записанные за эти дни отменяются.

## Бизнес-правила и требования

- FR-ABS-01 — период отсутствия задаётся датами начала и окончания. *(Здесь: доменная сущность `AbsencePeriod` (5.1 спеки) и сценарий записи в `app`. Обе даты — `LocalDate` по Вильнюсу, **обе включительно**: так в ADR-003, пример 3 («отпуск 10.10–13.10» отменяет А10…А13). Кнопки и экрана здесь нет.)*
- FR-ABS-02 — период задаётся заранее или задним числом. *(Здесь: нет ограничений на положение периода относительно «сегодня». Прошлый, текущий и будущий периоды записываются одинаково.)*
- FR-ABS-03 — на время отпуска автосписания не выполняются, список покупок не формируется. *(Здесь — только автосписания: сутки D, попадающие в любой записанный период, планировщик обрабатывает без событий и отмечает в курсоре. Списка покупок ещё нет, его часть — B-11, см. «Не входит».)*
- FR-ABS-04 — ретроспективная отметка отменяет уже выполненные автосписания за эти дни. *(Здесь: в одной транзакции с записью периода на каждое **действующее** `auto_writeoff`, у которого сутки D (местная дата `occurredAt`) попадают в период, пишется `cancel`. Ключ — `absence_cancel:{target_id}`, `id` = UUIDv5, `occurredAt` = `clock.now()` (ADR-003 §5.3), `source = 'absence'`. ADR-005.)*
- BR-02 / инвариант 2 — события не удаляются и не правятся. *(Здесь: отпуск выражается только новыми событиями `cancel`. Таблица периодов тоже работает только на добавление.)*
- BR-26 — повтор не создаёт дублей. *(Здесь: повтор записи того же периода, а также пересекающийся период новых отмен не создают: ключ зависит только от цели. Повтор записи периода с тем же `id` ничего не пишет.)*
- BR-27, NFR-14 — сутки по Вильнюсу. *(Здесь: принадлежность автосписания периоду определяется по `localDateOf(occurredAt)`, сутки перехода на летнее/зимнее время — ровно одни сутки.)*
- BR-15 / инвариант 6 — минус не ошибка. *(Здесь: ни запись периода, ни отмены не проверяют остаток.)*
- NFR-07 — мягкая деградация. *(Здесь: отпуск, отмеченный поздно или не отмеченный вовсе, ничего не ломает. Сбой записи отпуска не оставляет половины операции.)*
- NFR-16 — домен чистый. *(Здесь: поиск отменяемых автосписаний и проверка «день в отпуске» — чистые функции без часов.)*

`recordAbsence`:

1. `id` — клиентский UUID v4 в нижнем регистре, тем же правилом, что в `recordEvent` (ADR-003 §8). Иначе `rejected: 'id'`, ничего не пишется.
2. `createAbsencePeriod` с `recordedAt = clock.now()`. Отказ домена — `rejected` с его атрибутом.
3. Одна `storage.transaction`:
   - есть период с этим `id`: те же `start`/`end` → `repeat`, `cancelled = 0`, новых событий нет; другие даты → `conflict` с записанным периодом, ничего не пишется;
   - иначе `addAbsencePeriod`, затем `absenceCancels` по событиям всех позиций и один `recordSystemBatch` с элементами `{ kind: 'cancel', productId, targetId, key, occurredAt: clock.now(), source: 'absence' }`. Пакет вернул `rejected` → исключение внутри транзакции, весь отпуск откатывается (как `runPending`, T-010 А11).
4. Ошибки хранилища не перехватываются ни внутри транзакции, ни снаружи — пробрасываются как есть (хвост T-011 НВ-1).

## Критерии приёмки

Все критерии — в общем наборе `npm test`. Время фиксированное и передаётся явно: в домене — параметром, на сервере — поддельными часами `Clock`. Сервер — на `:memory:` или временном файле. Пояс — `Europe/Vilnius`, `autoWriteoffTime = '00:00'`. Позиции, нормы и вспомогательные функции выбирает tester. «Автосписание за D» — событие `auto_writeoff` с `occurredAt = dayBounds(D).start`.

### Домен

**Д1. `isLocalDate`.**
- Тогда: `true` для `2026-10-07`, `2028-02-29`, `2026-12-31`. `false` для `2026-02-29`, `2026-13-01`, `2026-10-7`, `2026-10-07T00:00:00.000Z`, `''`, `20261007`, числа и `undefined`.

**Д2. `createAbsencePeriod`: проверки.**
- Тогда:
  - `start = end = '2026-10-10'` → `ok` (однодневный период);
  - `start = '2026-10-13'`, `end = '2026-10-10'` → отказ `'end'`;
  - `start = '2026-02-30'` → `'start'`; `end = 'завтра'` → `'end'`; `id = '  '` → `'id'`; `recordedAt = '2026-10-15'` → `'recordedAt'`;
  - период в прошлом (`2020-01-01…2020-01-05`) и в будущем (`2030-07-01…2030-07-14`) — `ok`: положение относительно «сегодня» домен не знает и не проверяет (FR-ABS-02).
- И: на невалидном вводе исключений нет.

**Д3. `isAbsenceDay`: границы включительно.**
- Дано: периоды `2026-10-10…2026-10-13` и `2026-10-20…2026-10-20`.
- Тогда: `true` для `10-10`, `10-11`, `10-13`, `10-20`; `false` для `10-09`, `10-14`, `10-19`, `10-21`. При пустом списке — `false` для любой даты.
- И: пересекающиеся периоды `10-10…10-13` и `10-12…10-15` дают `true` для `10-10` … `10-15` и `false` для `10-16`.

**Д4. `autoWriteoffsForDay` пропускает дни отпуска.**
- Дано: ритмичная активная позиция с нормой 20 (как Д7 T-010), период `2026-10-10…2026-10-13`.
- Тогда: для `10-09` и `10-14` — по одному элементу, как в T-010; для `10-10` … `10-13` — `[]`.
- И: с `absences = []` результат совпадает с T-010 Д7–Д11 (тесты T-010 зелёные после механической правки вызова).

**Д5. `absenceCancels`: что отменяется.**
- Дано: события двух ритмичных позиций P и Q: автосписания за `10-09` … `10-14` у обеих. У P — порция с `occurredAt` в `10-11 12:00` местного времени, инвентаризация в `10-12 22:00` и покупка в `10-11 09:00`. Период `2026-10-10…2026-10-13`.
- Тогда: ровно 8 элементов — автосписания P и Q за `10-10` … `10-13`, по возрастанию `seq`. У каждого `productId` — позиция цели, `targetId` — `id` автосписания, `key = 'absence_cancel:{targetId}'`. Автосписаний за `10-09` и `10-14`, порции, инвентаризации и покупки в результате нет.

**Д6. Уже отменённые не отменяются повторно; `cancelledIds` — только принадлежность (хвост ревью T-003).**
- Дано: как Д5, плюс:
  - автосписание P за `10-10` отменено пользовательской отменой C1;
  - автосписание P за `10-11` отменено отменой C2, а C2 отменена отменой C3 (автосписание снова действует);
  - автосписание Q за `10-12` уже отменено отменой с ключом `absence_cancel:…` от более раннего периода;
  - в `events` есть отмена с `targetId`, которого нет среди событий (висячая ссылка).
- Тогда: в результате нет P/`10-10` и Q/`10-12`, есть P/`10-11`. Всего 6 элементов. Висячая ссылка на результат не влияет.

**Д7. Сутки перехода времени (BR-27).**
- Дано: автосписания за `2026-03-28`, `03-29`, `03-30`, `2026-10-24`, `10-25`, `10-26`, у каждого `occurredAt = dayBounds(D).start` (для `10-25` — `2026-10-24T21:00:00.000Z`, для `03-29` — `2026-03-28T22:00:00.000Z`).
- Тогда: период `2026-03-29…2026-03-29` даёт ровно автосписание за `03-29`, период `2026-10-25…2026-10-25` — ровно за `10-25`. Соседние сутки не задеты.

**Д8. Чистота.**
- Тогда: повторный вызов `absenceCancels`, `isAbsenceDay`, `createAbsencePeriod` с теми же аргументами даёт равный результат. Подмена `Date.now` на результат не влияет. Входные массивы и объекты не изменяются.

### Хранилище

**Х1. Миграция.**
- Дано: БД на версии 2 (после T-010) с данными каталога, журналом и `job_runs`; новая пустая БД.
- Когда: `openStorage`.
- Тогда: обе БД на `user_version = 3`, таблица `absence_period` есть, прежние данные не изменились. Проверки нумерации миграций T-004 проходят. Если тест T-004/T-010 перечисляет таблицы схемы, его ожидание дополняется `absence_period` — по основанию, как правка К2 в T-010.

**Х2. `addAbsencePeriod` / `listAbsencePeriods`.**
- Тогда: на пустой таблице список пуст. После добавления периодов `10-20…10-20`, `10-10…10-13`, `10-12…10-15` список возвращает их в порядке `start_day`, с теми же полями. Повтор с тем же `id` и другими датами возвращает `exists` с **первоначальным** периодом, строк не прибавилось.
- И: `UPDATE` и `DELETE` строки `absence_period` прямым SQL отклоняются триггером. `INSERT OR REPLACE` с существующим `id` отклоняется.
- И: добавление внутри `storage.transaction`, которая затем откатывается исключением, строки не оставляет.

### Сценарий `recordAbsence` (`app`, поддельные часы)

Дано для О1–О11, если не сказано иное: ритмичные позиции P (кофе, г, норма 20) и Q (норма 1), `burst`-позиция B. Курсор автосписания и автосписания за нужные сутки подготовлены через `createAutoWriteoff(...).runPending()` на поддельных часах, а не вставкой напрямую. «Отмены отпуска» — события `kind = 'cancel'`, `source = 'absence'`.

**О1. Ретро-отпуск после инвентаризации — ADR-003, пример 3 целиком (FR-ABS-04).**
- Дано: у P события из примера 3: инвентаризация 500 в `2026-10-08 23:00`, автосписания за `10-09` … `10-13` через `runPending`, инвентаризация 480 в `10-13 22:00`, автосписание за `10-14`. Часы — `2026-10-15 09:00` по Вильнюсу.
- Когда: `recordAbsence({ id, start: '2026-10-10', end: '2026-10-13' })`.
- Тогда: исход `new`; `cancelled = 8` (P и Q за 4 суток); у P ровно 4 отмены отпуска — на автосписания `10-10` … `10-13`. У каждой `id = derivedId('absence_cancel:{target}')`, `occurredAt = recordedAt = now`, `productId` = P.
- И: остаток P = 460 до и после. В `stockLedger` у инвентаризации 480 `implicit` был +80, стал 0.

**О2. Ретро-отпуск без инвентаризации возвращает остаток (пример 3, вариант без seq 7).**
- Дано: как О1, но без инвентаризации 480.
- Тогда: остаток P до записи отпуска — 380, после — 460.

**О3. Отпуск заранее: планировщик пропускает сутки (FR-ABS-02, FR-ABS-03).**
- Дано: курсор `2026-10-08`, часы `2026-10-08 12:00` местного времени.
- Когда: `recordAbsence` на `10-10…10-13` (исход `new`, `cancelled = 0`). Затем часы идут до `2026-10-15 00:30` местного времени шагом 15 минут, на каждом шаге — `runPending()`.
- Тогда: автосписания P и Q есть за `10-09` и `10-14` и нет за `10-10` … `10-13`. Курсор — `2026-10-14`; `job_runs` содержит строки за `10-10` … `10-13` (сутки обработаны, а не пропущены курсором).

**О4. Отпуск, начавшийся до записи и ещё идущий.**
- Дано: автосписания за `10-09`, `10-10`, `10-11` записаны. Часы — `2026-10-12 10:00` местного времени.
- Когда: `recordAbsence` на `10-10…10-14`, затем `runPending()` по часам до `2026-10-16 00:30`.
- Тогда: `cancelled = 4` (P и Q за `10-10`, `10-11`); новых автосписаний за `10-12` … `10-14` нет; за `10-15` — есть.

**О5. Простой сервера во время отпуска: несписанные сутки не досписываются.**
- Дано: курсор `2026-10-09`, автосписание за `10-09` записано. Сервер «выключен» до `2026-10-16 10:00`.
- Когда: в `2026-10-16 10:00` сначала `recordAbsence` на `10-10…10-13`, затем `runPending()`.
- Тогда: `cancelled = 0`; после `runPending` автосписаний за `10-10` … `10-13` нет, за `10-14` и `10-15` — есть. Курсор — `2026-10-15`.
- И: обратный порядок (`runPending()` до `recordAbsence`) даёт тот же итоговый остаток P и Q и то же множество **действующих** автосписаний. Отличие только в том, что за `10-10` … `10-13` есть пары «автосписание + отмена отпуска».

**О6. Повтор того же периода (BR-26).**
- Дано: после О1.
- Когда: `recordAbsence` с тем же `id` и теми же датами; затем через минуту ещё раз.
- Тогда: оба раза `repeat`, `cancelled = 0`; число событий журнала и `maxStockSeq()` не изменились; периодов в `listAbsencePeriods()` — один.

**О7. Тот же `id`, другие даты — конфликт.**
- Дано: после О1.
- Когда: `recordAbsence` с тем же `id` и датами `10-10…10-14`.
- Тогда: `conflict` с периодом `10-10…10-13`; журнал и таблица периодов не изменились, автосписания за `10-14` действуют.

**О8. Пересекающийся период (ADR-005: дублей нет).**
- Дано: после О1.
- Когда: `recordAbsence` с новым `id` на `10-12…10-14`.
- Тогда: `new`, `cancelled = 2` (только P и Q за `10-14`); за `10-12`, `10-13` новых отмен нет, у каждого автосписания периода ровно одна отмена отпуска. Периодов — два.

**О9. Затрагиваются только автосписания.**
- Дано: в периоде `10-10…10-13` у P есть порция, у B — покупка и порча, у P — автосписание, отменённое пользователем до отпуска.
- Тогда: после `recordAbsence` отмен отпуска на порцию, покупку, порчу и на уже отменённое автосписание нет. Отмена пользователя — по-прежнему единственная ссылка на своё автосписание.

**О10. Отказ ввода — ничего не пишется.**
- Тогда: `id` не v4 (v5 из `derivedId`, верхний регистр, не строка) → `rejected: 'id'`; `start = '2026-10-13'`, `end = '2026-10-10'` → `rejected: 'end'`; `start = 'x'` → `rejected: 'start'`. В каждом случае журнал и `absence_period` не изменились.

**О11. Атомарность: отказ пакета отмен.**
- Дано: как О1; обёртка хранилища возвращает `{ status: 'rejected', reason: 'invalid_target' }` на `addStockEvent` **второй** отмены (приём `faulty` из T-010 А11).
- Когда: `recordAbsence`.
- Тогда: исключение проброшено; периода в `listAbsencePeriods()` нет; отмен отпуска в журнале нет, в том числе первой; остаток P — как до вызова. Счётчик поверх обёртки зафиксировал, что первая отмена была вставлена (`added`) до отказа: тест не проходит впустую.
- И: с исправной обёрткой повторный `recordAbsence` с тем же `id` даёт `new` и `cancelled = 8`.

**О12. Авто-откат SQLite внутри сценария: ошибка не перехватывается (хвост T-011 НВ-1).**
- Дано: как О1, файловая БД. Во временный триггер `BEFORE INSERT` с `SELECT RAISE(ROLLBACK, '…')` вариантами: (а) на `absence_period`; (б) на `stock_event`, срабатывающий на второй отмене отпуска (`kind = 'cancel'`, `source = 'absence'`, уже есть одна такая строка).
- Когда: `recordAbsence`.
- Тогда: в обоих вариантах исключение проброшено из `recordAbsence`. Через отдельное `raw`-соединение: строк `absence_period` нет, отмен отпуска нет. `storage.inTransaction()` — `false`.
- И: триггер снят, следующий `recordAbsence` с тем же `id` выполняется штатно (`new`, `cancelled = 8`), а `storage.transaction`, бросившая исключение после одной вставки, не оставляет этой вставки. Так проверяется, что после авто-отката хранилище не осталось в автокоммите.

**О13. Кэш остатков видит ретро-отпуск (ADR-003a).**
- Дано: `createBalanceCache` над той же БД прогрет (`warm()`) до `recordAbsence` из О2.
- Когда: после `recordAbsence` вызываются `balance(P)` и `all()`.
- Тогда: `balance(P) = 460`; `all()` совпадает со свёрткой `stockBalance` по всем позициям.

## Открытые вопросы

- **НВ-1. Ссылка отмены на период и хранение периода.** ADR-003 §6 и ADR-005 говорят: у системной отмены «источник „отпуск“ и ссылка на период». Поля для ссылки в `stock_event` нет (§4 ADR-003 его не перечисляет), а хранение периода ADR-005 отдаёт B-07.
  - (а) Ссылку не хранить. У отмены `source = 'absence'`, период выводится из данных: отменённое автосписание за сутки D отменено отпуском, в который D попадает. Период — отдельная таблица `absence_period`, только добавление (миграция 0003). Модель события остатка не меняется.
  - (б) Новая колонка `absence_id` в `stock_event`: меняет `StockEvent`, `CONTENT_KEYS`, `createStockEvent` и §4 ADR-003.
  - (в) Таблица связей «период → событие отмены».

  Рекомендация — (а). Ключ `absence_cancel:{target_id}` от периода не зависит, поэтому ссылка не нужна ни для идемпотентности, ни для свёртки. Для журнала действий (B-30) периода, выведенного по дате, достаточно. При пересекающихся периодах отмена принадлежит любому из них, и пользователю это безразлично. (б) и (в) добавляют модель ради подписи в ленте. Это отклонение от буквы ADR-003 §6, поэтому нужна одна строка-уточнение от architect в ADR-005 («Отпуск задним числом») и ADR-003 §6. Отдельный ADR не нужен: ADR-005 явно отдал хранение в B-07, а третья таблица только на добавление повторяет готовый образец `job_runs`. Контракт и критерии написаны по (а).

- **НВ-2. Можно ли удалить или изменить отпуск.** Спека говорит только «добавить» (FR-ABS-01). Ошибочный период (не те даты) после ретро-отмены вернуть нечем: перезапуск автосписаний за прошедшие сутки не произойдёт, потому что курсор их уже прошёл.
  - (а) В B-07 только добавление. Ошибку исправляет пользователь отменой отдельных отмен в журнале (FR-LOG-02, B-30). Нужно ли удаление вообще — новый вопрос владельцу к B-33.
  - (б) В B-07 — удаление только ещё не начавшегося периода. Отмен у него нет, удаление — событие «период отменён» в журнале периодов.
  - (в) В B-07 — полное удаление: отмена отмен отпуска и досписание пропущенных суток. Это новые ключи, отдельная механика и, вероятно, уточнение ADR-005.

  Рекомендация — (а). Требования удаления нет. Отпуск — 3 события в год (Q-19), ошибка редка, и её последствия смягчает калибровка (NFR-07). Если владелец захочет удаление, удобнее всего (б) вместе с экраном B-33. Предлагаемая формулировка для `docs/questions.md`: «Нужно ли удалять или менять уже записанный отпуск? Варианты: нет / только будущий / любой с восстановлением списаний. Рекомендация: только будущий, в B-33».

### Допущения (подтвердить вместе с вопросами)

- Даты периода включительны с обеих сторон (по ADR-003, пример 3). День отъезда и день возвращения — дни отпуска, автосписаний за них нет.
- `id` периода создаёт клиент (UUID v4, как у одиночного действия пользователя, ADR-003 §8): это защищает от двойного нажатия. Повтор с тем же `id` и другими датами — `conflict`.
- Пересекающиеся и вложенные периоды допустимы и не сливаются: день в отпуске, если он попадает хотя бы в один период.
- Принадлежность автосписания периоду определяется по `localDateOf(occurredAt)`, а не по ключу: `id` для домена непрозрачен. Это совпадает с датировкой автосписания началом суток (ADR-003 §5.3).
- Отмена пользователем отмены отпуска делает автосписание снова действующим. Новый пересекающийся период его не отменит: ключ занят. Это прямое следствие ADR-005 («ключ зависит только от цели»), а не решение задачи.
- Поиск отменяемых автосписаний читает события всех позиций внутри транзакции записи, мимо кэша (ADR-003a §5). На 10-м году это до ≈ 2 с на редкое действие. Критерия производительности нет. Узкий метод чтения хранилища backend-dev может добавить, не меняя контракта.
- `source` отмены отпуска — `'absence'`.
