## Контекст

Ритмичные позиции (кофе, молоко, хлеб) расходуются каждый день, и пользователь отмечает только отклонения от нормы. Чтобы остаток оставался правдоподобным без ежедневных отметок, сервер раз в сутки после их окончания пишет по каждой такой позиции событие «автосписание по норме». Если сервер был выключен, он догоняет пропущенные сутки. Повторный запуск ничего не дублирует, а переход на летнее время не теряет и не удваивает сутки.

## Бизнес-правила и требования

- FR-CON-01 — ритмичные позиции списываются автоматически ежедневно по норме. *(Здесь: списывается позиция с типом `rhythmic`, заданной нормой и активная в сутки D. Количество — суточная норма `Product.norm` в расходной единице (Q-25, BR-03). Позиции `burst`, `slow` и `unset` не списываются (FR-CON-02, FR-CON-03; про `unset` — НВ-1).)*
- FR-CON-07 — автосписание выполняется раз в сутки после их окончания по местному времени. *(Здесь: сутки D считаются завершёнными, когда наступило «время автосписания» суток D+1 по Вильнюсу. ADR-005.)*
- FR-CON-08 — после простоя догоняются пропущенные сутки; повторный запуск за те же сутки ничего не меняет. *(Здесь: курсор `job_runs` и `id` = UUIDv5(NS, `auto_writeoff:{product_id}:{D}`). Записанное событие — факт: при повторе содержимое не сравнивается, даже если норма поменялась. Отменённое автосписание не появляется снова. ADR-005, ADR-003 §8.)*
- BR-27 — даты интерпретируются в Europe/Vilnius; сутки — календарные; переход на летнее время не создаёт лишних и не теряет списаний. *(Здесь: сутки — `LocalDate`. 23- и 25-часовые сутки — ровно одни сутки и одна суточная норма.)*
- NFR-14 — сервер хранит время в UTC, домен работает в поясе дома. *(Здесь: `occurredAt` автосписания за D — 00:00 суток D по Вильнюсу, в UTC и в каноне `YYYY-MM-DDTHH:mm:ss.sssZ`. Пояс — из конфигурации, через `Intl` без библиотек.)*
- BR-09 — неактивная позиция не списывается автоматически. *(Здесь: активность — по журналу состояний на конец суток D, НВ-2.)*
- BR-10 / инвариант 5 — система не выставляет норму сама. *(Здесь: позиция без нормы не списывается, норма не подставляется.)*
- BR-15 / инвариант 6 — минус в остатке не ошибка. *(Здесь: автосписание пишется, даже если остаток уйдёт в минус. Проверки «хватает ли остатка» нет.)*
- BR-01, BR-02 / инварианты 1, 2 — остаток не хранится, события не удаляются и не правятся. *(Здесь: задача только дописывает события `auto_writeoff`. Курсор `job_runs` — служебная таблица, остатка в ней нет.)*
- Q-29 (закрыт) — при первом запуске история назад не досписывается. Курсор инициализируется сутками D₀−1, где D₀ — местная дата первого запуска. Первые списываемые сутки — D₀.
- ADR-003a §4.4 — в конце тика, после фиксации всех его транзакций, вызывается `warm()` кэша остатков, вне транзакций. Ошибка прогрева логируется и тик не прерывает.
- NFR-07 — сбой обработки суток не ломает работу: зафиксированные сутки остаются, следующий тик продолжает с первых необработанных.

## Критерии приёмки

Все критерии — в общем наборе `npm test`. Время фиксированное и передаётся явно (14.4): в домене — параметром, на сервере — поддельными часами `Clock`, в планировщике — поддельными таймерами тестового раннера. Сервер тестируется на `:memory:`-БД или временном файле. Параметры по умолчанию: `timeZone = 'Europe/Vilnius'`, `autoWriteoffTime = '00:00'`, `tickMinutes = 15`. Файлы и вспомогательные функции выбирает tester.

### Домен: сутки по Вильнюсу (BR-27, NFR-14)

**Д1. Границы суток.**
- Дано: пояс Europe/Vilnius.
- Когда: вызывается `dayBounds` для `2026-10-07`, `2026-03-29`, `2026-10-25` и `2026-12-31`.
- Тогда:
  - `2026-10-07` → `2026-10-06T21:00:00.000Z` … `2026-10-07T21:00:00.000Z` (24 ч);
  - `2026-03-29` → `2026-03-28T22:00:00.000Z` … `2026-03-29T21:00:00.000Z` (23 ч);
  - `2026-10-25` → `2026-10-24T21:00:00.000Z` … `2026-10-25T22:00:00.000Z` (25 ч);
  - `2026-12-31` → `2026-12-30T22:00:00.000Z` … `2026-12-31T22:00:00.000Z`.
- И: все значения проходят `isInstant`.

**Д2. Местная дата момента.**
- Когда: `localDateOf` вызывается для пар моментов по обе стороны каждой границы из Д1 (граница − 1 мс и сама граница), а также для `2026-10-25T00:30:00.000Z` и `2026-10-25T01:30:00.000Z` (местные 03:30 до и после перевода часов).
- Тогда: момент «граница − 1 мс» относится к предыдущим суткам, сама граница — к следующим. Оба момента осеннего повтора дают `2026-10-25`.

**Д3. `addDays`.**
- Тогда: `addDays('2026-03-28', 1) = '2026-03-29'`, `addDays('2026-10-25', 1) = '2026-10-26'`, `addDays('2026-12-31', 1) = '2027-01-01'`, `addDays('2026-03-01', -1) = '2026-02-28'`, `addDays('2028-03-01', -1) = '2028-02-29'`.

**Д4. Местное время суток и DST.**
- Тогда:
  - `localTimeOn('2026-10-07', '03:30')` = `2026-10-07T00:30:00.000Z`;
  - `localTimeOn('2026-03-29', '03:30')` = `2026-03-29T01:00:00.000Z` (время в разрыве — первый момент после него, местные 04:00);
  - `localTimeOn('2026-03-29', '03:00')` = `2026-03-29T01:00:00.000Z`;
  - `localTimeOn('2026-10-25', '03:30')` = `2026-10-25T00:30:00.000Z` (повтор — первое из двух);
  - `localTimeOn('2026-10-25', '03:00')` = `2026-10-25T00:00:00.000Z`;
  - `localTimeOn(D, '00:00')` равно `dayBounds(D).start` для дат из Д1.

**Д5. Сверка с помощником симулятора.**
- Дано: `tests/sim/local-time.ts` (T-006 К4) — независимая реализация правила ЕС.
- Когда: для каждой даты D с `2026-01-01` по `2027-12-31` и для каждого часа этого периода сравниваются функции домена и помощника.
- Тогда: `dayBounds(D).start = localToInstant(D, '00:00')`, `localTimeOn(D, '03:30') = localToInstant(D, '03:30')`, `localDateOf(t)` равен помощнику для каждого часового момента t.

**Д6. Завершённые необработанные сутки.**
- Дано: параметры по умолчанию.
- Тогда:
  - `cursor = '2026-10-05'`, `now = '2026-10-06T20:59:59.999Z'` → `[]`;
  - тот же курсор, `now = '2026-10-06T21:00:00.000Z'` → `['2026-10-06']` (граница включена);
  - `cursor = '2026-09-30'`, `now = '2026-10-07T21:00:00.000Z'` → семь дат с `2026-10-01` по `2026-10-07` по возрастанию;
  - `cursor = '2026-03-26'`, `now = '2026-04-01T09:00:00.000Z'` → `2026-03-27` … `2026-03-31`, пять дат, `2026-03-29` ровно один раз;
  - `cursor = '2026-10-22'`, `now = '2026-10-28T09:00:00.000Z'` → `2026-10-23` … `2026-10-27`, пять дат, `2026-10-25` ровно один раз;
  - курсор не раньше последних завершённых суток или позже `now` (часы ушли назад) → `[]`, без исключения.
- И: с `autoWriteoffTime = '03:30'` и `cursor = '2026-03-27'` сутки `2026-03-28` ещё не завершены в `2026-03-29T00:59:59.999Z` и завершены в `2026-03-29T01:00:00.000Z`. С `cursor = '2026-10-23'` сутки `2026-10-24` завершены в `2026-10-25T00:30:00.000Z`, а не в `01:30`.

### Домен: что и сколько списывается за сутки (FR-CON-01, BR-09, BR-10)

**Д7. Ритмичная активная позиция с нормой.**
- Дано: позиция `rhythmic`, `norm = 250` (мл), событий состояния нет.
- Когда: `autoWriteoffsForDay('2026-10-07', …)`.
- Тогда: ровно один элемент: `productId` позиции, `quantity = 250`, `key = 'auto_writeoff:{id}:2026-10-07'`, `occurredAt = '2026-10-06T21:00:00.000Z'`.

**Д8. Сутки перехода — одна норма.**
- Когда: та же позиция на `2026-03-29` и `2026-10-25`.
- Тогда: по одному элементу, `quantity = 250` (не 23/24 и не 25/24 нормы), `occurredAt` — `2026-03-28T22:00:00.000Z` и `2026-10-24T21:00:00.000Z` соответственно.

**Д9. Кого не списывать.**
- Дано: позиции `burst`, `slow` и `unset` с нормой; позиция `rhythmic` без нормы (`norm = null`).
- Тогда: ни одного элемента ни для одной из них.

**Д10. Активность на сутки D (BR-09, ADR-003 §7; НВ-2).**
- Дано: ритмичные позиции с нормой и событиями состояния:
  - A — `inactive` до начала D;
  - B — `inactive` в 15:00 местного времени суток D;
  - C — `inactive` до D и `active` (повод `purchase`) в 10:00 суток D;
  - E — `inactive` в 00:30 суток D+1;
  - F — `inactive` и `active` с одинаковым `occurredAt` внутри D, порядок по `seq`: сначала `inactive`, потом `active`.
- Тогда: элементы есть у C, E и F; у A и B — нет. Решает последнее событие состояния с `occurredAt < dayBounds(D).end` по `(occurredAt, seq)` (`isActive` по этому срезу).

**Д11. Чистота и детерминизм.**
- Тогда: два вызова с одинаковыми аргументами дают равные (`toEqual`) результаты. Порядок элементов совпадает с порядком `entries`. Функции домена не читают системные часы: результат не меняется при подмене `Date.now` в тесте. Входные массивы и объекты не изменяются.

### Хранилище: курсор `job_runs`

**Х1. Миграция.**
- Дано: БД на версии 1 (после T-004) с данными и новая пустая БД.
- Когда: `openStorage`.
- Тогда: обе БД на `user_version = 2`, таблица `job_runs` есть, существующие данные каталога и журнала не изменились. Проверки нумерации миграций T-004 проходят.

**Х2. `lastJobDay` / `markJobDay`.**
- Тогда: на пустой таблице `lastJobDay('auto_writeoff')` возвращает `undefined`. После `markJobDay` для `2026-10-05`, `2026-10-07` и `2026-10-06` (в таком порядке) возвращает `2026-10-07`. Повторный `markJobDay` той же пары не бросает и не создаёт второй строки. Строки другой задачи (`'other'`) на результат не влияют.
- И: `markJobDay` внутри `storage.transaction`, которая затем откатывается исключением, строки не оставляет.

### Сценарий автосписания (`app`, поддельные часы)

Дано для А1–А11, если не сказано иное: каталог — две ритмичные позиции с нормами 250 и 1 (P1, P2), одна `burst` с нормой, одна ритмичная без нормы, одна ритмичная неактивная. «Автосписания» — события `kind = 'auto_writeoff'` журнала.

**А1. Первый запуск (Q-29).**
- Дано: `job_runs` пуст, `now = 2026-10-07T10:00:00.000Z`.
- Когда: `runPending()`.
- Тогда: автосписаний нет, `processed = []`, `lastJobDay('auto_writeoff') = '2026-10-06'`. За сутки до первого запуска ничего не досписывается.

**А2. Первые сутки.**
- Дано: после А1 часы переведены на `2026-10-07T21:00:00.000Z`.
- Когда: `runPending()`.
- Тогда: `processed = ['2026-10-07']`, ровно два автосписания — у P1 (`quantity = 250`) и P2 (`quantity = 1`). У каждого `id = derivedId('auto_writeoff:{id}:2026-10-07')`, `occurredAt = '2026-10-06T21:00:00.000Z'`, `recordedAt = now`, `source = 'auto_writeoff'`. Курсор — `2026-10-07`.

**А3. Повторный запуск ничего не меняет (FR-CON-08).**
- Когда: после А2 `runPending()` вызывается ещё раз с тем же `now` и ещё раз через 15 минут.
- Тогда: `processed = []`, число событий журнала и `maxStockSeq()` не изменились.

**А4. Отставший курсор не дублирует.**
- Дано: после А2 у позиции P1 изменена норма на 300, строка `job_runs` за `2026-10-07` удалена напрямую в БД (имитация отставшего курсора).
- Когда: `runPending()`.
- Тогда: `processed = ['2026-10-07']`, новых событий нет, у P1 по-прежнему одно автосписание за сутки с `quantity = 250` (записанное — факт). Курсор снова `2026-10-07`.

**А5. Отменённое автосписание не возвращается.**
- Дано: после А2 автосписание P1 за `2026-10-07` отменено системной отменой через `recordSystemBatch` (как ретро-отпуск, ADR-005). Строка курсора за эти сутки удалена.
- Когда: `runPending()`.
- Тогда: нового автосписания P1 за `2026-10-07` нет, остаток P1 равен остатку до прогона (`stockBalance` исключает отменённое).

**А6. Догон после недельного простоя.**
- Дано: курсор `2026-09-30`, `now = 2026-10-07T22:00:00.000Z`.
- Когда: `runPending()`.
- Тогда: `processed` — семь дат `2026-10-01` … `2026-10-07` по возрастанию. У P1 и P2 по семь автосписаний, по одному за каждые сутки, с `occurredAt` = начало соответствующих суток. `seq` автосписаний растёт вместе с датой. Курсор — `2026-10-07`.
- И: остаток P1 без других событий равен `−1750`. Отказа и исключения нет (BR-15).

**А7. Весенний переход при тиках каждые 15 минут (BR-27).**
- Дано: курсор `2026-03-26`. Часы идут от `2026-03-27T00:00:00.000Z` до `2026-04-01T00:00:00.000Z` шагом 15 минут, на каждом шаге — `runPending()`.
- Тогда: у P1 и P2 ровно по одному автосписанию за каждые сутки `2026-03-27` … `2026-03-31`, пропусков и дублей нет. Автосписание за `2026-03-29` записано на первом шаге с `now ≥ 2026-03-29T21:00:00.000Z`, его `occurredAt = '2026-03-28T22:00:00.000Z'`.

**А8. Осенний переход при тиках каждые 15 минут (BR-27).**
- Дано: как в А7, курсор `2026-10-22`, часы от `2026-10-23T00:00:00.000Z` до `2026-10-28T00:00:00.000Z`.
- Тогда: по одному автосписанию за каждые сутки `2026-10-23` … `2026-10-27`. За `2026-10-25` — `occurredAt = '2026-10-24T21:00:00.000Z'`, записано на первом шаге с `now ≥ 2026-10-25T22:00:00.000Z`.

**А9. Время автосписания из конфигурации.**
- Дано: `autoWriteoffTime = '03:30'`, курсоры как в А7 и А8.
- Тогда: сутки `2026-03-28` обрабатываются на первом шаге с `now ≥ 2026-03-29T01:00:00.000Z`, сутки `2026-10-24` — на первом шаге с `now ≥ 2026-10-25T00:30:00.000Z`. Число автосписаний — как в А7 и А8.

**А10. Атомарность суток: исключение хранилища.**
- Дано: курсор `2026-10-04`, `now = 2026-10-07T21:00:00.000Z`. Обёртка хранилища бросает исключение на `addStockEvent` второй позиции за сутки `2026-10-06`.
- Когда: `runPending()`.
- Тогда: исключение проброшено. Сутки `2026-10-05` зафиксированы: оба автосписания и курсор. За `2026-10-06` нет ни одного автосписания (в том числе первой позиции), курсор — `2026-10-05`. Сутки `2026-10-07` не обработаны.
- И: обёртка исправна, повторный `runPending()` даёт `processed = ['2026-10-06', '2026-10-07']` без дублей за `2026-10-05`.

**А11. Атомарность суток: отказ внутри пакета (хвост ревью T-005).**
- Дано: как в А10, но обёртка возвращает `{ status: 'rejected', reason: 'unknown_product' }` на `addStockEvent` второй позиции за `2026-10-06`. `recordSystemBatch` вложен в транзакцию суток и перехватывает отказ сам.
- Тогда: результат как в А10. Частично обработанных суток нет: отказ пакета откатывает и уже вставленное автосписание первой позиции, и курсор за эти сутки.

**А12. Не списываются `burst`, позиция без нормы и неактивная.**
- Тогда: после А2 и А6 у `burst`-позиции, у ритмичной без нормы и у неактивной ритмичной нет ни одного автосписания.

### Планировщик (`jobs`) и прогрев (ADR-005, ADR-003a §4.4, §6.1)

Дано для П1–П5: настоящие `createAutoWriteoff` и `createBalanceCache` над одной БД. Хранилище кэша обёрнуто счётчиком вызовов `listStockEvents`, `warm` обёрнут шпионом. `log` — шпион.

**П1. Тик при старте и каждые N минут.**
- Дано: поддельные таймеры, `tickMinutes = 15`, курсор `2026-10-06`, `now = 2026-10-07T21:00:00.000Z`.
- Когда: `startScheduler(...)`.
- Тогда: к возврату из `startScheduler` автосписания за `2026-10-07` уже записаны (тик при старте). Через 14 мин 59 с второго тика нет, через 15 мин есть. После `stop()` и ещё 60 минут таймеров тиков больше нет.

**П2. Прогрев в конце тика.**
- Когда: `tick()` записывает автосписания за одни сутки, затем вызывается `cache.all()`.
- Тогда: `all()` не вызывает `listStockEvents` ни разу и совпадает со свёрткой по всем позициям.

**П3. Один прогрев на догон.**
- Дано: курсор на 5 суток позади.
- Когда: `tick()`.
- Тогда: `warm` вызван ровно один раз, после фиксации последней транзакции (в момент вызова `storage.inTransaction() = false`, курсор уже на последних сутках).

**П4. Ошибка прогрева не прерывает тик (NFR-07).**
- Дано: `warm` бросает исключение.
- Когда: `tick()`.
- Тогда: `tick()` не бросает. Автосписания и курсор записаны. `log` вызван один раз с этой ошибкой. Следующий `tick()` с исправным `warm` выполняется штатно, и после него `all()` совпадает со свёрткой.

**П5. Ошибка суток не останавливает планировщик.**
- Дано: хранилище как в А10.
- Когда: срабатывает тик по таймеру.
- Тогда: исключение не выходит из таймера. `log` вызван с ошибкой, `warm` вызван (зафиксированные сутки прогреты). Следующий тик по таймеру с исправным хранилищем дообрабатывает оставшиеся сутки.

## Открытые вопросы

- **НВ-1. Списывать ли позицию с нормой, у которой тип `unset`.** FR-CON-01 называет только ритмичные. Тип `unset` получает любая новая позиция (Q-28), а авто-тип по истории появится только в B-12. До B-12 позиция с нормой, но без ручного выбора «ритмичная», списываться не будет.
  - (а) Только `rhythmic`, буквально по FR-CON-01.
  - (б) `rhythmic` и `unset` с нормой: раз норма задана, позиция похожа на ритмичную.

  Рекомендация — (а). Спека явно ограничивает автосписание ритмичными, а (б) списывало бы рывковые позиции, у которых пользователь задал норму для списка покупок. Критерий Д9 написан по (а).
- **НВ-2. На какой момент суток D проверяется активность.** ADR-005 говорит «активность на D», но момент не уточняет.
  - (а) На конец суток D: последнее событие состояния с `occurredAt < end(D)`.
  - (б) На начало суток D.
  - (в) На момент тика.

  Рекомендация — (а). Позиция, возвращённая покупкой днём D, в этот день уже расходуется. Результат не зависит от того, когда прошёл тик, поэтому догон и обычная ночь дают одно и то же. Вариант (в) при догоне задним числом применял бы сегодняшнее отключение к прошлым дням. Д10 написан по (а).
- **НВ-3. Создаёт ли T-010 `src/server/main.ts`.** Хвост НВ-8 T-009: `main.ts` создаёт первая задача, которой он нужен.
  - (а) T-010 создаёт `main.ts` без HTTP: открыть БД → `warm()` → `startScheduler`. B-17 потом вставит порт между шагами.
  - (б) T-010 даёт только `startScheduler` и проверяет его на поддельных таймерах. `main.ts` создаёт первая задача с HTTP (B-16/B-17) или B-18.

  Рекомендация — (б). Порядок старта по ADR-003a §4.4 — «миграции → порт → `warm()` → планировщик». Без порта `main.ts` будет неполным, и его придётся переписывать. До развёртывания (B-22) процесс всё равно не запускается. Тик при старте проверяет П1 через `startScheduler`. Критерии написаны по (б).

### Допущения (подтвердить вместе с вопросами)

- Норма и тип списания берутся из карточки на момент тика: их истории нет. В обычной работе тик отстаёт от конца суток не больше чем на `tickMinutes`, поэтому норма на момент тика практически равна норме на конец D.
- Позиция, добавленная в каталог в сутки D, списывается за D: время создания позиции не хранится. Это согласуется с датировкой автосписания началом суток (ADR-003 §5.3).
- Если курсор потерян полностью (в `job_runs` нет строк задачи), это считается первым запуском: курсор — вчера, пропущенные сутки не досписываются. Если курсор отстал (А4), сутки обрабатываются повторно без дублей.
- Сбой суток D останавливает проход на D: более поздние сутки не обрабатываются, чтобы курсор (максимум `day`) не перепрыгнул через D (А10).
- `source = 'auto_writeoff'`, имя задачи в курсоре — `'auto_writeoff'`.
- Флаг «тик идёт» (ADR-005) не требуется критерием: тик синхронный (ADR-002) и наложиться сам на себя не может. Если backend-dev его добавит, это не нарушение.
