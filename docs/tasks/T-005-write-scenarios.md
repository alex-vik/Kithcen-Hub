## Контекст

Повтор отметки при плохой связи не должен давать дубль, а системные задачи должны безопасно перезапускаться: второй запуск автосписания за тот же день ничего не дописывает. Задача добавляет поверх хранилища T-004 минимальные сценарии записи (`src/server/app/`) и реальные часы (`src/server/clock.ts`). HTTP нет: сценарии проверяются тестами напрямую, на `:memory:`-БД или временном файле и с поддельными часами.

Тесты сервера идут на Node 22.18+. `node:sqlite` печатает `ExperimentalWarning` — это шум, а не ошибка (ADR-002). Глобально предупреждения не глушить.

## Бизнес-правила

- BR-26 — повторная отправка события с тем же идентификатором не создаёт дубль. *(ADR-003 §8. Запрос клиента: записанное с тем же `id` совпадает по содержимому → «повтор», возвращается записанное; отличается → «конфликт» без перезаписи. Системная задача: `id` уже есть → «выполнено». Производный `id` = UUIDv5(NS, ключ), считает `app` через `node:crypto`.)*
- BR-02 / инвариант 2 — ошибочная отметка отменяется событием-отменой со ссылкой на неё. *(Здесь: отмена через сценарий; ссылку проверяет хранилище T-004. Клиентская отмена несёт время нажатия, как любая отметка — ADR-003 §5.3, решение НВ-3.)*
- NFR-14 — сервер хранит время в UTC. *(Здесь: время клиента приводится к канону `YYYY-MM-DDTHH:mm:ss.sssZ` до создания события, решение НВ-2; `clock.now()` возвращает канон.)*
- NFR-08 — все изменения остатка прослеживаются через журнал событий. *(Здесь: `recordedAt` = `clock.now()` ставит сервер, клиент его не передаёт.)*
- BR-15 / инвариант 6 — минус в остатке не ошибка. Сценарии не отклоняют запись из-за того, что остаток уйдёт в минус.
- ADR-003 §6 — отмена ссылается на существующее событие той же позиции и записана позже цели.

## Сценарии `app` (для понимания критериев)

Имена функций и типов выбирают tester и backend-dev; критерии задают поведение. Это минимум, нужный для проверки идемпотентности и атомарности.

| Сценарий | Вход | Что делает |
| --- | --- | --- |
| Запись события от клиента | `id` (клиентский UUID v4 в нижнем регистре), `productId`, `kind`, поля вида, `occurredAt` (строка времени от клиента; у отмены — время нажатия «отменить»), `source`. `seq` и `recordedAt` во входе нет | В одной транзакции хранилища: проверка `id` → канон времени → позиция → `createStockEvent` с `recordedAt = clock.now()` → поиск записанного по `id` → `resolveEventWrite` → для нового события: вставка (хранилище проверяет ссылку отмены). Исход: «новое», «повтор», «конфликт» или отказ с причиной |
| Пакетная запись системных событий | Список элементов: строка-ключ, `productId`, `kind`, поля вида, `occurredAt` (`Instant`), `source` | Одна транзакция на весь пакет: `id` = UUIDv5(NS, ключ) → `createStockEvent` с `recordedAt = clock.now()` → `resolveSystemWrite` → вставка новых. Любой отказ откатывает весь пакет. Это примитив, который вызовут B-06 (тик автосписания) и B-07 (отмены из-за отпуска) |

- Если `id` уже записан, исход — «повтор» или «конфликт» (у пакета — «выполнено») независимо от проверки ссылки отмены. Порядок остальных проверок при нескольких ошибках одного запроса не задан.
- Предсказуемые отказы (невалидный ввод, неизвестная позиция, плохая ссылка отмены, конфликт) — результат, а не исключение. Коды ответа — B-16.

## Критерии приёмки

Время в критериях — UTC. «Поддельные часы» возвращают заданный тестом `Instant`. Номера критериев сохранены из общего черновика T-004 (там К1–К18 и К30–К32), поэтому здесь они начинаются с К19.

**К19. Время клиента приводится к канону (хвост ревью «B-02/B-03a»; решение НВ-2).**
- Дано / Когда / Тогда — вход → результат:
  - `2026-10-12T12:00:00+03:00` → `2026-10-12T09:00:00.000Z`
  - `2026-10-12T00:30:00.000+03:00` → `2026-10-11T21:30:00.000Z`
  - `2026-10-12T09:00:00Z` → `2026-10-12T09:00:00.000Z`
  - `2026-10-12T09:00:00.5Z` → `2026-10-12T09:00:00.500Z`
  - `2026-10-12T09:00:00.000Z` → без изменений
- И: отказ с атрибутом `occurredAt` без исключения: `2026-10-12T09:00:00` (без смещения), `2026-10-12`, `2026-02-30T10:00:00Z`, `2026-10-12T09:00:00.1234Z`, `2026-10-12 09:00:00Z`, `завтра`, пустая строка, число

**К20. Новое событие от клиента.**
- Дано: позиция «Гречка», поддельные часы 12.10 09:00:05.000
- Когда: сценарий получает порцию −100 с клиентским UUID v4, `occurredAt` `2026-10-12T12:00:00+03:00`
- Тогда: исход «новое»; в журнале одна строка: `occurredAt` `2026-10-12T09:00:00.000Z`, `recordedAt` = время часов, `seq` от хранилища; возвращённое событие строго равно прочитанному из журнала

**К21. Повтор через хранилище возвращает записанное (BR-26; хвост ревью T-003, п. 3).**
- Дано: журнал после К20; часы переведены на 12.10 09:00:40.000
- Когда: тот же запрос приходит повторно — (а) с тем же текстом времени; (б) с тем же моментом в другой записи (`2026-10-12T09:00:00Z`)
- Тогда: в обоих случаях исход «повтор»; возвращается событие с исходными `seq` и `recordedAt` 09:00:05.000; строка в журнале одна
- И: то же для покупки 2 уп × 900 и для отмены: двойное нажатие «отменить» — два запроса с тем же `id`, `targetId` и `occurredAt` (время нажатия от клиента, ADR-003 §5.3), часы между запросами переведены — второй даёт «повтор», а не «конфликт»

**К22. Повтор с другим содержимым — конфликт без перезаписи (хвост ревью T-003, п. 1).**
- Дано: записана инвентаризация 500 с `id` X
- Когда: приходит инвентаризация 480 с тем же `id` X; отдельно — порция с `id` уже записанной порции и другим количеством
- Тогда: исход «конфликт» с указанием `id`; в журнале прежние строки без изменений, новых нет

**К23. Отказ без записи.**
- Дано: позиция «Гречка»
- Когда: по отдельности: порция с `quantity` 0; событие для неизвестной позиции; `occurredAt` без смещения; `id` вида `e-7`, `id` UUID v4 в верхнем регистре, `id` — UUID версии 5
- Тогда: отказ с атрибутом соответственно `quantity`, `productId`, `occurredAt`, `id`; в журнале ни одной строки; исключение не выбрасывается

**К24. Отмена через сценарий.**
- Дано: у гречки записаны покупка +1800 и порция −100 (E2); у риса — порция E3
- Когда: (а) отмена E2; (б) отмена `id`, которого нет; (в) отмена E3 с `productId` гречки
- Тогда: (а) исход «новое», `stockBalance` гречки по журналу = 1800; (б) и (в) — отказ из-за ссылки, ничего не записано
- И (исход по `id` не зависит от проверки ссылки): (г) отмена с `id` уже записанной порции E2 и `targetId`, которого нет, — исход «конфликт», а не отказ из-за ссылки; ничего не записано

**К25. Два повтора подряд дают одну строку.**
- Дано: пустой журнал позиции
- Когда: один и тот же запрос выполняется дважды подряд в одном тике цикла событий (без `await` между вызовами), а затем ещё раз через новое открытие той же файловой БД
- Тогда: ровно один исход «новое», остальные — «повтор»; строка одна
- *(Синхронный драйвер исполняет каждую транзакцию целиком, поэтому чередования запросов нет; от дубля при любом раскладе защищает первичный ключ — T-004 К11.)*

**К26. Производный `id` = UUIDv5(NS, ключ).**
- Дано: функция UUIDv5 и константа `NS`
- Когда: вычисляется UUIDv5 от пространства DNS (`6ba7b810-9dad-11d1-80b4-00c04fd430c8`) и строки `python.org`
- Тогда: `886313e1-3b8a-5372-9b90-0c9aee199e5d` (контрольный пример из документации Python `uuid`)
- И: производный `id` — строка UUID в нижнем регистре, версия 5, вариант RFC 4122; одинаковый ключ даёт одинаковый `id`, разные ключи — разные
- И (golden-тест): `NS` = `3f6c2a9e-8b1d-4e57-a0c4-7d92e15b6f08` (ADR-003 §8); производный `id` для ключа `auto_writeoff:p-1:2026-10-12` равен литералу, который tester вычисляет один раз и вписывает в тест. Смена `NS` ломает тест

**К27. Пакет системных событий: повторный запуск — «выполнено» (ADR-003 §8, ADR-005).**
- Дано: позиция «Кофе»; пакет из двух автосписаний −20 с ключами `auto_writeoff:{кофе}:2026-10-12` и `…:2026-10-13`
- Когда: пакет записывается; затем записывается снова, но с количеством −25 (норма изменилась); затем первое автосписание отменяется, и пакет записывается в третий раз
- Тогда: после первого раза — две строки с `id` = UUIDv5(NS, ключ), `recordedAt` = время часов, исходы «новое»; после второго и третьего — исходы «выполнено», новых строк нет, количества остаются −20, отменённое автосписание не появляется заново

**К28. Пакет атомарен.**
- Дано: позиция «Кофе»
- Когда: (а) пакет из трёх элементов, где третий ссылается на неизвестную позицию; (б) то же, но третий — отмена несуществующего события; (в) пакет из автосписания и отмены этого автосписания с ключом `absence_cancel:{его id}`
- Тогда: (а) и (б) — отказ с указанием номера элемента, в журнале ни одной строки из пакета; (в) — обе строки записаны, цель отмены найдена внутри той же транзакции, `stockBalance` = 0

**К29. Реальные часы дают канон.**
- Дано: реальная реализация `Clock`
- Когда: вызывается `now()`
- Тогда: `isInstant` = `true`, значение не раньше и не позже моментов, взятых тестом до и после вызова

- Чтение конфигурации из окружения и сборка `src/server/main.ts` — **B-17**.
- Сценарии записи событий состояния (автоархив, возврат покупкой, отмена отключения) и правило «повтор или конфликт» для них — **B-12**.
- Строки-ключи `auto_writeoff:…`, `absence_cancel:…`, `auto_archive:…`, `operation_line:…` в домене и их источники — **B-06, B-07, B-12, B-19/B-20**. В тестах К26–К28 ключи — просто строки.
- Генерация системных событий (что и когда списывать, что отменять из-за отпуска) — **B-06, B-07**. Здесь — только примитив пакетной записи.
- Курсор `job_runs`, планировщик, тик — **B-06, B-18** (ADR-005).
- `operationId`, `recognitionConfidence` и отмена операции целиком — **B-17/B-19/B-20**.

- Общий хелпер `fail`/`isPositive` — отдельной задачей (хвост в бэклоге).
- Всё из «Чего нет в первой версии»: сроки годности, места хранения, открытые упаковки, офлайн, многопользовательский режим, Barbora.

## Открытые вопросы

- **НВ-4. Кто задаёт `occurredAt` системной отмены в пакете.** Решение НВ-3: «системные отмены берут `clock.now()`». Неясно, ставит ли это время сам пакетный сценарий или его передаёт вызывающий (B-07) во входе пакета, как у любого элемента.
  - (а) Вызывающий: вход пакета у всех элементов одинаковый, B-07 передаёт `clock.now()`. Сценарий виды не различает. У системных событий содержимое при повторе не сравнивается, поэтому время на исход не влияет.
  - (б) Сценарий: для элемента-отмены `occurredAt` во входе нет, сценарий ставит `clock.now()`. Особый случай в примитиве.

  Рекомендация — (а): меньше логики в примитиве, правило «отмена — время записи» живёт там, где отмену создают (B-07). К28 (в) написан по (а): `occurredAt` отмены задаёт тест. Решение команды, на поведение для владельца не влияет.

Закрытые решения (delivery-lead, 2026-10-06; решения команды, технические, на поведение для владельца не влияют):

- **НВ-2. Какие записи времени клиента принимаются.** → **(а)**: сервер принимает ISO-8601 с обязательным смещением `Z` или `±HH:MM`, секунды обязательны, дробная часть 0–3 знака; всё остальное — отказ с атрибутом `occurredAt`; принятое приводится к канону `YYYY-MM-DDTHH:mm:ss.sssZ`. Отвергнуты: (б) только строгий канон; (в) всё, что разбирает `Date.parse`, включая время без смещения. Критерии: К19, К23.
- **НВ-3. Время события пользовательской отмены.** → **(а)**: клиентская отмена несёт время нажатия, как любая отметка; системные отмены берут `clock.now()`. Пометку в ADR-003 §5.3 вносит architect параллельно — задача ссылается на ADR-003 §5.3. Отвергнуто: (б) `clock.now()` в сценарии и особый случай сравнения в домене. Критерии: К21; уточнение для пакета — НВ-4.

Подтверждённые предположения (delivery-lead, 2026-10-06):

- Клиентский `id` в сценарии клиента — UUID версии 4 в нижнем регистре, иначе отказ с атрибутом `id` (К23). Без этой проверки клиент может прислать `id` версии 5 и занять производный `id` системного события (ADR-003 §8).
- Пакетная запись системных событий входит в эту задачу как минимум для проверки атомарности и UUIDv5 (К27, К28). Генерацию самих событий добавят B-06 и B-07.
- Если `id` уже записан, исход — «повтор» или «конфликт» независимо от проверки ссылки отмены (К24). Порядок остальных проверок при нескольких ошибках не задан.
