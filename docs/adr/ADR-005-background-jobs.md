# ADR-005 — Фоновые задачи: суточное автосписание, догон, сутки по Вильнюсу

| Поле | Значение |
| --- | --- |
| Статус | принято 2026-10-06 |
| Дата | 2026-10-06 |
| Автор | architect |
| Бэклог | B-00d (решение), B-06, B-07 (реализация) |
| Связано | FR-CON-01, FR-CON-07, FR-CON-08, FR-ABS-03, FR-ABS-04, BR-09, BR-26, BR-27, NFR-07, NFR-14, параметр «Время автосписания» (раздел 15); ADR-002, ADR-003, ADR-004 |

## Контекст

Ритмичные позиции списываются по норме раз в сутки после их окончания по местному времени (FR-CON-01, FR-CON-07). Если сервер был недоступен, при восстановлении пропущенные сутки догоняются, повторный запуск за те же сутки ничего не меняет (FR-CON-08). Сутки — календарные по Europe/Vilnius; переход на летнее время не создаёт лишних и не теряет списаний (BR-27). Во время отпуска автосписаний нет, отпуск задним числом отменяет уже выполненные (FR-ABS-03, FR-ABS-04). Неактивные позиции не списываются (BR-09).

Позже на этот же механизм лягут пересмотр по четвергам, напоминание в субботу, автоархив, удаление фото (B-18) — этот ADR их не решает, но не должен им мешать.

## Варианты

### Где запускать

| Вариант | За | Против |
| --- | --- | --- |
| **Таймер внутри серверного процесса** | Один процесс, одна база, общий код; ничего не нужно настраивать в Docker | Пока сервер лежит, ничего не происходит — но это закрывает догон |
| Системный cron / отдельный контейнер | Привычно | Второй процесс пишет в ту же SQLite; настройка на хосте; конфликт с ADR-007 до его принятия |
| Очередь задач (BullMQ и т. п.) | Повторы, расписания | Redis и инфраструктура ради одной задачи в сутки |

### Как считать сутки

| Вариант | Оценка |
| --- | --- |
| «Каждые 24 часа от запуска» | Ломается на DST (сутки 23 и 25 часов) и при перезапусках |
| `Date` + ручные смещения пояса | Ошибкоопасно в дни перехода |
| **`Temporal.PlainDate` + `Temporal.ZonedDateTime` с поясом из параметров** | Встроен в Node 26 (ADR-001), календарная арифметика отделена от часовой |

### Как обеспечить «ровно один раз»

| Вариант | Оценка |
| --- | --- |
| Только отметка «последний обработанный день» | Падение между записью событий и отметкой даёт дубль |
| **Детерминированный идентификатор события + отметка в той же транзакции** | Повтор — `INSERT … ON CONFLICT DO NOTHING` (тот же механизм, что BR-26); отметка лишь экономит работу |

## Рекомендация

### Планировщик

- В серверном процессе (`src/server/jobs/`) — тик раз в 5 минут и один тик сразу при старте. Тик — функция `tick(now)`: тесты вызывают её с фиксированным `now`, без поддельных таймеров.
- Состояние — таблица `job_state(name TEXT PRIMARY KEY, last_day TEXT)`; для автосписания `name = 'auto_write_off'`, `last_day` — последний обработанный локальный день `YYYY-MM-DD`.
- При первом запуске `last_day` = вчерашний локальный день: история до установки не дописывается (FR-CAT-07 — каталог наполняется по ходу).

### Домен (чистые функции, ADR-004)

1. `completedDays(lastDay, now, params) → PlainDate[]` — все локальные дни `D`, такие что `lastDay < D` и начало суток `D + 1` в `params.timeZone` наступило не позже `now` (с учётом параметра «время автосписания»: по умолчанию — сразу после 00:00).
2. `planAutoWriteOffs(day, products, absences, params, now) → StockEvent[]` — для каждой активной ритмичной позиции с подтверждённой нормой, если `day` не входит в отпуск: событие автосписания
   - `id = auto:<productId>:<YYYY-MM-DD>` — детерминированный;
   - `occurred_at` = начало суток `day` по Вильнюсу (ADR-003, раздел 3);
   - количество — суточная норма (точная формула нормы — B-06/B-08);
   - `recorded_at = now`.
3. `reconcileAbsence(days, absences, journal, now) → StockEvent[]` — для отпуска задним числом и его отмены (раздел «Отпуск» ниже).

### Сервер

Тик для автосписания:

```
for day in completedDays(job_state.last_day, now, params):
  BEGIN IMMEDIATE
    events = planAutoWriteOffs(day, products, absences, params, now)
    INSERT … ON CONFLICT(id) DO NOTHING for each event
    UPDATE job_state SET last_day = day
  COMMIT
```

Одна транзакция на день: падение посреди догона оставляет журнал согласованным, следующий тик продолжает с нужного дня.

### Сутки и DST

- Сутки — календарные даты; перебор — `PlainDate.add({ days: 1 })`, без часов. Каждая дата встречается ровно один раз, сколько бы часов в ней ни было (23 в последнее воскресенье марта, 25 в последнее воскресенье октября).
- Начало суток — `day.toZonedDateTime({ timeZone })`. В Вильнюсе переход происходит в 03:00 → 04:00 (весной) и 04:00 → 03:00 (осенью), полночь всегда существует и однозначна; Temporal всё равно разрешает неоднозначности по правилу `compatible`, так что код не зависит от этого факта.
- Пояс — только `params.timeZone`; переменная `TZ` контейнера не влияет. Правила поясов приходят с ICU внутри Node — обновление Node обновляет и их.

### Догон

- Сколько бы суток ни пропустил сервер, тик перебирает их все. Год простоя — порядка 30 позиций × 365 дней ≈ 11 тыс. событий за один тик; это секунды.
- Право на автосписание (активна, ритмичная, есть норма) оценивается по **текущему** состоянию позиции на момент догона. Состояние позиции на прошлую дату не восстанавливается (ADR-003, раздел 4). Расхождение возможно только если за время простоя менялась карточка; его подбирает калибровка (NFR-07).
- Повторный запуск за те же сутки ничего не меняет: день уже ниже `last_day`, а даже при сбросе отметки события не задублируются из-за детерминированного `id` (FR-CON-08).
- Автосписание, отменённое пользователем вручную, не восстанавливается: событие с этим `id` уже существует.

### Отпуск

- Отпуск заранее: дни отпуска пропускаются в `planAutoWriteOffs`, событий нет (FR-ABS-03).
- Отпуск задним числом (FR-ABS-04): при создании отпуска сервер в одной транзакции пишет отмены всех действующих автосписаний за прошедшие дни отпуска. Идентификатор отмены детерминирован — `absence:<absenceId>:<eventId>`, `group_id` = отпуск. Повтор ничего не дублирует.
- Отмена или сокращение отпуска: отмены, записанные этим отпуском, отменяются (отмена отмены восстанавливает событие, ADR-003). Для прошедших дней, где автосписаний не было, потому что отпуск был задан заранее, `planAutoWriteOffs` запускается для этих дней — `id` детерминированы, существующие не задублируются.
- Влияние на остаток — только через события журнала (NFR-08); свёртка об отпусках не знает.

### Другие периодические задачи

Пересмотр, напоминания, автоархив, удаление фото (B-18) используют тот же тик и ту же таблицу `job_state` со своим `name`. Их правила — в задачах шага 5.

## Последствия

- Внешнего планировщика нет; развёртывание (ADR-007) — один контейнер.
- Автосписание за день D появляется после полуночи D+1; в течение дня D остаток показывает данные на утро D. Учитывать ли «сегодняшний» расход в статусах — решение B-10.
- Отпуск задним числом и его отмена работают только через события, видны в журнале действий и отменяемы.
- Тесты B-06 обязаны покрыть: обычные сутки; последнее воскресенье марта (23 ч) и октября (25 ч) — ровно одно автосписание; простой в несколько суток; повторный тик; падение между днями; отпуск заранее, задним числом и его отмену.
- Принятое упрощение: при догоне используется текущее состояние карточки.
