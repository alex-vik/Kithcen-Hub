## Контекст

Владелец закрыл Q-01: SQLite. За десять лет журнал вырастет до нескольких сотен тысяч строк (оценка из Q-01: десятки событий в день). Сервер — один процесс Node (ADR-001). Нужно решить: чем открывать базу, в каком режиме, как менять схему и как тесты получают изолированную базу.

## Варианты

### Драйвер

| Вариант | За | Против |
| --- | --- | --- |
| **`node:sqlite` (встроен в Node)** | Ноль зависимостей, ничего не компилируется при установке, синхронный API (`DatabaseSync`) — транзакции без гонок в однопоточном процессе. Статус release candidate с Node 24.15 / 25.7 | Не «stable»: по правилам Node RC допускает ограниченные несовместимые изменения. API беднее better-sqlite3 (нет, например, пользовательских агрегатов — они не нужны) |
| better-sqlite3 | Зрелый, быстрый, синхронный | Нативный модуль: при отсутствии готового бинарника под платформу и версию Node собирается через node-gyp — в Docker нужны python, make, g++. Каждое обновление Node — проверка совместимости |
| libsql / @libsql/client | Репликация, удалённый режим | Асинхронный API, нативный бинарник, возможности не нужны на этом масштабе |
| ORM / построитель запросов (Drizzle, Kysely) поверх драйвера | Типизированные запросы, генерация миграций | Лишний слой для ~10 таблиц; миграции и так простые |

### Миграции

| Вариант | За | Против |
| --- | --- | --- |
| **Нумерованные SQL-файлы + `PRAGMA user_version`** | Без инструментов, читаемо, версия хранится в самом файле базы | Нет «вниз» — и не нужно |
| Инструмент миграций (umzug, knex, drizzle-kit) | Привычно | Зависимость и конфигурация ради десятка файлов |

### Изоляция тестов

| Вариант | За | Против |
| --- | --- | --- |
| **Новая `:memory:` база на тест + применение миграций** | Полная изоляция, миллисекунды, параллельный запуск файлов Vitest безопасен | Не проверяет WAL и работу с файлом |
| Общий файл с очисткой таблиц | Ближе к проду | Хрупко, мешает параллельности, нарушает append-only (очистка = удаление событий) |
| Временный файл на тест | Проверяет файловое поведение | Медленнее; нужен только для отдельных тестов |

## Рекомендация

**Драйвер:** `node:sqlite`, `DatabaseSync`, одно соединение на процесс. Сырые SQL-запросы в тонких функциях хранения (`src/server/db/`), ручное отображение строк в доменные типы. Без ORM.

**Режим и PRAGMA при открытии:**

| PRAGMA | Значение | Зачем |
| --- | --- | --- |
| `journal_mode` | `WAL` | Чтение не блокирует запись; бэкап читается параллельно работе |
| `synchronous` | `FULL` | Десятки записей в день — цена fsync не важна; транзакция переживает потерю питания (важно для домашнего сервера, Q-02). `NORMAL` в WAL может потерять последнюю транзакцию |
| `foreign_keys` | `ON` | В SQLite по умолчанию выключены |
| `busy_timeout` | `5000` | На случай внешнего чтения (бэкап, ручной `sqlite3`) |

Запись — в `BEGIN IMMEDIATE … COMMIT`. Одно пользовательское действие (например, приход по чеку из 15 строк) — одна транзакция.

**Время и числа в схеме:**

- моменты времени — `INTEGER`, миллисекунды UTC (NFR-14); сравнение и сортировка — числовые;
- календарные дни по Вильнюсу (даты отпуска, BR-27) — `TEXT` `YYYY-MM-DD`;
- количества — `REAL` в единице счёта позиции (BR-03); погрешность плавающей точки ниже требуемой точности (A-03).

**Append-only на уровне базы.** Для журнала событий остатка и журнала изменений позиций (ADR-003) — триггеры, запрещающие `UPDATE` и `DELETE`:

```sql
CREATE TRIGGER stock_events_no_update BEFORE UPDATE ON stock_events
BEGIN SELECT RAISE(ABORT, 'stock_events is append-only'); END;
CREATE TRIGGER stock_events_no_delete BEFORE DELETE ON stock_events
BEGIN SELECT RAISE(ABORT, 'stock_events is append-only'); END;
```

Инвариант 2 (BR-02) тогда защищён не только ревью. Идемпотентность (BR-26) — `UNIQUE` по клиентскому идентификатору события и `INSERT … ON CONFLICT(id) DO NOTHING`.

**Миграции:**

- файлы `src/server/db/migrations/NNNN-<slug>.sql`, применяются по возрастанию номера при старте сервера;
- текущая версия — `PRAGMA user_version`; каждая миграция и установка версии — в одной транзакции;
- только вперёд; применённую миграцию не правят, исправление — новой миграцией;
- миграции не удаляют и не переписывают строки журнала событий. Если это когда-нибудь понадобится — это изменение инварианта, отдельный ADR и решение владельца.

**Тесты:**

- доменные тесты базу не трогают вообще (ADR-004);
- тесты хранения и приёмочные через API — новая база `new DatabaseSync(':memory:')` на каждый тест, с применёнными миграциями. Открытие и миграции — одна функция `openDb(path)` из `src/server/db/`, ей же пользуется продакшн, поэтому тесты гоняют ту же схему;
- тесты, которым нужен файл (WAL, бэкап, восстановление для NFR-13), создают временный каталог через `fs.mkdtempSync(os.tmpdir())` и удаляют его после себя.

**Расположение файла базы:** путь из переменной окружения (`DB_PATH`), по умолчанию `./data/kitchen.sqlite`; каталог `data/` в `.gitignore`. Бэкап — `VACUUM INTO` в отдельный файл и вынос за пределы сервера; детали — ADR-007 (Q-02, NFR-13).

## Последствия

- Нет нативных зависимостей: Docker-образ без компиляторов, обновление Node не ломает установку.
- `node:sqlite` — release candidate. Если в Node 26 LTS изменится API, правится только `src/server/db/`. Запасной вариант — better-sqlite3 с почти тем же синхронным API; решение о переходе — отдельным ADR.
- Схема пишется вручную на SQL; reviewer проверяет, что миграции не трогают строки журнала.
- Журнал защищён от правки и удаления триггерами; ошибки в данных исправляются только новыми событиями (BR-02).
- Масштаб: даже 1 млн строк журнала с индексом `(product_id, occurred_at)` — десятки мегабайт и миллисекунды на выборку по позиции. Переезд на PostgreSQL при необходимости — перенос двух append-only таблиц и нескольких справочников (Q-01).
