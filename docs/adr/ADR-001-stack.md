# ADR-001. Технологический стек и структура репозитория

- **Статус:** принято 2026-09-28 — владелец выбрал вариант A (TypeScript целиком)
- **Дата:** 2026-09-28
- **Вопрос:** Q-06 (решает владелец по этому документу)
- **Задача:** B-00a, шаг 0
- **Учитывает:** Q-01 закрыт: SQLite. Хостинг (Q-02) здесь не решается. От стека требуется только одно: приложение собирается в Docker-образ и запускается на любой Linux-машине.

Версии проверены 2026-09-28 по страницам релизов (ссылки в конце). При принятии ADR точные версии фиксирует lock-файл, в тексте они приведены для оценки зрелости.

---

## 1. Контекст

Что влияет на выбор, в порядке важности для владельца:

1. **Код пишут агенты, поддерживает один человек.** Важно, сколько инструментов, языков, lock-файлов и тест-раннеров придётся держать в голове. Агенты работают с узкими правами (`.claude/agents/*.md`): backend-dev пишет только в `src/domain/` и `src/server/`, frontend-dev — только в `src/web/`, tester — только в `tests/`.
2. **Домен — чистые функции, время передаётся параметром** (NFR-16). На этом держится симулятор `tests/sim/` (шаг 2): многомесячная, а лучше многолетняя синтетическая жизнь дома, несколько сценариев из 14.2. Скорость прогона важна, потому что Stop-хук `.claude/hooks/require-green-tests.sh` гоняет **весь** набор из `.claude/test-command` при каждом завершении работы backend-dev и frontend-dev.
3. **Общие типы событий на клиенте и сервере.** Уточнение: по правилам frontend-dev доменной логики на клиенте нет, остаток и статусы приходят с сервера. Поэтому общими нужны только **типы** (DTO событий, перечисление типов событий из 5.2, ответы API), а не код.
4. **SQLite** (Q-01): зрелость драйвера и способ миграций.
5. **Playwright для Barbora во второй фазе** (BR-23): в первой версии код не пишется, но стек не должен мешать потом.
6. **Self-hosted, Docker/Proxmox**, хостинг не выбран.
7. **Время:** сутки по Europe/Vilnius, переход на летнее время не теряет и не дублирует списаний (BR-27, NFR-14).

Масштаб: 150–200 позиций, десятки событий в день, один пользователь. Производительность HTTP и БД роли не играет ни в одном варианте. Различия проявляются в эксплуатации, в типах и в скорости симулятора.

## 3. Вариант A — TypeScript целиком

### 3.1 Набор

| Слой | Выбор | Версия и зрелость |
| --- | --- | --- |
| Рантайм | Node.js 26 | Вышел 2026-05-05, статус Active LTS получает 2026-10-28, то есть через месяц после этого ADR. В нём по умолчанию включён Temporal API. Node 24 — текущий LTS, но 2026-10-20 уходит в maintenance, а Temporal в нём нет |
| Запуск TS на сервере | Встроенное в Node удаление типов (type stripping) | Стабильно с Node 24.12 / 25.2. Работает только со «стираемым» синтаксисом: без `enum`, `namespace` и parameter properties. Флаг `--experimental-transform-types` удалён в Node 26. Отдельной сборки сервера нет |
| Проверка типов | TypeScript 7.0 (нативный компилятор на Go, релиз 2026-07-08) | В 8–12 раз быстрее прежнего `tsc` по данным Microsoft. Важно, потому что проверка типов входит в test-command |
| HTTP | Hono 4.13 + `@hono/node-server` 2.1 | Небольшой, на Web-стандартах `Request`/`Response`. Приёмочные тесты вызывают `app.request()` без поднятия порта. Типизированный клиент `hc` даёт типы ответов на клиенте без кодогенерации. Равноценная альтернатива — Fastify 5.12 (зрелее, консервативнее, тесты через `inject()`) |
| Драйвер SQLite | `better-sqlite3` 13.0 | Синхронный API, давний стандарт для SQLite в Node. Начиная с 13.0 собран на N-API: готовые бинарники не зависят от версии Node. Встроенный `node:sqlite` тоже синхронный и не требует зависимостей, но пока в статусе 1.2 «release candidate». К нему можно перейти позже, API похожи |
| Время и пояс | `Temporal` (встроен в Node 26) | `ZonedDateTime` в Europe/Vilnius, `startOfDay()`, арифметика по календарным дням с учётом DST. BR-27 закрывается без сторонних библиотек |
| Тесты | Vitest 5.0 | Требует Node ≥ 22 и Vite ≥ 6.4. Один раннер на домен, сервер, клиент и симулятор |
| Пакетный менеджер | npm | Идёт вместе с Node, один `package-lock.json` |
| Фаза 2 | `playwright` 1.63 (Node) | Основная реализация Playwright написана на TS |

### 3.2 Структура репозитория

```
package.json            одна кодовая база, без workspaces
package-lock.json
tsconfig.json           strict, erasableSyntaxOnly, verbatimModuleSyntax, noEmit
vite.config.ts          root: src/web
vitest.config.ts        include: tests/**
src/domain/             чистые функции и типы событий; без node:*, без БД, без часов
src/server/             Hono, репозиторий SQLite, миграции, планировщик, main.ts
src/web/                PWA: index.html, manifest, sw.js, экраны
tests/unit/             домен
tests/acceptance/       критерии задач через app.request()
tests/sim/              синтетический дом
tests/e2e/              позже: сквозные сценарии Playwright (14.1)
```

Общие типы: `src/web` импортирует из `src/domain` **только** `import type`. Благодаря `verbatimModuleSyntax` такие импорты стираются при сборке, так что доменный код в клиентский бандл не попадёт. Как закрепить правило механически — решит ADR-004.

### 3.3 `.claude/test-command`

```
npx tsc --noEmit && npx vitest run
```

Сначала проверка типов всего репозитория, затем все тесты: домен, приёмочные, симулятор, клиент.

### 3.4 Доводы

**За:**
- Один язык, один рантайм, один lock-файл, один тест-раннер. Tester пишет тесты в одном фреймворке, reviewer читает один язык.
- Контракт событий проверяется компилятором. Если backend-dev меняет тип события несовместимо, `tsc` в test-command сразу падает на стороне `src/web`. Кодогенерации и проверки её свежести нет.
- Симулятор быстрее, оценка — в разделе 5.
- Temporal в рантайме закрывает BR-27 без зависимостей.
- Для сервера нет шага сборки: Node 26 запускает `.ts` напрямую.

**Против:**
- `better-sqlite3` — нативный модуль. Готовые бинарники есть, но при сборке образа на экзотической архитектуре или musl возможна компиляция из исходников. Этот риск исчезает при переходе на `node:sqlite` после его стабилизации.
- Высокая скорость смены мажорных версий в экосистеме: за последние 12 месяцев вышли Vite 7→8, Vitest 4→5, TypeScript 6→7, Node 24→26. Частично это касается и варианта B, потому что клиент там тоже на Vite и Vitest.
- В JS нет встроенного десятичного типа. Для нас это не важно: количества целые в расходных единицах, а точность до грамма не нужна (A-03).
- Node 26 будет «Current» ещё месяц, до 2026-10-28. Пока идёт шаг 0, это не мешает.

## 4. Вариант B — Python на сервере и в домене, TypeScript на клиенте

### 4.1 Набор

| Слой | Выбор | Версия и зрелость |
| --- | --- | --- |
| Рантайм | CPython 3.14 | Текущая стабильная ветка, 3.14.7 от 2026-08-05. Версия 3.15.0 выходит 2026-10-01. Переходить на неё стоит, когда зависимости выпустят колёса под 3.15 |
| HTTP | FastAPI 0.141 + Pydantic 2.13 + uvicorn | FastAPI всё ещё 0.x, выпуски частые: 52 релиза с января по июль 2026. Автоматически публикует OpenAPI-схему |
| Драйвер SQLite | `sqlite3` из стандартной библиотеки | Самый проверенный драйвер из всех рассмотренных, без нативных зависимостей в проекте |
| Время и пояс | `datetime` + `zoneinfo` (стандартная библиотека) | Работает. Есть известная ловушка: `aware datetime + timedelta` считает по настенному времени, поэтому для суток нужно оперировать `date`. В slim-образе проверить наличие системного tzdata или поставить пакет `tzdata` |
| Проверка типов | mypy или pyright | Аннотации в Python не обязательны. Без проверяющего инструмента в test-command типы не страхуют агентов |
| Тесты сервера | pytest 9.1 | Зрелый, быстрый старт |
| Тесты клиента | Vitest 5.0 | Клиент на TS, второй раннер неизбежен |
| Пакетные менеджеры | uv 0.12 (Python) + npm (клиент) | Два lock-файла: `uv.lock` и `package-lock.json` |
| Типы для клиента | Схема OpenAPI из FastAPI → `openapi-typescript` 7.13 → `src/web/api/schema.d.ts` | Кодогенерация, сгенерированный файл хранится в репозитории |
| Миграции | Нумерованные `.sql` (как в A). Альтернатива — Alembic 1.20, но он требует SQLAlchemy, а для `ALTER` в SQLite нужен batch-режим | |
| Фаза 2 | `playwright` 1.63 (Python) | Поддерживает Python 3.10–3.14 |

### 4.2 Структура репозитория

```
pyproject.toml          зависимости Python, настройки pytest (pythonpath = ["src"]) и mypy
uv.lock
package.json            только клиент: Vite, Vitest, openapi-typescript
package-lock.json
tsconfig.json
vite.config.ts          root: src/web
vitest.config.ts        include: tests/web/**
src/domain/             Python-пакет: чистые функции, frozen dataclasses
src/server/             FastAPI, sqlite3, миграции, планировщик, экспорт OpenAPI
src/web/                PWA; src/web/api/schema.d.ts — сгенерирован
tests/unit/             pytest
tests/acceptance/       pytest + TestClient FastAPI
tests/sim/              pytest
tests/web/              vitest
tests/e2e/              позже
```

### 4.3 `.claude/test-command`

```
uv run mypy src && uv run pytest -q && npx tsc --noEmit && npx vitest run
```

Сюда не входит проверка свежести `schema.d.ts`: после изменения API схему нужно перегенерировать. Если добавить проверку в test-command, backend-dev получит красный Stop-хук из-за файла в `src/web/`, который ему менять нельзя. Поэтому перегенерация становится отдельным шагом frontend-dev после каждого изменения API.

### 4.4 Доводы

**За:**
- `sqlite3` и `zoneinfo` входят в стандартную библиотеку: для SQLite и BR-27 нет ни одной внешней зависимости.
- FastAPI бесплатно даёт OpenAPI-документацию API.
- Если владельцу удобнее читать и чинить Python, это весомый довод: поддерживает он.
- Для анализа выгрузок симулятора удобнее Python-экосистема (pandas, Jupyter). Это удобство, а не требование: метрики G-1 и G-2 считаются простыми функциями.

**Против:**
- Два языка, два рантайма, два пакетных менеджера, два lock-файла, два тест-раннера. Tester пишет тесты на pytest и на Vitest, test-command длиннее, а Docker-сборка двухступенчатая: Node для `vite build`, Python для рантайма.
- Контракт между клиентом и сервером держится на кодогенерации. Рассинхрон ловится только после перегенерации, а права агентов делают перегенерацию отдельным шагом другого агента.
- Типы не страхуют агентов, пока в test-command нет mypy или pyright. С ним — ещё один инструмент со своими настройками.
- Симулятор медленнее, оценка — в разделе 5.
- В FastAPI обработчики `def` выполняются в пуле потоков, а соединение `sqlite3` по умолчанию привязано к потоку (`check_same_thread`). Нужна явная дисциплина соединений. В A синхронный драйвер работает в одном потоке, и вопрос не возникает.

## 5. Скорость симулятора — оценка, а не замер

**Объём работы.** 200 позиций × 365 дней × 10 лет ≈ 730 тыс. «позиция-суток» на сценарий. За каждые сутки симулятор генерирует реальный расход и отметки, система делает автосписание, а раз в неделю — прогноз и статусы. Сценариев 9 (14.2), плюс, возможно, несколько сидов.

**Разница рантаймов.** В независимом замере Мигеля Гринберга (октябрь 2025) на CPU-нагруженном коде без библиотек (Фибоначчи, пузырьковая сортировка) PyPy был в 18 раз быстрее CPython 3.14 и в 3 раза быстрее Node.js. Отсюда Node ≈ в 6 раз быстрее CPython 3.14. JIT в 3.14 экспериментальный и по умолчанию выключен, медианный выигрыш 3.14 над 3.13 на pyperformance — около 12–18%. Порядок разницы это не меняет.

**Что это значит для нас.** Если одна позиция-сутки стоит ~10 мкс в Node, то в CPython это ~60 мкс. Десятилетний сценарий займёт ~7 с против ~45 с, а все 9 сценариев — ~1 мин против ~7 мин. Значения за мкс — предположение. Надёжен только порядок соотношения, и он зависит от кода: на словарях и объектах разрыв обычно меньше, чем на чистой арифметике.

**Что сильнее языка.** Алгоритм. Если на каждые сутки остаток пересчитывается свёрткой всего журнала, получается O(n²), и это медленно на любом языке. Этот вопрос решает ADR-003 (проекция-кэш или вычисление на лету), и его ответ сильнее влияет на симулятор, чем выбор между A и B.

**Смягчение для B.** Сценарии независимы и параллелятся через pytest-xdist. У A то же преимущество: Vitest гоняет файлы в воркерах. PyPy быстр, но совместимость зависимостей (pydantic-core) пришлось бы проверять отдельно, домен при этом их не использует.

**Как проверить за 1–2 часа, если владелец хочет замер вместо оценки.** Написать одинаковый наивный цикл «автосписание + свёртка остатка» на 200 позиций × 10 лет на обоих языках и засечь время. Это не каркас и не прикладная логика, а одноразовый замер вне репозитория.

## 6. Сводное сравнение

| Критерий | A: TypeScript целиком | B: Python + TypeScript |
| --- | --- | --- |
| Инструменты для поддержки одним человеком | 1 язык, npm, Vitest | 2 языка, uv + npm, pytest + Vitest, mypy |
| Общие типы событий | `import type` из `src/domain`, проверяет компилятор | Кодогенерация OpenAPI → TS, отдельный шаг, рассинхрон ловится поздно |
| Чистый домен, время параметром | Равно | Равно |
| Сутки по Вильнюсу, DST (BR-27) | Temporal встроен в Node 26 | `zoneinfo` в стандартной библиотеке, есть ловушка с `timedelta` |
| Скорость симулятора | Порядка ×6 быстрее (оценка) | Базовая; заметно при многолетних прогонах в Stop-хуке |
| Драйвер SQLite | `better-sqlite3` 13 (нативный, N-API); `node:sqlite` в RC | `sqlite3` из стандартной библиотеки — самый зрелый |
| Миграции | Свои `.sql` + `user_version` | Свои `.sql` + `user_version`; Alembic как опция |
| Playwright (фаза 2) | Основная реализация | Полноценная поддержка |
| Docker | Одна ступень Node | Node для сборки клиента + Python для рантайма |
| Скорость смены мажорных версий | Высокая (Vite, Vitest, TS, Node) | Та же на клиенте, плюс FastAPI 0.x |

## 7. Рекомендация

**Вариант A — TypeScript целиком на Node.js 26.** Решающие доводы: один набор инструментов для одного поддерживающего, контракт событий проверяется компилятором без кодогенерации, симулятор быстрее, а BR-27 закрывается встроенным Temporal.

Вариант B разумен, если владелец заметно увереннее читает и отлаживает Python или планирует анализировать данные симулятора в Python-экосистеме. Тогда владелец принимает цену из раздела 4.4: два набора инструментов, кодогенерация контракта и более медленный симулятор.

Решение за владельцем.

## 8. Последствия

### Если принят A

Architect создаёт отдельным шагом после принятия, в рамках B-00a:
- `package.json`: зависимости, `"type": "module"`, `"engines": { "node": ">=26" }`;
- `tsconfig.json`: `strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, `noEmit`. Относительные импорты пишутся с расширением `.ts`, как требует Node для прямого запуска;
- `vite.config.ts`, `vitest.config.ts`;
- `.gitignore`: добавить `dist/` и файлы БД;
- `.claude/test-command` из раздела 3.3;
- один проходящий smoke-тест, чтобы Stop-хук заработал.

Ещё два последствия:
- Версия Node в Docker-образе закрепляется тегом базового образа в ADR-007. Файл `.nvmrc` не нужен: `engines` достаточно.
- Правило «клиент импортирует из домена только типы» и его механическая проверка переходят в ADR-004.

### Если принят B

- Architect создаёт `pyproject.toml` и `package.json` (только клиент), конфиги и `.claude/test-command` из раздела 4.3.
- Нужен порядок перегенерации `schema.d.ts`: кто и когда её запускает. Предложение: frontend-dev первым шагом любой задачи, которая идёт после изменения API. Это пункт для delivery-lead.
- Tester ведёт тесты в двух фреймворках.

### В обоих случаях

- **Симулятор в test-command.** Stop-хук гоняет весь набор при каждом завершении работы разработчика. Предложение: в test-command входят сценарии симулятора на коротком горизонте с фиксированным сидом, а многолетние прогоны идут отдельной командой (`npm run sim` или `uv run python -m tests.sim`). Их запускают tester и backend-dev по правилу 14.4 «изменение прогноза — метрики до и после». Это уточнение процесса, спеку оно не меняет. Решает delivery-lead вместе с tester.
- Спека не меняется, инварианты не затрагиваются: стек не влияет ни на BR-01, ни на BR-02, ни на остальные правила из CLAUDE.md.
- ADR-002 (СУБД, миграции), ADR-004 (модули) и ADR-005 (планировщик, DST) пишутся под выбранный язык.
