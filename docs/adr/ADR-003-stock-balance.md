## 1. Контекст

Остаток позиции — производная от журнала событий (BR-01). Журнал не редактируется, ошибки исправляются отменой (BR-02). В таблице 5.2 спеки семь типов событий, и они устроены по-разному:

- **приращения** — покупка, потребление порции, автосписание, списание по рецепту, порча — сдвигают остаток на количество;
- **значения** — инвентаризация и «закончилось» — устанавливают остаток, независимо от того, каким он был;
- **отмена** ссылается на другое событие.

Значения-события не укладываются в буквальное «сумма событий»: у инвентаризации нет собственного количества-приращения, оно зависит от того, что было до неё. Кроме того, события приходят задним числом: чек загружают на следующий день, отпуск отмечают после возвращения (FR-ABS-02, FR-ABS-04), автосписание догоняет пропущенные сутки (FR-CON-08). Всё это должно давать один и тот же остаток независимо от того, в каком порядке события были записаны.

Объём, на который рассчитано решение:

| Величина | Оценка |
| --- | --- |
| Позиций | 150–200, из них ритмичных (с ежедневным автосписанием) — до 60 |
| Событий в сутки | 50–100: до 60 автосписаний + десятки ручных отметок |
| Событий в год | 20–40 тыс. |
| Событий за 10 лет | 200–400 тыс.; для оценки берём верхнюю границу **500 тыс.** |
| Событий на одну позицию за 10 лет | в среднем ~2,5 тыс., максимум у ритмичной ~5 тыс. (3650 автосписаний + отметки и покупки) |
| Размер журнала в SQLite | порядка 100 байт на строку с индексом → 50–100 МБ за 10 лет |

## 2. Решение кратко

1. **Остаток вычисляется на лету** чистой доменной функцией-свёрткой по событиям позиции. Хранимой проекции в первой версии нет. Условие, при котором она вводится, и правила для неё — в разделе 3.
2. **Свёртка, а не сумма.** События позиции упорядочиваются по времени события. Значение-событие устанавливает остаток, приращения прибавляются или вычитаются после него. Без значения-события отсчёт идёт от нуля. По сути это уточнение формулировки BR-01, поэтому вынесено владельцу (раздел 9).
3. **Отмена — это исключение из свёртки.** Отмена — новое событие со ссылкой на отменённое. Отменённое событие остаётся в журнале, но в расчёт не входит. Для приращения это то же самое, что компенсация. Для значения-события только так и можно отменить корректно: остаток пересчитывается от предыдущего значения-события. Отмену можно отменить.
4. **Порядок — по времени события**, при совпадении — по порядку записи. Событие задним числом встаёт на своё место во времени. Если перед ним в той же позиции стоит более поздняя инвентаризация, текущий остаток оно не меняет: факт, зафиксированный инвентаризацией, сильнее. Меняется только неучтённый расход, который видит обучение. Автосписание за сутки D датируется началом суток D по Вильнюсу.
5. **Состояние позиции** (отключена, архивирована, возвращена) хранится в отдельном журнале состояний — append-only, не события остатка. Признак активности выводится из последнего события этого журнала. Экран журнала действий показывает обе ленты вместе, отсортированные по времени.
6. **Идемпотентность**: `id` события — UUID и первичный ключ. Для одиночного действия пользователя его создаёт клиент. Для строк операции и системных событий (автосписание, отмены из-за отпуска, автоархив) это UUIDv5 от канонической строки-ключа, поэтому повторный запуск ничего не дублирует. Повтор с тем же `id` возвращает уже записанное событие (раздел 8).

## 3. На лету или проекция-кэш

### Варианты

| | A. На лету | B. Хранимая проекция | C. Кэш в памяти процесса |
| --- | --- | --- | --- |
| Суть | Каждый запрос остатка читает события позиции и сворачивает их | Таблица «позиция → остаток», пересобирается из журнала | Словарь в памяти сервера «позиция → остаток», сбрасывается при записи по позиции |
| Источник правды | Журнал | Журнал; таблица — кэш | Журнал; словарь — кэш |
| Сложность | Нет лишнего состояния | Нужна инвалидация при событиях задним числом, отменах, ретро-отпуске; нужна проверка «кэш = свёртка» | Инвалидация та же, но кэш живёт только в памяти и при рестарте собирается заново |
| Риск расхождения | Нет | Есть: ошибка инвалидации — неверный остаток, который выглядит правдой | Меньше, чем у B: рестарт всё лечит |

### Стоимость варианта A на нашем объёме

Цифры — порядки величин, а не замеры. Замер — условие пересмотра решения, см. ниже.

| Операция | Год 1 (~40 тыс. событий) | Год 10 (~500 тыс.) |
| --- | --- | --- |
| Остаток одной позиции: чтение до 5 тыс. строк по индексу `(product_id, occurred_at)` и свёртка | < 1 мс | 1–5 мс |
| Остатки всех позиций (киоск, инвентарь, статусы, список): один проход по журналу, отсортированному по позиции и времени | 10–40 мс | 0,2–0,5 с |

Сама свёртка в TypeScript занимает микросекунды, основное время уходит на чтение строк из SQLite. Одна позиция — дёшево всегда. Узкое место — экраны со всеми позициями через несколько лет эксплуатации.

### Рекомендация

**Вариант A в первой версии.** На первые годы запаса производительности хватает с большим запасом, а A — единственный вариант, где расхождение кэша с журналом невозможно в принципе. Это важно, потому что события задним числом, отмены и ретро-отпуск — именно те случаи, на которых инвалидация ошибается.

Остаток не считается SQL-запросом (`SUM`): правило свёртки живёт в одном месте — в доменной функции (NFR-16). Хранилище только выдаёт упорядоченные события.

**Условие ввести кэш.** На синтетическом журнале в 500 тыс. событий вычисление остатков всех активных позиций на целевом сервере занимает больше 100 мс. Замер добавляется в симулятор (B-04) или отдельным тестом производительности. Когда условие сработает, кэш вводится дополнением к этому ADR по таким правилам:

- сначала вариант C, и только если его недостаточно — B;
- кэш хранится по позиции и пересобирается целиком для позиции в той же транзакции, что и любая запись в её журнал: новое событие, отмена, отмены из-за ретро-отпуска. Пересборка одной позиции стоит единицы миллисекунд, поэтому частичной инвалидации не делаем;
- кэш можно удалить в любой момент без потери данных; при старте и по команде он пересобирается из журнала;
- тест сверяет кэш со свёрткой на всём журнале симулятора.

Сокращение без кэша, которое можно применить раньше. Значение-событие обнуляет историю до себя, поэтому свёртка от последнего действующего значения-события даёт **точно** тот же результат, что свёртка всего журнала. Это свойство самой модели, а не кэш. Им можно ограничить чтение, если узким местом окажется только чтение.

## 4. Модель события остатка

Логические атрибуты. Физическая схема — задача B-02 в рамках ADR-002.

| Атрибут | Обязателен | Смысл |
| --- | --- | --- |
| `id` | да | UUID, первичный ключ: от клиента или UUIDv5 от строки-ключа (BR-26, раздел 8) |
| `seq` | да | Порядок записи: монотонный номер, присваивает хранилище. Разрешает совпадения времени и задаёт «отмена позже цели» |
| `product_id` | да | Позиция. У отмены — позиция отменяемого события |
| `kind` | да | Тип из 5.2, см. таблицу ниже |
| `quantity` | у приращений | Количество в расходной единице, больше нуля. Знак задаёт тип, а не число |
| `value` | у инвентаризации | Установленный остаток в расходной единице, не меньше нуля: это наблюдаемый факт, и проверка относится к вводу, а не к расчётному остатку (BR-15). У «закончилось» значение всегда 0 и не хранится |
| `target_id` | у отмены | Идентификатор отменяемого события |
| `occurred_at` | да | Время события, UTC, мс (NFR-14). Задаёт порядок свёртки |
| `recorded_at` | да | Время записи на сервере, UTC, мс. Для аудита и для «что система знала к моменту T» |
| `source` | да | Источник: киоск, телефон, чек, фото стола, голос, автосписание, калибровка, отпуск и т. п. |
| `operation_id` | нет | Общий для событий одной операции: рецепт, чек, фото стола. Группирует ленту, позволяет отменить операцию целиком (FR-KSK-11), задаёт идентификаторы строк (раздел 8) |
| `recognition_confidence` | нет | Уверенность распознавания для распознанных событий (5.1, FR-CAL-08) |
| `packs`, `units_per_pack` | у покупки, если приход в упаковках | Сколько упаковок и по какому коэффициенту пересчитано в момент записи (BR-03). `quantity` = `packs` × `units_per_pack` |

Количество фиксируется в расходной единице в момент записи. Поэтому изменение коэффициента в карточке историю не переписывает. Так же и значение инвентаризации из грубого ответа калибровки (FR-CAL-07) пересчитывается в число при записи, и последующие изменения нормы на него не влияют.

| Тип 5.2 | `kind` | Класс | Действие в свёртке |
| --- | --- | --- | --- |
| Покупка | `purchase` | приращение | `+quantity` |
| Потребление порции | `portion` | приращение | `−quantity` |
| Автосписание по норме | `auto_writeoff` | приращение | `−quantity` |
| Списание по рецепту или блюду | `recipe` | приращение | `−quantity` |
| Выброс из-за порчи | `spoilage` | приращение | `−quantity` |
| Сигнал «закончилось» | `depleted` | значение | остаток := 0 |
| Инвентаризация | `inventory` | значение | остаток := `value` |
| Отмена события | `cancel` | отмена | исключает `target_id` из свёртки (раздел 6) |

Новых типов ADR не вводит. Если B-14 решит выражать «оценка остатка повышается» (BR-14) событием, это будет инвентаризация с источником «вычёркивание», а не новый тип: новый тип менял бы 5.2.

## 5. Свёртка и порядок событий

### 5.1 Правило

Для позиции, по набору её событий и необязательной границе `asOf`:

1. **Действующие события.** Событие действует, если на него не ссылается ни одна действующая отмена. Отмена всегда записана позже цели (`seq` больше), поэтому один проход по убыванию `seq` решает всё: встретили отмену, которая сама не отменена, — помечаем её цель как отменённую. Рекурсия «отмена отмены» получается сама.
2. **Порядок.** Действующие приращения и значения сортируются по `(occurred_at, seq)`. Отмены в порядке не участвуют: они действуют на всю историю, независимо от собственного времени.
3. **Граница.** Если задан `asOf`, учитываются события с `occurred_at ≤ asOf`. Для текущего остатка граница не нужна: событий в будущем в журнале нет.
4. **Свёртка.** Начальное значение — 0. Приращение прибавляет или вычитает `quantity`, значение-событие заменяет остаток своим значением.
5. **Ограничений нет.** Результат не обрезается снизу, отрицательный остаток возвращается как есть (BR-15, инвариант 6). Ни одна запись не отклоняется из-за того, что остаток уйдёт в минус.

Вспомогательный результат той же свёртки — **лента остатка**: для каждого действующего события остаток до и после. Для значения-события разница «после − до» — это **неявное приращение**: неучтённый расход (отрицательное) или недосписание (положительное). Оно не хранится, а вычисляется заново при каждой свёртке. Неявное приращение — то, чему «учит прогноз» инвентаризация и «закончилось» (колонка 5.2), и вход для калибровки (B-13): аномалия, отрицательный остаток перед значением-событием.

Чтобы получить «что система знала к моменту T» (симулятор, разбор ошибок), вызывающий передаёт события с `recorded_at ≤ T` и `asOf = T`. Обе границы — параметры, системные часы домен не читает (NFR-16).

### 5.2 Как это сочетается с BR-01

Буквально BR-01 говорит: «вычисляется как сумма событий». Предлагаемое правило эквивалентно формулировке «последнее действующее значение-событие плюс сумма приращений после него; если значения-события нет — сумма всех приращений». Суть инварианта сохраняется: остаток никогда не хранится числом и всегда выводится из журнала. Но формулировка «сумма событий» становится неточной. Поэтому это **изменение текста инварианта**, и спека здесь не правится — вопрос в разделе 9 (решён 2026-10-06, текст BR-01 уточнён).

Отвергнутые способы сохранить буквальную сумму:

- **Записывать инвентаризацию как приращение, вычисленное при записи** (`value − остаток в момент записи`). Ломается на любом событии задним числом раньше инвентаризации и на отмене такого события: зафиксированная разница перестаёт соответствовать факту. В примере 1 это даёт фантомные 1800 г гречки.
- **Запретить события задним числом раньше последней инвентаризации.** Противоречит FR-ABS-02, FR-ABS-04 и NFR-07 и вводит запрет там, где спека требует мягкой деградации.

### 5.3 Время события, а не время записи

Свёртка упорядочена по `occurred_at`. Обоснование: инвентаризация — это факт «в момент T на полке было X». Всё, что физически произошло до T, в этом X уже учтено. Если упорядочить по времени записи, поздно загруженный чек добавит товар, который уже был пересчитан, а ретро-отпуск вернёт автосписания, перекрытые инвентаризацией. При совпадении `occurred_at` порядок задаёт `seq`.

Откуда берётся `occurred_at`:

- отметки на киоске и телефоне — время нажатия на клиенте. Клиент передаёт его в запросе, повтор отправки передаёт то же время;
- явный ввод задним числом — время, которое выбрал пользователь;
- приход по чеку — время с чека, если оно распознано, иначе время загрузки. Это существенно: см. пример 1. Детали — B-20;
- автосписание за сутки D — **начало суток D по Europe/Vilnius** (00:00 местного времени, в UTC с учётом DST — ADR-005), хотя записывается оно после окончания суток (FR-CON-07);
- отмена — время записи. На свёртку оно не влияет и нужно только ленте.

Почему автосписание датируется началом суток. Значение-событие в течение дня D (обычно «закончилось» или вечерняя инвентаризация) перекрывает автосписание этого дня, и после «закончилось» остаток остаётся нулём, а не уходит в минус. Если бы автосписание датировалось концом суток, каждое «закончилось» у ритмичной позиции давало бы минус на суточную норму. Это ложный сигнал BR-15, который понижает уверенность. Цена выбора: расход, случившийся в день D после значения-события, теряется — не больше одной суточной нормы и только в дни со значением-событием. Это перекрывается страховым запасом (Q-09). Если симулятор покажет, что этого мало, правило меняется дополнением к ADR. Уже записанные события при этом не трогаются.

Для ADR-005: метка времени автосписания определена здесь, ADR-005 должен её использовать.

### 5.4 Примеры

Дни — октябрь 2026, Пн 12.10. `seq` — порядок записи.

**Пример 1. Чек загружен позже инвентаризации.** Гречка, г, рывковая — автосписаний нет.

| seq | Событие | occurred_at | Записано |
| --- | --- | --- | --- |
| 1 | Инвентаризация 400 | Пн 12.10 09:00 | Пн 09:00 |
| 2 | Инвентаризация 1900 (фото стола) | Вт 13.10 10:00 | Вт 10:00 |
| 3 | Рецепт −250 | Вт 13.10 20:00 | Вт 20:00 |
| 4 | Покупка 2 уп × 900 = +1800 (чек) | Пн 12.10 18:00 | Ср 14.10 09:00 |

Реальность: 400 + 1800 − 300 неотмеченного расхода = 1900 на вторник, после рецепта — 1650.

- До загрузки чека: 400 → **1900** (неявное +1500, «откуда-то взялось») → −250 = **1650**.
- После загрузки, по времени события: 400 → +1800 = 2200 → **1900** (неявное −300, реальный неотмеченный расход) → −250 = **1650**. Текущий остаток не изменился, обучение получило правильный расход.
- Если бы порядок был по времени записи: 400 → 1900 → 1650 → +1800 = **3450**. Фантомные 1800 г.

**Пример 2. Отмена ошибочной инвентаризации и событие задним числом после неё.** Рис, г, рывковый.

| seq | Событие | occurred_at |
| --- | --- | --- |
| 1 | Инвентаризация 1000 | Пт 09.10 10:00 |
| 2 | Покупка +900 | Сб 10.10 12:00 |
| 3 | Рецепт −300 | Вс 11.10 19:00 |
| 4 | Инвентаризация 200 — ошибка: ответ «кончается» отнесён не к той позиции | Пн 12.10 08:00 |
| 5 | Порция −100 | Пн 12.10 20:00 |
| 6 | Отмена seq 4 | Вт 13.10 09:00 |
| 7 | Порция −100, внесена в среду задним числом | Вс 11.10 21:00 |

- До отмены: 1000 → 1900 → 1600 → **200** → 100.
- После отмены (seq 4 исключено): 1000 + 900 − 300 − 100 = **1500**.
- После события задним числом: 1000 + 900 − 300 − 100 − 100 = **1400**. Правильно.
- Отмена как компенсация: в момент отмены вычисляем +1400 (1600 − 200) и записываем приращение. Сейчас это тоже даёт 1500, но после seq 7 получится 1000 + 900 − 300 − 100 → 200 → −100 → +1400 = **1500** вместо 1400. Событие задним числом поглотила отменённая инвентаризация, а «компенсация» застыла на старом числе. Поэтому значение-событие компенсацией не отменить.
- Если затем отменить отмену seq 6, seq 4 снова действует: 1000 + 900 − 300 − 100 → 200 → −100 = **100**.

**Пример 3. Отпуск задним числом после инвентаризации (FR-ABS-04).** Кофе, г, ритмичный, норма 20 г/сут. А_D — автосписание за сутки D, датировано D 00:00 по Вильнюсу, записано в ночь на D+1.

Реальность: в Чт 08.10 в 23:00 было 500 г; в пятницу выпили 20; с Сб 10.10 по Вт 13.10 дома никого; в Ср 14.10 выпили 20.

| seq | Событие | occurred_at |
| --- | --- | --- |
| 1 | Инвентаризация 500 | Чт 08.10 23:00 |
| 2–6 | А09…А13, по −20 | Пт 09.10 … Вт 13.10, 00:00 |
| 7 | Инвентаризация 480 (вернулись, фото стола) | Вт 13.10 22:00 |
| 8 | А14 −20 | Ср 14.10 00:00 |
| 9–12 | Отмены А10…А13 — пользователь в Чт 15.10 отметил отпуск 10.10–13.10 | Чт 15.10 09:00 |

- До отметки отпуска: 500 − 20 × 5 = 400 → **480** (неявное +80: выглядит так, будто норма завышена) → −20 = **460**.
- После отметки: 500 − 20 (А09) = 480 → **480** (неявное 0) → −20 (А14) = **460**. Текущий остаток тот же — его зафиксировала инвентаризация. Но ложное расхождение +80 исчезло, и обучение нормы и уверенность его не увидят.
- Вариант без инвентаризации seq 7: до отметки отпуска 500 − 20 × 6 = **380**, после — 500 − 20 − 20 = **460**. Отпуск вернул 80 г в текущий остаток.

Вывод: отпуск задним числом всегда выражается отменами автосписаний за дни отпуска. Перед инвентаризацией такие отмены исправляют только историю расхода, после неё — ещё и текущий остаток. Отмены создаёт отдельная операция: она находит действующие `auto_writeoff` за дни периода и пишет по отмене на каждое, с детерминированными идентификаторами (раздел 8). Механика расписания и догона — ADR-005, B-07.

## 6. Отмена

**Смысл.** Отмена — событие `cancel` со ссылкой `target_id`. Отменённое событие не удаляется и не редактируется (инвариант 2) и видно в журнале с пометкой. В свёртке оно не участвует, как если бы его не было, — на всей временной оси, а не с момента отмены.

- Для приращения исключение численно совпадает с компенсацией: остаток меняется на `∓quantity` во всех точках после события. BR-02 в его буквальном смысле выполняется.
- Для значения-события исключение означает, что остаток после него пересчитывается от предыдущего действующего значения-события (или от нуля) с учётом всех приращений между ними, включая внесённые задним числом позже (пример 2). Выразить это фиксированным числом нельзя: правильная поправка зависит от событий, которые ещё могут прийти. Поэтому формулировку «компенсация отменённого» (5.2, BR-02) для таких событий нужно уточнить — вопрос в разделе 9 (решён 2026-10-06, BR-02 и 5.2 уточнены).

**Отмена отмены** (FR-LOG-02: «любое событие можно отменить») восстанавливает действие исходного события. Правило из 5.1 обрабатывает её без особых случаев.

**Повторная отмена** того же события другим идентификатором ничего не меняет: событие уже исключено. Если отменить одну из двух таких отмен, событие останется исключённым — другая отмена продолжает действовать.

**Целостность.** Отмена ссылается на существующее событие той же позиции. Хранилище проверяет это при записи — это проверка ссылки, а не запрет по остатку. Отмена всегда записана позже цели, поэтому циклов нет.

**Отмена операции.** Кнопка «отменить» на киоске (FR-KSK-11) после «приготовил» отменяет все события операции: по одной отмене на событие с общим `operation_id`. В модели отдельного «отменить операцию» нет.

**Системные отмены:** ретро-отпуск (пример 3) — с источником «отпуск» и ссылкой на период.

## 7. Изменения состояния позиции (FR-LOG-03)

Отключение кнопкой «больше не покупаю» (FR-CAT-04), автоархив (FR-CAT-05) и возврат в активные (FR-CAT-06) остаток не меняют. Поэтому это не события остатка.

### Варианты

| | Суть | Оценка |
| --- | --- | --- |
| A. Отдельный журнал состояний | Таблица событий состояния позиции, только добавление | Свёртка остатка его не видит; повод хранится как данные |
| B. Новый тип в журнале остатка | `state_change` рядом с покупками | Каждая свёртка обязана его отфильтровать; меняет таблицу 5.2 — правка спеки |
| C. Флаг `active` в карточке + общий аудит-лог правок | Признак хранится, лог — отдельно | Два источника правды о состоянии, которые могут разойтись |

### Рекомендация — A

Событие состояния позиции:

| Атрибут | Смысл |
| --- | --- |
| `id` | Клиентский или детерминированный идентификатор (раздел 8) |
| `seq`, `recorded_at`, `occurred_at` | Как у событий остатка; `occurred_at` = момент действия |
| `product_id` | Позиция |
| `state` | `inactive` или `active` — одно состояние «неактивна» (BR-08) |
| `reason` | `user_button` (кнопка), `auto_archive` (по сроку), `purchase` (возврат покупкой), `user_restore` (вернул вручную или отменил отключение) |
| `ref_event_id` | Необязательная ссылка: покупка, вернувшая позицию; отменяемое событие состояния |

- Признак активности **выводится** из последнего по `(occurred_at, seq)` события состояния позиции. Если событий нет — позиция активна. Стоит это ничего: событий состояния единицы на позицию.
- Отмена изменения состояния (FR-LOG-02) — новое событие с противоположным `state` и `reason = user_restore`. Исключение из свёртки здесь не нужно: состояние определяет последнее событие, и новое естественным образом его перекрывает.
- Журнал действий (FR-LOG-01, FR-LOG-03) — объединение двух лент по времени: события остатка и события состояния. От истории уведомлений он отделён (FR-LOG-04).
- Кто и когда пишет события состояния (автоархив по порогу Q-10, возврат покупкой и что делать, если эту покупку отменили) — задача B-12. ADR задаёт только место хранения и форму.
- Правки остальных атрибутов карточки (норма, коэффициент) в журнал действий FR-LOG-03 не требует, и этот ADR их не логирует.

В разделе 5.1 спеки этой сущности нет. Поведение она не меняет — это хранение, которого требуют BR-08 и FR-LOG-03. Добавлять ли строку в 5.1, решает delivery-lead.

## 8. Идемпотентность (BR-26)

Одна схема для всех событий — и остатка, и состояния позиции (раздел 7). Отдельного поля «ключ идемпотентности» нет: эту роль играет `id`.

- **`id` — всегда UUID и первичный ключ журнала.** Источников два:
  1. **Клиентский UUID** — для одиночного действия пользователя: отметка, отмена, ручное отключение. Клиент создаёт его в момент действия (`crypto.randomUUID()`, v4) и переиспользует при повторной отправке. Так же клиент создаёт `operation_id` многострочной операции.
  2. **Производный UUIDv5** — для строк операции и системных событий: `id = UUIDv5(NS, ключ)`. `NS` — постоянный UUID-namespace проекта: задаётся один раз в B-02 и после первой записи в журнал не меняется. Ключ — строка по шаблону из таблицы ниже.

  Версии v4 и v5 различаются полем версии внутри UUID, поэтому клиентский и производный `id` совпасть не могут.

| Событие | Ключ | Кто формирует |
| --- | --- | --- |
| Строка многострочной операции (рецепт, чек, фото стола) | `operation_line:{operation_id}:{номер строки}` | сервер при разборе запроса; повтор присылает те же строки в том же порядке. Номер строки, а не позиция: в одном чеке позиция может встретиться дважды (разные упаковки, BR-05) |
| Автосписание за сутки D | `auto_writeoff:{product_id}:{D}` | домен (ADR-005) |
| Отмена автосписания из-за отпуска | `absence_cancel:{target_id}` | домен (ADR-005) |
| Автоархив | `auto_archive:{product_id}:{местная дата}` | домен (B-12) |

`{D}` и `{местная дата}` — `YYYY-MM-DD` по Europe/Vilnius; `{product_id}`, `{operation_id}`, `{target_id}` — как в журнале.

- **Кто вычисляет UUIDv5.** Домен формирует только строку-ключ: это чистая функция, а хеш SHA-1 требует `node:crypto`, которого в домене нет (ADR-004). Сценарий в `src/server/app/` переводит ключ в `id` перед записью. Для домена `id` — непрозрачная строка: он их сравнивает, но не разбирает и не порождает. Поэтому симулятор может использовать ключ как `id` напрямую.
- **Запись** — «вставить, если такого `id` нет»:
  - запрос клиента: событие с этим `id` уже есть и содержимое совпадает — сервер возвращает записанное событие, как при первой записи. Содержимое отличается — ошибка клиента: сервер ничего не перезаписывает и возвращает конфликт. Коды ответа — API-контракт (B-16);
  - системная задача: событие с этим `id` уже есть — оно считается выполненным, содержимое не сравнивается. Записанное — факт, и повторный запуск не спорит с ним, даже если с тех пор поменялась норма. Это относится и к отменённому событию: отменённое автосписание при повторном прогоне тех же суток не появится снова.
- Домен получает события уже без дублей и сам их не убирает: уникальность гарантирует первичный ключ.
- Один механизм покрывает двойное нажатие, повтор при плохой связи, повтор операции целиком и догон автосписаний (FR-CON-08). Отмены идемпотентны так же: двойное нажатие «отменить» отправляет один и тот же `id`.

## 9. Вопрос владельцу

> **Решение принято, вопрос закрыт.** Владелец 2026-10-06 выбрал вариант 1. Спека уточнена: BR-01, BR-02 и строка «Отмена события» в 5.2 приведены к тексту ниже. Инварианты 1–2 в CLAUDE.md ведёт delivery-lead, этот ADR их не правит. Ниже — исходная постановка вопроса без изменений.

**Уточнение формулировок BR-01 и BR-02** (и инвариантов 1–2 в CLAUDE.md, строки «Отмена события» в 5.2).

Контекст: инвентаризация и «закончилось» задают значение, а не приращение. Их нельзя честно записать как слагаемое суммы и нельзя отменить фиксированной компенсацией, если допускаются события задним числом (FR-ABS-02, FR-ABS-04, поздние чеки). Примеры 1 и 2.

Предлагаемый текст, суть которого не меняется: остаток не хранится, журнал не правится.

- **BR-01.** Остаток не хранится числом. Он вычисляется из журнала событий позиции в порядке времени события: инвентаризация и «закончилось» устанавливают остаток, остальные события прибавляют или вычитают количество. Без инвентаризации отсчёт идёт от нуля.
- **BR-02.** Ошибочная отметка отменяется новым событием-отменой со ссылкой на неё. Исходное событие не удаляется и не редактируется, но исключается из расчёта остатка. Для приращений это равносильно компенсации. Отмену можно отменить.
- **5.2, «Отмена события».** Влияние на остаток: «Исключает отменённое событие из расчёта».

Варианты:

1. Принять уточнение — **рекомендация**.
2. Оставить буквальную «сумму» и хранить инвентаризацию как приращение на момент записи. Поздние чеки и отмены дают неверный остаток (фантомные 1800 г в примере 1).
3. Запретить события задним числом раньше последней инвентаризации. Противоречит FR-ABS-04 и NFR-07.

До ответа реализация B-02 и B-03 может идти по варианту 1: на поведение для пользователя он не влияет, меняется только текст правила.

## 10. Последствия

**Плюсы**

- Один источник правды без кэша; события задним числом, ретро-отпуск и отмены решаются порядком и исключением, без специальных путей пересчёта.
- Неявное приращение у значений-событий даёт обучению и калибровке реальный неучтённый расход «бесплатно».
- Один механизм идемпотентности для пользовательских и системных событий.
- Всё доменное — чистые функции от списка событий и параметров времени. Симулятор может воспроизводить любую историю, в том числе «что система знала к моменту T».

**Минусы и риски**

- Экраны со всеми позициями через годы эксплуатации замедлятся (оценка 0,2–0,5 с на 10-м году). Условие и порядок ввода кэша — раздел 3.
- Автосписание с меткой начала суток теряет расход после значения-события в тот же день (не больше суточной нормы). Проверяется симулятором.
- Событие задним числом раньше инвентаризации не меняет текущий остаток. Для пользователя это может выглядеть как «внёс покупку, а остаток не вырос». Лента журнала должна показывать, что событие учтено до инвентаризации. Это требование к экрану журнала (B-30), без изменения поведения.

## 11. Эскиз доменного интерфейса

Иллюстрация к решению, не код. Имена, модуль и размещение — ADR-004 и B-02.

```ts
type Instant = number; // UTC, мс

type DeltaKind = 'purchase' | 'portion' | 'auto_writeoff' | 'recipe' | 'spoilage';

type StockEvent =
  | { kind: DeltaKind; id: string; seq: number; productId: string; occurredAt: Instant; quantity: number }
  | { kind: 'inventory'; id: string; seq: number; productId: string; occurredAt: Instant; value: number }
  | { kind: 'depleted'; id: string; seq: number; productId: string; occurredAt: Instant }
  | { kind: 'cancel'; id: string; seq: number; productId: string; occurredAt: Instant; targetId: string };

// Остаток позиции; asOf — необязательная граница по времени события.
declare function stockBalance(events: readonly StockEvent[], asOf?: Instant): number;

// Остаток до и после каждого действующего события; implied — неявное приращение значений-событий.
declare function stockTimeline(events: readonly StockEvent[]): ReadonlyArray<{
  eventId: string; before: number; after: number; implied: number | null;
}>;
```

## 12. Предположения

- Клиентские часы киоска и телефона синхронизированы (NTP). Время события задаёт клиент. Если пришло время из будущего относительно сервера, его ограничивает сервер (API-контракт, B-16). Домен это не проверяет.
- «Любое событие можно отменить» (FR-LOG-02) включает отмены, поэтому отмена отмены разрешена.
- Отмена изменения состояния позиции выражается обратным событием состояния, а не исключением.
- Значение инвентаризации не бывает отрицательным: это факт с полки. Расчётный остаток может быть любым (BR-15).
