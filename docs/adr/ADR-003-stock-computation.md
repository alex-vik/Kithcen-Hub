# ADR-003 — Вычисление остатка: свёртка журнала, значения-события, отмена, порядок, лента позиции

| Поле | Значение |
| --- | --- |
| Статус | принято 2026-10-06 |
| Дата | 2026-10-06 |
| Автор | architect |
| Бэклог | B-00c |
| Связано | BR-01, BR-02, BR-03, BR-15, BR-26, 5.2, FR-ABS-04, FR-LOG-01…04, FR-CAL-07, NFR-07, NFR-08; ADR-002, ADR-005 |

## Контекст

Спека задаёт остаток как «сумму событий журнала» (BR-01) и отмену как «компенсирующее событие» (BR-02). Но в таблице 5.2 два типа событий задают **значение**, а не приращение: «закончилось» — обнуление, «инвентаризация» — установка фактического значения. Кроме того:

- события бывают задним числом: отпуск, отмеченный после возвращения, отменяет уже выполненные автосписания (FR-ABS-04); «приготовил вчера», повтор отправки при плохой связи;
- журнал действий показывает не только события остатка, но и повод изменения состояния позиции — отключена кнопкой, заархивирована по сроку (FR-LOG-03, BR-08);
- любое событие журнала можно отменить (FR-LOG-02).

Нужно решить: как значения-события сочетаются с суммой, что значит отмена значения, в каком порядке складываются события, где живут изменения состояния позиции, и вычислять ли остаток на лету или держать проекцию.

## 1. Значения-события и BR-01

### Варианты

| Вариант | Суть | Оценка |
| --- | --- | --- |
| A. Хранить приращение | Инвентаризация при записи вычисляет `факт − текущий расчёт` и пишет дельту | Ломается задним числом: событие, вставленное до инвентаризации, сдвигает и результат после неё — хотя инвентаризация зафиксировала физический факт. Отмена «закончилось» требует знать расчёт на момент записи. Хранится производная величина, а не то, что сказал пользователь |
| **B. Хранить значение, свёртка с якорями** | Событие хранит значение. Остаток — левая свёртка журнала в порядке времени события: дельта прибавляется, значение заменяет накопленное | Хранится факт; события задним числом ведут себя физически правильно; отмена выражается просто |
| C. Хранить и значение, и дельту на момент записи | Гибрид | Дельта устаревает при первом событии задним числом; два источника правды внутри одной строки |

### Решение — B

Остаток позиции — результат свёртки действующих событий (раздел 2) в порядке раздела 3:

```
balance = 0
for e in effective(events) ordered by (occurred_at, seq):
  delta-событие:     balance = balance + signedQty(e)
  значение-событие:  balance = value(e)          # «закончилось»: value = 0
```

Эквивалентная формулировка в терминах BR-01: остаток = значение последнего действующего значения-события («якоря») плюс сумма действующих дельт после него. Можно сказать и иначе: каждое значение-событие вносит в сумму неявную дельту `value − остаток_до`, которая **вычисляется при свёртке, а не хранится**. Остаток по-прежнему нигде не хранится числом (инвариант 1).

| Тип (5.2) | Класс | Что хранится |
| --- | --- | --- |
| Покупка | дельта + | количество в расходных единицах; число упаковок и коэффициент на момент записи (BR-03) |
| Потребление порции | дельта − | количество |
| Автосписание по норме | дельта − | количество; локальный день (ADR-005) |
| Списание по рецепту / блюду | дельта − | количество; ссылка на рецепт или блюдо |
| Выброс из-за порчи | дельта − | количество |
| «Закончилось» | значение | ничего (значение 0 по типу) |
| Инвентаризация | значение | фактическое значение; для ответа калибровки — исходный ответ «много / мало / кончается» (FR-CAL-07) |
| Отмена | ссылка | идентификатор отменяемого события |

Количество покупки хранится уже пересчитанным в расходные единицы: последующая правка коэффициента в карточке не меняет смысл старых событий.

Свёртка отдаёт не только итог, но и шаги — `{eventId, before, after}` для каждого действующего события. Неявная дельта значения-события (`after − before`) — то, что «учит прогноз» в 5.2: разница между расчётом и фактом. Обучение нормы и калибровка (шаги 3–4) читают её из шагов свёртки.

Минус не ограничивается и не валидируется (BR-15, инвариант 6): свёртка может дать отрицательный остаток, значение-событие его просто заменяет.

## 2. Отмена (BR-02)

### Варианты

| Вариант | Суть | Оценка |
| --- | --- | --- |
| A. Отрицательная дельта | Отмена пишет `−x` | Работает только для дельт. Для «закончилось» и инвентаризации непонятно, чему равен `x`, а при событиях задним числом он меняется |
| **B. Событие-ссылка, аннулирующее цель** | Отмена — новое событие с `target_id`. Свёртка не учитывает аннулированные события, как будто их не было в журнале | Одинаково для дельт и значений; ничего не удаляется и не правится |

### Решение — B

Отмена — событие `cancel` со ссылкой на отменяемое. Строки не удаляются и не меняются (инвариант 2; в базе — триггеры, ADR-002). «Компенсация» из 5.2 и BR-02 трактуется как **аннулирование по ссылке**: для дельты результат совпадает с компенсацией `−x` в той же точке времени, для значения-события — остаток пересчитывается так, будто якоря не было: предыдущий якорь плюс все дельты после него.

Правила:

- действующее событие — то, на которое не ссылается ни одна действующая отмена. Отмена может ссылаться только на ранее записанное событие (`target.seq < cancel.seq`), поэтому ссылки образуют лес без циклов, и «действующее» вычисляется однозначно;
- **отмена отмены восстанавливает событие.** Это нужно для FR-LOG-02 («любое событие можно отменить») и для отмены отпуска, который уже аннулировал автосписания (ADR-005);
- несколько действующих отмен одного события — то же, что одна;
- отмена применяется в точке времени цели, а не в момент своей записи: аннулирование всегда «задним числом». В журнале действий отмена показывается в момент записи;
- позиция отмены совпадает с позицией цели (копируется при записи) — для выборки по позиции.

Групповые действия («приготовил» — 6 ингредиентов, чек — 15 строк, отпуск — N автосписаний) пишут события с общим `group_id`. Отмена группы — N отмен в одной транзакции, по одной на событие. Отдельного типа «отмена группы» нет.

## 3. Порядок событий

### Варианты

| Вариант | За | Против |
| --- | --- | --- |
| Время записи (`recorded_at`, порядок вставки) | Монотонно, просто | Событие задним числом встаёт не туда: отмеченная вчерашняя порция окажется после сегодняшней инвентаризации и уведёт остаток ниже факта |
| **Время события (`occurred_at`), при равенстве — порядок записи (`seq`)** | Физически верно: инвентаризация «видит» всё, что случилось до неё | Нужен индекс по времени события; позднее событие может менять историю (это и есть цель) |

### Решение — время события

Каждое событие хранит `occurred_at` (когда это произошло, UTC) и `recorded_at` + `seq` (когда и в каком порядке записано). Свёртка остатка — по `(occurred_at, seq)`. Журнал действий (FR-LOG-01) — по `recorded_at`: это лента «что я делал», в ней ищут, что отменить; время события показывается рядом, если оно отличается.

Откуда берётся время события:

- нажатие на киоске, приход, «закончилось» — момент действия на клиенте; при повторной отправке (BR-26) тот же. Сервер не принимает `occurred_at` позже своего `recorded_at` — заменяет его на `recorded_at` (часы клиента могут спешить). Точный допуск — в API-контракте (B-16);
- автосписание за день D — начало суток D по Europe/Vilnius (ADR-005). Так значение-событие внутри дня D поглощает автосписание этого дня: «закончилось» в 19:00 и покупка в 20:00 дают остаток, равный покупке, а не покупке минус дневная норма. Ошибка — не больше дневной нормы, в пределах A-03;
- отмена — момент записи (но действует в точке цели, раздел 2).

### Событие задним числом после инвентаризации

Пример — кофе, норма 20 г/сутки:

| # | occurred_at | Событие | Остаток после |
| --- | --- | --- | --- |
| 1 | 03.10 10:00 | покупка +500 | 500 |
| 2 | 04.10 00:00 | автосписание за 04.10, −20 | 480 |
| 3 | 04.10 21:00 | инвентаризация = 450 (неявная дельта −30) | 450 |
| 4 | 05.10 00:00 | автосписание за 05.10, −20 | 430 |
| 5 | 06.10 00:00 | автосписание за 06.10, −20 | 410 |

07.10 пользователь делает две вещи:

1. **Отмечает отпуск 05.10–06.10 задним числом** (FR-ABS-04). Пишутся отмены #4 и #5. Они стоят после якоря #3 — остаток становится 450. Верно: никто не пил.
2. **Отмечает порцию −10 с временем 04.10 08:00.** Событие встаёт до якоря #3 — остаток не меняется (450), неявная дельта инвентаризации становится −20. Верно: инвентаризация уже видела эту порцию на полке; изменилась только картина расхода для обучения нормы.

Если затем отменить саму инвентаризацию #3, остаток = 500 − 20 − 10 = 470 (#4 и #5 по-прежнему аннулированы отпуском).

Общее правило: событие задним числом меняет текущий остаток, только если встаёт после последнего действующего якоря. До якоря оно меняет историю — шаги свёртки, по которым учится прогноз, — но не текущее значение.

## 4. Изменения состояния позиции (FR-LOG-03)

Отключение кнопкой, автоархив, возврат при покупке, подтверждение нормы, смена типа списания, правка атрибутов — это не события остатка: они не входят в свёртку и не подчиняются BR-01.

### Варианты

| Вариант | За | Против |
| --- | --- | --- |
| Писать их в журнал остатка особыми типами | Одна лента | Свёртка должна их пропускать; смешиваются два разных инварианта; «отмена» норма-события ≠ аннулирование |
| Полное event sourcing позиции | Единый подход | Состояние позиции не суммируется, его не нужно восстанавливать на прошлую дату; сложность без пользы |
| **Текущее состояние в строке `products` + append-only журнал изменений `product_changes`** | Каталог — обычные данные с правкой; повод и история видны; просто | Два источника для ленты — объединяются при чтении |

### Решение

- `products` — текущее состояние позиции, правится (FR-CAT-02). Остатка в ней нет (инвариант 1).
- `product_changes` — append-only (триггеры, ADR-002): `id`, `product_id`, `at`, `kind`, `actor` (`user` / `system`), `reason`, `before` и `after` (JSON изменённых полей), `cause_event_id` (например, покупка, вернувшая позицию в активные, FR-CAT-06), `reverts_id`.
- Любое изменение строки `products` проходит через одну серверную функцию, которая в одной транзакции правит строку и пишет запись в `product_changes`. Изменение без записи в журнал — дефект.
- Одно состояние «неактивна» (BR-08); повод — в `reason`: `user_button` (FR-CAT-04), `auto_archive` (FR-CAT-05), `review_proposal` (BR-16). Перечень `kind` и `reason` дополняется задачами шагов 1, 3, 4.
- Отмена изменения позиции (FR-LOG-02) — новая запись с `reverts_id`, применяющая `before`. Какие изменения отменяемы (например, создание позиции) — решается в B-17 / B-30.

Отпуск (`absence_periods`) — отдельная сущность. Его влияние на остаток видно в журнале через отмены автосписаний с `group_id` отпуска.

## 5. Лента изменений позиции и журнал действий

| Лента | Состав | Порядок |
| --- | --- | --- |
| Журнал действий (FR-LOG-01) | все `stock_events` (включая отмены) + все `product_changes` | по времени записи, новые сверху |
| Лента позиции (карточка, B-29) | `stock_events` и `product_changes` одной позиции | по времени события; аннулированные события показаны зачёркнутыми со ссылкой на отмену; у значений-событий — неявная дельта из свёртки |

Объединение — при чтении, на сервере. Отдельной таблицы ленты нет.

## 6. На лету или проекция

### Оценка объёма

Ритмичная позиция даёт около 365 автосписаний в год плюс отметки и покупки — порядка 500 событий в год, 5 000 за десять лет. Свёртка 5 000 элементов в памяти — доли миллисекунды. Весь журнал за десять лет — порядка 300 000 строк; выборка всего журнала из SQLite и свёртка по всем позициям — сотни миллисекунд.

### Решение — на лету, без проекции в первой версии

- кнопка киоска (NFR-06) — запись одного события и свёртка одной позиции: миллисекунды при любом сроке;
- инвентарь, статусы, список, пересмотр — свёртка всех активных позиций; на горизонте первых лет — десятки миллисекунд.

Проекция вводится, только если замер покажет проблему. Порог: экран, сворачивающий все позиции, отвечает дольше 200 мс на синтетическом журнале за 10 лет (сгенерировать может симулятор). Тогда — кэш в памяти процесса (сервер один), собранный из журнала при старте, обновляемый при добавлении и сбрасываемый по позиции при событии задним числом. Кэш — производная, источник правды остаётся журналом; при сомнении кэш выбрасывается.

## Рекомендация

1. Значения-события хранят значение; остаток — свёртка журнала в порядке времени события, значение заменяет накопленное.
2. Отмена — событие-ссылка, аннулирующее цель; отмена отмены восстанавливает.
3. Порядок свёртки — `(occurred_at, seq)`; журнал действий — по времени записи.
4. Состояние позиции — строка `products` с обязательной записью в append-only `product_changes`.
5. Остаток — на лету, без проекции, до замера.

## Последствия

- Домен получает одну чистую функцию свёртки: на вход — события позиции (уже с `seq`), на выход — остаток и шаги. Ни времени, ни базы ей не нужно.
- BR-01 и BR-02 выполняются в трактовке «свёртка с якорями» и «аннулирование по ссылке». Формулировки спеки буквально говорят «сумма» и «компенсация» — это **вопрос владельцу** (ниже), а не правка.
- Событие задним числом до якоря не меняет текущий остаток — это нужно учесть в тестах и симуляторе (сценарий «отпуск с отметкой задним числом»).
- Автосписание за день D датируется началом дня D — договорённость, на которую опираются ADR-005 и тесты B-06.
- Журнал действий собирается из двух таблиц.

## Вопросы владельцу

1. **Трактовка BR-01 и BR-02.** Подтвердить: «сумма событий» = свёртка, в которой инвентаризация и «закончилось» задают значение (как в 5.2), а отмена любого события = аннулирование по ссылке, в том числе отмена отмены. Рекомендация — да; при согласии delivery-lead может уточнить формулировки BR-01/BR-02 в спеке.
2. **Противоречие инварианта 5 и FR-CAT-05** (замечено попутно, к шагу 3, B-12). Инвариант 5 в `CLAUDE.md`: «система не отключает позицию без подтверждения пользователя». FR-CAT-05 и BR-08: позиция, не покупавшаяся полгода, становится неактивной автоматически. ADR-003 предусматривает повод `auto_archive`, но не решает, нужно ли подтверждение. Варианты: автоархив без подтверждения как исключение из инварианта 5; автоархив как предложение на пересмотре (BR-16).
