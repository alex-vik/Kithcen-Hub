# ADR-003 — Вычисление остатка: свёртка журнала, значения-события, отмена, порядок, лента позиции, оценка по темпу

## Контекст

Остаток — свёртка событий журнала (BR-01), отмена — событие-ссылка (BR-02). В таблице 5.2 два типа событий задают **значение**, а не приращение: «закончилось» — обнуление, «пересчитал» — установка фактического значения. Кроме того:

- события бывают задним числом: «использовал вчера», повтор отправки при плохой связи (BR-26);
- между отметками система показывает оценку остатка по темпу расхода (BR-29, BR-30), а дни отъезда в ней не считаются — в том числе отъезд, отмеченный задним числом (FR-ABS-02, FR-ABS-03);
- журнал действий показывает не только события остатка, но и повод изменения состояния позиции — например, «отключена кнопкой» (FR-LOG-03, BR-08);
- любое событие журнала можно отменить (FR-LOG-02).

Спека 1.3 (Q-29) убрала граммы, коэффициенты, порции, нормы, автосписание и калибровку. Остаток — целое или дробное число в единице счёта позиции; единица — только подпись (BR-03).

Нужно решить: как значения-события сочетаются со свёрткой, что значит отмена значения, в каком порядке складываются события, где живут изменения состояния позиции, как считаются оценка и темп и нужна ли проекция.

## 1. Значения-события и BR-01

### Варианты

| Вариант | Суть | Оценка |
| --- | --- | --- |
| A. Хранить приращение | «Пересчитал» при записи вычисляет `факт − текущий расчёт` и пишет дельту | Ломается задним числом: событие, вставленное до пересчёта, сдвигает и результат после него — хотя пересчёт зафиксировал физический факт. Отмена «закончилось» требует знать расчёт на момент записи. Хранится производная величина, а не то, что сказал пользователь |
| **B. Хранить значение, свёртка с якорями** | Событие хранит значение. Остаток — левая свёртка журнала в порядке времени события: дельта прибавляется, значение заменяет накопленное | Хранится факт; события задним числом ведут себя физически правильно; отмена выражается просто |
| C. Хранить и значение, и дельту на момент записи | Гибрид | Дельта устаревает при первом событии задним числом; два источника правды внутри одной строки |

### Решение — B

Остаток позиции — результат свёртки действующих событий (раздел 2) в порядке раздела 3:

```
balance = 0
for e in effective(events) ordered by (occurred_at, seq):
  delta-событие:     balance = balance + signedQty(e)
  значение-событие:  balance = value(e)          # «закончилось»: value = 0
```

Остаток = значение последнего действующего значения-события («якоря») плюс сумма действующих дельт после него. Каждое значение-событие вносит неявную дельту `value − остаток_до`, которая **вычисляется при свёртке, а не хранится**. Остаток нигде не хранится числом (инвариант 1).

| Тип (5.2) | Класс | Что хранится |
| --- | --- | --- |
| Покупка | дельта + | количество N в единицах счёта |
| Использовал (открыл, выбросил) | дельта − | количество N, по умолчанию 1 |
| «Закончилось» | значение | ничего (значение 0 по типу) |
| Пересчитал | значение | фактическое значение N |
| Отмена | ссылка | идентификатор отменяемого события |

Свёртка отдаёт не только итог, но и шаги — `{eventId, at, before, after}` для каждого действующего события. Неявная дельта значения-события (`after − before`) — расход, который не отметили: из шагов его берёт темп (раздел 7).

Минус не ограничивается и не валидируется (BR-15, инвариант 6): свёртка может дать отрицательный остаток, значение-событие его просто заменяет.

## 2. Отмена (BR-02)

### Варианты

| Вариант | Суть | Оценка |
| --- | --- | --- |
| A. Отрицательная дельта | Отмена пишет `−x` | Работает только для дельт. Для «закончилось» и «пересчитал» непонятно, чему равен `x`, а при событиях задним числом он меняется |
| **B. Событие-ссылка, аннулирующее цель** | Отмена — новое событие с `target_id`. Свёртка не учитывает аннулированные события, как будто их не было в журнале | Одинаково для дельт и значений; ничего не удаляется и не правится |

### Решение — B

Отмена — событие `cancel` со ссылкой на отменяемое. Строки не удаляются и не меняются (инвариант 2; в базе — триггеры, ADR-002). Для дельты результат совпадает с компенсацией `−x` в той же точке времени; для значения-события остаток пересчитывается так, будто якоря не было: предыдущий якорь плюс все дельты после него.

Правила:

- действующее событие — то, на которое не ссылается ни одна действующая отмена. Отмена может ссылаться только на ранее записанное событие (`target.seq < cancel.seq`), поэтому ссылки образуют лес без циклов, и «действующее» вычисляется однозначно;
- **отмена отмены восстанавливает событие** (BR-02, FR-LOG-02);
- несколько действующих отмен одного события — то же, что одна;
- отмена применяется в точке времени цели, а не в момент своей записи. В журнале действий отмена показывается в момент записи;
- позиция отмены совпадает с позицией цели (копируется при записи) — для выборки по позиции.

Если задаче понадобится отменять групповое действие целиком (приход по чеку, пересчёт по фото стола), его события получают общий `group_id`, а отмена группы — N отмен в одной транзакции. Отдельного типа «отмена группы» нет; колонка `group_id` появляется с первой такой задачей.

## 3. Порядок событий

### Варианты

| Вариант | За | Против |
| --- | --- | --- |
| Время записи (`recorded_at`, порядок вставки) | Монотонно, просто | Событие задним числом встаёт не туда: вчерашнее «использовал» окажется после сегодняшнего пересчёта и уведёт остаток ниже факта |
| **Время события (`occurred_at`), при равенстве — порядок записи (`seq`)** | Физически верно: пересчёт «видит» всё, что случилось до него | Нужен индекс по времени события; позднее событие может менять историю (это и есть цель) |

### Решение — время события

Каждое событие хранит `occurred_at` (когда это произошло, UTC) и `recorded_at` + `seq` (когда и в каком порядке записано). Свёртка — по `(occurred_at, seq)`. Журнал действий (FR-LOG-01) — по `recorded_at`: это лента «что я делал», в ней ищут, что отменить; время события показывается рядом, если оно отличается.

Откуда берётся время события:

- отметка с киоска или телефона — момент действия на клиенте; для отметки задним числом — время, которое передал клиент; при повторной отправке (BR-26) тот же. Сервер не принимает `occurred_at` позже своего `recorded_at` — заменяет его на `recorded_at` (часы клиента могут спешить). Точный допуск — в API-контракте (B-16);
- отмена — момент записи (но действует в точке цели, раздел 2).

### Событие задним числом после пересчёта

Пример — молоко, бутылки:

| # | occurred_at | Событие | Остаток после |
| --- | --- | --- | --- |
| 1 | 03.10 10:00 | покупка +6 | 6 |
| 2 | 04.10 08:00 | использовал −1 | 5 |
| 3 | 04.10 21:00 | пересчитал = 3 (неявная дельта −2) | 3 |
| 4 | 05.10 09:00 | использовал −1 | 2 |

07.10 пользователь:

1. **Отмечает «использовал» с временем 04.10 07:00.** Событие встаёт до якоря #3 — остаток не меняется (2), неявная дельта пересчёта становится −1. Верно: пересчёт уже видел, что этой бутылки нет; изменились только шаги свёртки.
2. **Отмечает «использовал» с временем 06.10 20:00.** Событие встаёт после якоря — остаток 1.
3. **Отменяет пересчёт #3.** Остаток = 6 − 1 − 1 − 1 − 1 = 2.

Общее правило (BR-01): событие задним числом меняет текущий остаток, только если встаёт после последнего действующего якоря. До якоря оно меняет историю — шаги свёртки, — но не текущее значение.

Отъезд, отмеченный задним числом, событий не пишет и отмеченный остаток не меняет: он влияет только на оценку и темп при следующем расчёте (раздел 7).

## 4. Изменения состояния позиции (FR-LOG-03)

Отключение кнопкой, отключение по вопросу «больше не покупаешь?», возврат при покупке, правка атрибутов — это не события остатка: они не входят в свёртку и не подчиняются BR-01.

### Варианты

| Вариант | За | Против |
| --- | --- | --- |
| Писать их в журнал остатка особыми типами | Одна лента | Свёртка должна их пропускать; смешиваются два разных инварианта; отмена правки карточки ≠ аннулирование события |
| Полное event sourcing позиции | Единый подход | Состояние позиции не суммируется, его не нужно восстанавливать на прошлую дату; сложность без пользы |
| **Текущее состояние в строке `products` + append-only журнал изменений `product_changes`** | Каталог — обычные данные с правкой; повод и история видны; просто | Два источника для ленты — объединяются при чтении |

### Решение

- `products` — текущее состояние позиции, правится (FR-CAT-02). Остатка в ней нет (инвариант 1).
- `product_changes` — append-only (триггеры, ADR-002): `id`, `product_id`, `at`, `kind`, `actor` (`user` / `system`), `reason`, `before` и `after` (JSON изменённых полей), `cause_event_id` (например, покупка, вернувшая позицию в активные, FR-CAT-06), `reverts_id`.
- Любое изменение строки `products` проходит через одну серверную функцию, которая в одной транзакции правит строку и пишет запись в `product_changes`. Изменение без записи в журнал — дефект.
- Одно состояние «неактивна» (BR-08); повод — в `reason`: `user_button` (FR-CAT-04), `not_buying_prompt` (FR-FIX-03, после подтверждения пользователя, BR-10). Автоархива нет (BR-08). Перечень `kind` и `reason` дополняется задачами (B-01a, B-12).
- Отмена изменения позиции (FR-LOG-02) — новая запись с `reverts_id`, применяющая `before`. Какие изменения отменяемы (например, создание позиции) — решается в B-17 / B-30.

Отъезд (`absence_periods`) — отдельная сущность, не событие остатка и не изменение позиции.

## 5. Лента изменений позиции и журнал действий

| Лента | Состав | Порядок |
| --- | --- | --- |
| Журнал действий (FR-LOG-01) | все `stock_events` (включая отмены) + все `product_changes` | по времени записи, новые сверху |
| Лента позиции (карточка, B-29) | `stock_events` и `product_changes` одной позиции | по времени события; аннулированные события показаны зачёркнутыми со ссылкой на отмену; у значений-событий — неявная дельта из свёртки |

Объединение — при чтении, на сервере. Отдельной таблицы ленты нет.

## 6. На лету или проекция

Автосписаний нет, в журнал пишет только пользователь: десятки событий в день на весь дом, порядка 10–20 тыс. в год, на позицию — десятки, редко сотни в год. Свёртка всех позиций за годы — миллисекунды.

**Решение — всё на лету, проекции нет.** Отмеченный остаток, темп и оценка вычисляются при каждом запросе из журнала и периодов отъезда. Кэш не вводится; если когда-нибудь замер покажет проблему — отдельный ADR.

## 7. Оценка остатка и темп

Оценка и темп — чистые функции домена (ADR-004), считаются на лету и нигде не хранятся. В журнал они ничего не пишут: оценка — не событие и не изменение остатка (NFR-08), отмеченный остаток меняют только события пользователя (FR-CON-01).

- **Темп** (BR-30) — простое среднее: сколько единиц ушло за окно (90 дней, раздел 15), делённое на число дней окна без отъездов. Вход — шаги свёртки (покупки и неявные дельты значений-событий), периоды отъезда, `now`, параметры. Пока истории меньше минимума (раздел 15) — темпа нет. Точная формула и граничные случаи — B-06.
- **Оценка остатка** (BR-29) = отмеченный остаток − темп × число дней с последнего действующего события позиции (в порядке свёртки) до `now`, без дней отъезда. Темпа нет — оценка равна отмеченному остатку.
- Дни — календарные по Europe/Vilnius (BR-27): `now` приходит параметром как `Temporal.Instant`, пояс — из параметров. Как считается неполный текущий день — B-06.
- Событие задним числом до якоря не меняет отмеченный остаток и «последнее событие», но может изменить шаги свёртки, а значит и темп (BR-01).
- Отъезд, заданный заранее или задним числом, просто исключает свои дни из обеих формул при следующем расчёте (FR-ABS-03). Переписывать нечего.

## Рекомендация

1. Значения-события («закончилось», «пересчитал») хранят значение; остаток — свёртка журнала в порядке времени события, значение заменяет накопленное.
2. Отмена — событие-ссылка, аннулирующее цель; отмена отмены восстанавливает.
3. Порядок свёртки — `(occurred_at, seq)`; журнал действий — по времени записи.
4. Состояние позиции — строка `products` с обязательной записью в append-only `product_changes`.
5. Отмеченный остаток, темп и оценка — на лету в домене, без проекции.

## Последствия

- Домен — три чистые функции: свёртка (события позиции → остаток и шаги), темп (шаги, отъезды, `now`, параметры → темп или «нет»), оценка (остаток, последнее событие, темп, отъезды, `now`, параметры). Ни базы, ни системных часов им не нужно.
- Событие задним числом до якоря не меняет текущий остаток — это покрывают тесты B-03/B-06 и сценарии симулятора.
- Отъезд не порождает событий; его влияние видно только в оценке и темпе.
- Журнал действий собирается из двух таблиц.
