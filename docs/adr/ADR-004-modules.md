# ADR-004. Модули: домен отдельно от хранения и HTTP

| Атрибут | Значение |

## 1. Контекст

NFR-16 требует, чтобы доменная логика была чистыми функциями без БД, сети и системных часов, а время приходило параметром. На этом держится симулятор (`tests/sim/`, шаг 2): он прогоняет годы жизни дома за секунды, и ворота ядра (14.3) измеряются именно на нём. Если домен тайком читает часы или базу, симулятор меряет не то, что работает в продакшене.

ADR-001 оставил сюда четыре вопроса:

1. Как разбит `src/domain` по шагам бэклога.
2. Где проходят границы с хранением (SQLite) и HTTP (Hono), нужны ли интерфейсы репозиториев.
3. Где живут параметры раздела 15. По CLAUDE.md это конфигурация, а не константы в логике.
4. Как механически проверить правила: домен не импортирует `node:*`, БД, сеть и не трогает часы; `src/web` берёт из домена только типы.

Ограничения, от которых зависит структура:

- **Права агентов.** backend-dev пишет только в `src/domain/` и `src/server/`, frontend-dev — только в `src/web/`, tester — только в `tests/`. Корневые конфиги и `.claude/test-command` пишет только architect. Поэтому общего каталога вроде `src/shared/` нет: писать в него некому.
- **Масштаб.** Один процесс, одно соединение с SQLite, 150–200 позиций, 200–400 тыс. событий за 10 лет. Слоёв, у которых нет второй реализации или второго потребителя, не заводим.
- **Порядок сборки.** Шаги 1–4 (журнал, автосписание, прогноз, калибровка) идут раньше API (шаг 5). Значит, приёмочные тесты этих шагов не могут идти через HTTP (раздел 8, вопрос В-1).

## 2. Решение коротко

| Вопрос | Решение | Раздел |
| --- | --- | --- |
| Направление зависимостей | `web → (только типы) domain, server/api`; `server → domain`; `domain →` ничего | 3 |
| Разбиение домена | Плоские файлы по механикам, один файл — один модуль, создаёт его первая задача, которой он нужен | 4 |
| Представление данных в домене | Количество — целые тысячные (`Milli`); мгновения в записях — `EpochMs` (как в базе), в параметрах — `Temporal.Instant`; сутки — `Temporal.PlainDate` | 4.3 |
| Репозитории | Интерфейсов репозиториев нет. Домен принимает данные и возвращает строки для вставки. SQL живёт в `src/server/db/`, транзакции — в сервисах `src/server/services/` | 5 |
| Параметры раздела 15 | Три объекта по слою-потребителю: `DomainConfig` (домен), `ServerConfig` (сервер), `webConfig` (клиент). Каждый параметр живёт ровно в одном из них. Домен получает конфигурацию только параметром | 6 |
| Сборка сервера | `main.ts` — единственное место с `process.env` и `Temporal.Now`. `createApp(deps)` не открывает базу и не заводит таймеров | 7 |
| Тесты и симулятор | Юнит и симулятор — только домен; приёмочные — `:memory:` и сервисы, с шага 5 ещё `app.request()` | 8 |
| Механическая проверка | `tsconfig.domain.json` (домену не видны глобалы Node и браузера) и тест `tests/arch/boundaries.test.ts` (импорты, часы, случайность, «клиенту только типы»). Новых зависимостей нет | 9 |

## 3. Слои и направление зависимостей

```
src/web ──import type──▶ src/domain
   │                        ▲
   └──import type──▶ src/server/api (контракт API, B-16)
                            │
src/server ─────────────────┘  (значения и типы)
   ├── main.ts        сборка: env, часы, база, планировщик, HTTP
   ├── app.ts         Hono: маршруты, без базы и таймеров внутри
   ├── api/           маршруты и типы контракта (B-16, B-17)
   ├── services/      команды и запросы: транзакция → домен → запись
   ├── scheduler.ts   runDueJobs, startScheduler (ADR-005)
   ├── config.ts      ServerConfig
   └── db/            драйвер, PRAGMA, миграции, SQL ↔ доменные типы
```

Правила:

| Откуда | Куда можно | Куда нельзя |
| --- | --- | --- |
| `src/domain` | Только другие файлы `src/domain` | Любой пакет, `node:*`, `src/server`, `src/web`. `Temporal` — глобальный объект, импорт не нужен |
| `src/server` | `src/domain` (значения и типы), пакеты | `src/web` |
| `src/server` вне `db/` | Тип `Db` и функции из `src/server/db/` | Прямой импорт `better-sqlite3` / `node:sqlite` (ADR-002: драйвер только в слое хранения) |
| `src/web` | `src/domain` и `src/server` **только** через `import type` / `export type`; клиентские пакеты | Импорт значений из `src/domain` и `src/server`, `node:*` |
| `tests/` | Всё | — |

Почему клиенту можно брать типы и из `src/server`. Ответы API — это HTTP-форма, а не домен, поэтому их типы живут рядом с маршрутами (`src/server/api/`). Будет ли это рукописный `contract.ts` или вывод типов через `hc<AppType>` из Hono, решает API-контракт (B-16). Правило «только `import type`» одинаково для обоих источников.

## 4. Модули домена

### 4.1 Варианты разбиения

| | Вариант | Оценка |
| --- | --- | --- |
| А | **Плоские файлы по механикам** (`stock.ts`, `auto.ts`, `status.ts` …) | Один файл — одна механика из бэклога. Задача трогает 1–2 файла, ревьюер видит границы по именам. На 15–20 файлов вложенность не нужна |
| Б | Каталоги по «ограниченным контекстам» (`journal/`, `planning/`, `review/`) с публичным `index.ts` | Структура рассчитана на команды и сотни файлов. Здесь это слой ради слоя, а бочки `index.ts` скрывают, от чего на самом деле зависит файл |
| В | Один `domain.ts` | Через месяц — тысячи строк. Задачи начинают конфликтовать в одном файле, а параллельная работа (CLAUDE.md) запрещает двум агентам править один файл |

**Рекомендация: А.**

Правила домена:

- Файл экспортирует типы (`readonly`-объекты) и функции. Изменяемого состояния на уровне модуля нет, классы не нужны.
- Зависимости идут сверху вниз по таблице, циклов нет. Задача, которой нужен обратный импорт, выносит общее в файл выше. Это правило проверяет reviewer.
- Бочки `index.ts` нет. Импорт идёт из конкретного файла с расширением `.ts`, как того требует прямой запуск в Node (ADR-001).
- Конфигурация приходит параметром. Значение `defaultConfig` другие файлы домена не импортируют, только тип (проверяется механически, раздел 9).

### 4.3 Представление данных

ADR-002 оставил сюда доменное представление количества. От него и от представления времени зависят все сигнатуры.

**Количество.** `type Milli = number`: целые тысячные доли расходной единицы, как `qty_milli` в базе (ADR-002, 8.3). В домене та же целочисленная арифметика, перевода на границе хранения нет. Брендированный тип (`number & { __brand }`) не вводим: он потребовал бы приведения на каждом литерале в тестах, а смешение единиц ловят имена полей с `Milli` и ревью.

**Мгновения.**

| | Вариант | Оценка |
| --- | --- | --- |
| А | `Temporal.Instant` везде, в том числе в полях событий | Одно представление. Но при чтении каждая строка превращается в объект, а сравнение в свёртке — это вызов встроенной функции `Temporal.Instant.compare`, а не сравнение чисел. Для симулятора, который сворачивает сотни тысяч событий, это заметная постоянная цена (оценка, не замер) |
| Б | **В записях (`StockEvent.occurredAt`, `recordedAt`, `product_log`) — `EpochMs = number`, как в базе. В параметрах (`now`, `asOf`) и календарной арифметике — `Temporal`** | Записи совпадают со строками базы, слой хранения не переводит типы. Свёртка сравнивает числа. Сигнатуры ADR-005 (`now: Temporal.Instant`, `day: Temporal.PlainDate`) не меняются |
| В | `EpochMs` везде, включая `now` | Переписывает сигнатуры ADR-005 и уводит календарную арифметику от `Temporal`, а это прямой путь к ошибкам с DST (BR-27) |

**Рекомендация: Б.** Перевод выполняют только функции `time.ts` (`toEpochMs(instant)`, `fromEpochMs(ms)`). Местные даты в записях (`meta.local_day`, границы отпуска) хранятся строкой `YYYY-MM-DD` (ADR-002, 8.2), в вычислениях превращаются в `Temporal.PlainDate`.

**Результат команды.** Отказ команды (время в будущем, цель отмены из другой позиции — ADR-003) — это значение, а не исключение:

```ts
type CommandResult<T, E extends string> = { ok: true; value: T } | { ok: false; error: E }
```

Сервер превращает `error` в ответ 4xx (B-16). Исключение означает ошибку программы. Минус в остатке отказом команды не бывает (инвариант 6).

## 5. Хранение: нужны ли интерфейсы репозиториев

### Варианты

| | Вариант | Оценка |
| --- | --- | --- |
| А | Порты в домене (`StockRepository` и т. п.), SQLite-адаптер в `src/server`, адаптер в памяти в `tests/` | Домен вызывает порт, то есть делает ввод-вывод и перестаёт быть чистой функцией (NFR-16). Адаптер в памяти заново реализует семантику SQLite (`UNIQUE(id)`, порядок `(occurred_at, seq)`, поиск целей отмены) и расходится с ней. Две реализации хранилища на одного пользователя |
| Б | **Портов нет.** Домен принимает снимок данных и возвращает строки для вставки. Сервер читает, вызывает домен, пишет | Домен чистый. Симулятору хранилище не нужно: он держит массивы и дописывает в них то, что вернул домен. Решения принимает только домен, поэтому цикл «прочитал → домен → записал» в симуляторе и на сервере одинаков по смыслу |
| В | Интерфейс хранилища в `src/server` с двумя реализациями, чтобы симулятор гонял сервисы сервера | Та же вторая реализация, что в А, плюс симулятор тянет серверный слой. Выигрыша перед Б нет: сервисы по правилу не принимают решений |

### Рекомендация: Б

Кто что реализует:

| Часть | Где | Кто пишет | Что делает |
| --- | --- | --- | --- |
| Доменные команды и запросы | `src/domain/*.ts` | backend-dev | `(снимок, вход, now, cfg) → CommandResult<строки>` или вычисленное значение. Строки приходят без `seq` (его назначает хранилище) и с `recordedAt = now` |
| Слой хранения | `src/server/db/` | backend-dev | Открытие базы и PRAGMA, `tx`, миграции, по файлу на таблицу: SQL ↔ доменные типы |
| Сервисы | `src/server/services/<область>.ts` | backend-dev | Одна функция на команду или запрос. Внутри одна транзакция: прочитать снимок, вызвать домен, записать строки |
| Маршруты | `src/server/api/` | backend-dev | Аутентификация, разбор и проверка формы запроса, вызов сервиса, сериализация ответа |

Файлы `src/server/db/`:

```
db/open.ts          openDb(path): Db — PRAGMA ADR-002; tx(db, fn) — BEGIN IMMEDIATE … COMMIT
db/migrate.ts       migrate(db) — раннер на user_version, снимок перед миграцией (ADR-002)
db/init.ts          точка входа скрипта db:init (ADR-002)
db/migrations/      NNNN-<slug>.sql — путь окончательный
db/<таблица>.ts     stock-events.ts, products.ts, product-log.ts, scheduler-state.ts … по задачам
```

Правила:

- `better-sqlite3` импортируется только в `src/server/db/` (проверяется механически). Остальной сервер знает тип `Db` и функции из `db/`, методы драйвера напрямую не вызывает. Транзакция открывается через `tx`, а не через `db.transaction()`: у запасного `node:sqlite` такого помощника нет (ADR-002, раздел 4).
- Сервис решает только, **что прочитать и куда записать**. Ветвление по данным склада («если остаток…», «если позиция ритмичная…») — признак логики, утёкшей из домена. Проверяет reviewer.
- Сервисы синхронные. Сетевые вызовы (распознавание, пуш) идут до или после транзакции (ADR-002, раздел 4).
- Почему сервисы отдельно от маршрутов. Ими пользуются три потребителя: маршруты (шаг 5), планировщик (ADR-005) и приёмочные тесты шагов 1–4, когда HTTP ещё нет. Без этого слоя логику транзакций пришлось бы повторять трижды.

## 6. Конфигурация: параметры раздела 15

### Варианты

| | Вариант | Оценка |
| --- | --- | --- |
| А | Один объект конфигурации для всего приложения | Клиент не может импортировать значения из домена и сервера (раздел 3). Пришлось бы отдавать конфигурацию по API ради двух чисел киоска |
| Б | **По объекту на слой-потребитель; каждый параметр живёт ровно в одном** | Домен получает свою часть параметром, клиент держит свои два числа сам. Дублирования нет, потому что наборы параметров не пересекаются |
| В | Файл или переменные окружения с переопределением значений | Гибкость на будущее, которую никто не просил. Значение меняется правкой одной строки через обычный поток задач |

### Рекомендация: Б

| Объект | Файл | Кто получает | Как |
| --- | --- | --- | --- |
| `DomainConfig`, `defaultConfig` | `src/domain/config.ts` | Функции домена | Параметром. Функция берёт нужную группу (`cfg: DomainConfig['list']`) и, если нужно, `timeZone` |
| `ServerConfig` | `src/server/config.ts` | `main.ts`, планировщик, сервисы | `loadServerConfig(env)`: `KH_DB_PATH` и порт из окружения (ADR-002), остальное — значения в коде; внутри поле `domain: DomainConfig` |
| `webConfig` | `src/web/config.ts` | Экраны | Импорт внутри клиента |

Куда попадают параметры реестра. Имена полей условные, окончательные задаёт задача. Параметр со значением «не задано» получает поле тогда, когда analyst предложит значение, а delivery-lead внесёт его в раздел 15. Пустых полей-заглушек нет.

Правила:

- В логике нет литералов, повторяющих значения раздела 15. Любое такое число берётся из конфигурации. Проверяет reviewer.
- Файлы домена импортируют из `config.ts` только тип. Поэтому тесты и симулятор могут подставить `{ ...defaultConfig, list: { ...defaultConfig.list, horizonDays: 10 } }` и прогнать ту же логику с другими параметрами, а это и нужно для подбора значений на симуляторе (14.4).
- **Настройки пользователя — не конфигурация.** То, что пользователь меняет в приложении (отпуск, режим пересмотра, время уведомлений из настроек, B-33), — это данные в базе. Они читаются сервисом и передаются в домен как вход. Если B-33 сделает время уведомлений пользовательской настройкой, поле `schedule.…` в `ServerConfig` станет её значением по умолчанию.
- `process.env` читается только в `src/server/main.ts`, дальше передаётся объектом в `loadServerConfig`.

## 7. Сборка сервера

```ts
// src/server/config.ts
type ServerConfig = {
  dbPath: string        // KH_DB_PATH, обязателен (ADR-002)
  port: number
  tickMs: number        // 60_000 (ADR-005)
  domain: DomainConfig
  // остальные поля добавляют задачи по таблице раздела 6
}
function loadServerConfig(env: Readonly<Record<string, string | undefined>>): ServerConfig

// src/server/db/open.ts
type Db                                      // непрозрачный тип для остального сервера
function openDb(path: string): Db            // ':memory:' в тестах
function tx<T>(db: Db, fn: () => T): T

// src/server/app.ts
type AppDeps = { db: Db; config: ServerConfig; clock: Clock }   // Clock — из ADR-005
function createApp(deps: AppDeps): Hono

// src/server/scheduler.ts — сигнатуры ADR-005
function runDueJobs(db: Db, config: ServerConfig, now: Temporal.Instant): void
function startScheduler(db: Db, config: ServerConfig, clock: Clock): () => void
```

`src/server/main.ts` — единственный файл, который знает об окружении и реальных часах:

1. `const config = loadServerConfig(process.env)` — без `KH_DB_PATH` старт падает.
2. `const clock: Clock = () => Temporal.Now.instant()`.
3. `const db = openDb(config.dbPath)`, затем `migrate(db)`.
4. `runDueJobs(db, config, clock())` — догон до приёма запросов (ADR-005, раздел 3).
5. `const stop = startScheduler(db, config, clock)`.
6. `serve({ fetch: createApp({ db, config, clock }).fetch, port: config.port })`.
7. На `SIGTERM` / `SIGINT`: `stop()`, закрыть HTTP-сервер, `db.close()` (ADR-002, раздел 4).

Правила:

- `createApp` не открывает базу, не заводит таймеров и не читает часы сам. Обработчик берёт `const now = deps.clock()` один раз на запрос и передаёт его в сервис. Это то, на чём держатся приёмочные тесты с фиксированным временем (ADR-002, раздел 9).
- Раздача собранного клиента (`dist/web`) и аутентификация решаются в ADR-007 и ADR-006. Точка их подключения — `createApp` или `main.ts`.

## 8. Как тесты и симулятор вызывают домен

| Вид | Каталог | Что импортирует | Время и параметры |
| --- | --- | --- | --- |
| Юнит домена | `tests/unit/` | Функции `src/domain/*.ts` напрямую | `Temporal.Instant.from('2026-10-25T21:59:59.999Z')` литералом; `defaultConfig` с переопределениями |
| Приёмочные, шаги 1–4 | `tests/acceptance/` | `openDb(':memory:')`, `migrate`, функции `src/server/services/` | `now` параметром сервиса |
| Приёмочные, шаг 5+ | `tests/acceptance/` | `createApp({ db, config, clock: () => t })` и `app.request()` | Подставные часы |
| Планировщик | `tests/acceptance/` | `runDueJobs(db, config, now)` (ADR-005, раздел 8) | `now` параметром |
| Симулятор | `tests/sim/` | Только `src/domain` | Цикл по `Temporal.PlainDate`, `now` вычисляется из даты |
| Границы | `tests/arch/` | `node:fs`, `node:module`, `node:path` | — |
| Помощники | `tests/support/` | Фабрики событий и позиций, открытие `:memory:` | — |

Как устроен цикл симулятора. Симулятор держит в памяти каталог и массив событий на позицию. На каждом шаге он вызывает те же функции, что и сервисы: команды `journal.ts` для отметок, `closedDays` и `planAutoConsumption` для автосписания. Возвращённые строки он дописывает в массивы и сам назначает им `seq` монотонным счётчиком, как это делает `rowid` в базе. Чтения (`balance`, статусы, список) — прямые вызовы домена над этими массивами. Базы, HTTP и таймеров нет. Совпадение с продакшеном держится на правиле раздела 5: сервисы не принимают решений.

## 9. Механическая проверка границ

### 9.1 Что проверяем

| # | Правило | Почему |
| --- | --- | --- |
| D1 | Файлы `src/domain` импортируют только относительные пути, которые разрешаются внутри `src/domain`. Это касается и `import type`, и `import()`, и `export … from` | Закрывает БД, сеть, `node:*`, `src/server`, `src/web` белым списком, а не перечнем запретов |
| D2 | В `src/domain` не встречаются `Date` (как слово), `Temporal.Now`, `Math.random`, `globalThis`, динамический `import(` | Системные часы и случайность есть в самом языке, импорт для них не нужен. Случайность — по той же причине, что и часы: симулятору нужна воспроизводимость (14.4). Идентификаторы и сиды приходят параметром. `globalThis` закрывает обход через `globalThis.Temporal.Now`. Динамический импорт домену не нужен, а с вычисляемым путём его не видит D1 |
| D3 | Коду `src/domain` не видны глобалы Node и браузера: `process`, `Buffer`, `setTimeout`, `setInterval`, `fetch`, `WebSocket`, `crypto`, `performance`, `console`, `document` … | Белый список окружения: домену доступен только стандарт языка (`lib: esnext`, вместе с `Temporal`) |
| D4 | Внутри `src/domain` значения из `config.ts` не импортируются, только типы | Конфигурация приходит параметром (раздел 6) |
| W1 | `src/web` импортирует из `src/domain` и `src/server` только через `import type` / `export type`. Встроенная форма `import { type X } from …` тоже запрещена | При `verbatimModuleSyntax` встроенная форма оставляет после стирания `import {} from '…'`, то есть модуль всё равно загружается и попадает в бандл |
| W2 | `src/web` не импортирует `node:*` | Клиент работает в браузере |
| S1 | `better-sqlite3` и `node:sqlite` импортируются только в `src/server/db/` | ADR-002: драйвер только в слое хранения |
| S2 | В `src/server` выражения `Temporal.Now`, `Date.now`, `new Date` встречаются только в `main.ts` | ADR-005: единственное место с реальными часами. Иначе приёмочные тесты не управляют временем |

### 9.2 Варианты

| | Вариант | Оценка |
| --- | --- | --- |
| А | ESLint + typescript-eslint: `no-restricted-imports` с `allowTypeImports`, `no-restricted-globals`, `no-restricted-properties`, переопределения по каталогам | Самый выразительный. Но typescript-eslint разбирает код через JS API компилятора, а в TypeScript 7.0 стабильного программного API нет: он ожидается в 7.1. Запрос на поддержку TS 7 закрыт как «не планируется». Обходной путь — держать рядом TypeScript 6 (`@typescript/typescript6`) только для линтера. Итого второй компилятор, несколько пакетов и ещё один инструмент в test-command |
| Б | dependency-cruiser | Правила графа импортов хороши. Но тип-онли импорты он различает только через парсер TypeScript (с парсером swc признак теряется, issue #1082), то есть та же проблема с TS 7. Часы и глобалы не видит |
| В | oxlint: `no-restricted-imports` с `allowTypeImports`, `no-restricted-globals`, `no-restricted-properties`, `overrides` по путям | Нативный бинарник, от компилятора TS не зависит, покрывает D1–D2, W1–W2, S1–S2 конфигурацией. Цена — новый инструмент и конфиг. Трактовку встроенного `import { type X }` правилом `allowTypeImports` нужно проверять отдельно (W1). Глобалы — перечень запретов, а не белый список |
| Г | **`tsconfig.domain.json` + собственный тест границ** | Новых зависимостей нет. D3 проверяет сам компилятор белым списком окружения. Остальные правила проверяет тест примерно на 80 строк на `node:fs`, `node:path` и `module.stripTypeScriptTypes` (встроен в Node 26). Стирание типов здесь то же, что делает Node при запуске, поэтому W1 проверяет фактическую семантику, а не догадку о ней |
| Д | Плагин Vite, который валит сборку, если в бандл попал файл `src/domain` | Проверяет только W1, только при `vite build`, которого нет в test-command |

### 9.3 Рекомендация: Г

**Часть 1. `tsconfig.domain.json` в корне** (пишет architect после принятия ADR):

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": { "lib": ["esnext"], "types": [] },
  "include": ["src/domain"]
}
```

`types: []` отключает `@types/node`, а `lib: ["esnext"]` без `dom` убирает браузерные глобалы. `Temporal` входит в `esnext` начиная с TypeScript 6.0 (`esnext.temporal`), так что остаётся доступен. Любое обращение к `process`, `setTimeout`, `fetch`, `console` в домене становится ошибкой компиляции. Корневой `tsconfig.json` не меняется.

**Часть 2. Тест `tests/arch/boundaries.test.ts`** (пишет tester по этому ADR):

```
файлы = все *.ts в src/domain, src/server, src/web (fs.readdirSync(…, { recursive: true }))

спецификаторы(код) = все строки после `from`, `import`, `import(`, `export … from`
    (регулярное выражение по тексту, кавычки ' " `)
значения(код)      = спецификаторы(stripTypeScriptTypes(код))
    // то, что осталось после стирания типов, то есть реально исполняется

D1: для файла домена каждый спецификатор(исходник) относительный
    и path.resolve(dirname, spec) лежит внутри src/domain
D2: исходник домена не содержит /\bDate\b/, /Temporal\s*\.\s*Now/, /Math\s*\.\s*random/, /\bglobalThis\b/, /\bimport\s*\(/
D4: для файла домена, кроме config.ts, ни одно из значений(код) не разрешается в src/domain/config.ts
W1: для файла клиента ни одно из значений(код) не разрешается в src/domain или src/server
W2: для файла клиента нет спецификаторов, начинающихся с 'node:'
S1: спецификаторы 'better-sqlite3' и 'node:sqlite' встречаются только в src/server/db/
S2: в src/server вне main.ts исходник не содержит Temporal.Now, Date.now, new Date
```

Обязательные части теста:

- **Контрольный пример стирания.** Тест проверяет, что `stripTypeScriptTypes("import type { A } from './x.ts'")` не содержит `./x.ts`, а `stripTypeScriptTypes("import { type A } from './x.ts'")` — содержит. Документация Node говорит, что встроенные типы заменяются пробелами, но `module.stripTypeScriptTypes` имеет стабильность 1.2 (release candidate). Если поведение изменится, упадёт этот пример, а не тихо ослабнет W1.
- **Проверка самой проверки.** Функция `violations(files: { path: string; code: string }[])` прогоняется на встроенных строках-образцах: по одному нарушителю на каждое правило плюс разрешённые формы. Только после этого её прогоняют по реальному `src/`. Так тест доказывает, что ловит нарушения, ещё когда `src/domain` пуст.
- Сообщение о нарушении содержит файл, правило (D1…S2) и спецификатор или токен.

Что проверка не ловит, и это граница ревью, а не теста:

- Намеренный обход (`const T = Temporal; T.Now`, вычисляемые строки). Проверка защищает от случайных нарушений.
- Спецификаторы в комментариях дают ложное срабатывание. Это осознанная строгость: правило одно для кода и комментариев.
- Нарушение направления между модулями домена (раздел 4.2) и логика в сервисах (раздел 5) проверяются ревью.

**Почему Г, а не В.** Обе закрывают задачу. Г не добавляет зависимостей, опирается на уже выбранный компилятор и стирание типов из рантайма и лежит в `tests/`, куда разработчики писать не могут, так что ослабить проверку ради зелёного Stop-хука они не смогут. В становится предпочтительнее, если клиент перейдёт на JSX (см. «Риски»): `stripTypeScriptTypes` JSX не разбирает.

## 10. Последствия

### Что изменить после принятия (делает architect, отдельным шагом)

| Файл | Изменение | Когда |
| --- | --- | --- |
| `tsconfig.domain.json` (новый) | Содержимое из раздела 9.3 | Вместе с первым `.ts`-файлом в `src/domain` (B-01). На пустом каталоге `tsc -p` падает с ошибкой «нет входных файлов» (TS18003) и сделает test-command красным |
| `.claude/test-command` | `npx tsc --noEmit && npx tsc --noEmit -p tsconfig.domain.json && npx vitest run` | Одновременно с `tsconfig.domain.json` |
| `package.json` | Скрипт `typecheck`: `tsc --noEmit && tsc --noEmit -p tsconfig.domain.json`. Скрипт `db:init` из ADR-002: `node src/server/db/init.ts`. Новых зависимостей нет | `typecheck` — вместе с `tsconfig.domain.json`; `db:init` — в B-02 |
| `tsconfig.json`, `vitest.config.ts`, `vite.config.ts` | Без изменений: `tests/**/*.test.ts` уже покрывает `tests/arch/` | — |

### Работа, которую порождает ADR

- **tester:** `tests/arch/boundaries.test.ts` по разделу 9.3 и `tests/support/`. Нужен до начала реализации B-01, чтобы первая же доменная задача шла под проверкой. Это тест-страж, а не тест критерия приёмки: на пустом `src/` он зелёный. Правило «тест, прошедший до реализации, — ошибка теста» к нему неприменимо, а его «красную» фазу заменяют образцы нарушителей (вопрос В-2).
- **backend-dev:** файлы по карте раздела 4.2 и раскладке разделов 5 и 7, каждый в своей задаче. `src/domain/config.ts` — с первым параметром (B-06).
- **analyst:** в задачах шагов 1–4 критерии приёмки формулируются через сервисы, если решение по В-1 — «да».
- **B-16:** форма типов контракта API в `src/server/api/` (`contract.ts` или `hc<AppType>`). На правило W1 выбор не влияет.

### Уточнения к другим ADR (сами документы этот ADR не правит)

- ADR-002, раздел 5: каталог миграций `src/server/db/migrations/` окончательный, скрипт `db:init` — `src/server/db/init.ts`, транзакции идут через `tx(db, fn)` из `src/server/db/open.ts`.
- ADR-002, раздел 8.3: доменное представление количества — целые тысячные (`Milli`), как рекомендовано там же.
- ADR-003, раздел 8, и ADR-005, раздел 6: имена функций окончательные, файлы — по таблице 4.2. Время в полях событий — `EpochMs`, в параметрах — `Temporal.Instant` (раздел 4.3). Отказ команды возвращается как `CommandResult`.
- ADR-005, раздел 8, пункт 5 (чистота домена «до ADR-004 проверяет reviewer») закрывается правилами D2, D3 и S2.

### Инварианты

Не меняются. Структура поддерживает их. 1 — остатка нет ни в схеме, ни в сервисах: сервис передаёт в домен события, а не число. 3 — `Milli` сквозной от ввода до базы. 6 — отказ команды описан типом и не включает минус в остатке. NFR-16 закреплён механически (D1–D4, S2).

### Риски

- **`module.stripTypeScriptTypes` в статусе release candidate.** Контрольный пример в тесте ловит смену поведения. Запасной путь — вариант В (oxlint).
- **JSX на клиенте.** Если в B-23 выберут фреймворк с `.tsx`, `stripTypeScriptTypes` такие файлы не разберёт. Тогда правило W1 переходит на вариант В или на парсер, уже установленный вместе с Vite. Это отдельное решение architect в рамках B-23.
- **Регулярные выражения вместо парсера.** Ошибаются в сторону строгости (строка-спецификатор в комментарии). Не видят динамический `import()` с вычисляемым путём: в домене любой `import(` запрещён правилом D2, в клиенте это граница ревью.
- **Производительность `EpochMs` против `Temporal.Instant`** оценена, а не измерена. Решение Б верно и без этого довода, потому что записи совпадают со строками базы.
- **Клиент не изолирован от глобалов Node** на уровне типов: корневой `tsconfig.json` даёт `types: ["node"]` всему `src`. W2 закрывает импорты `node:*`, а отдельный `tsconfig` для клиента — предмет B-23, если понадобится.

## 11. Вопросы

**В-1. Приёмочные тесты шагов 1–4 идут через сервисы, а не через API.** К delivery-lead, нужен до оформления B-01. В 14.1 спеки сказано «приёмочные — через API», но API появляется только на шаге 5 (после ADR-006 и контракта). Предложение: в шагах 1–4 критерии приёмки проверяются вызовом сервисов `src/server/services/` над базой `:memory:`, а с шага 5 те же сценарии дополняются тестами через `app.request()`. Если delivery-lead сочтёт это изменением 14.1, а не его уточнением для порядка сборки, вопрос уходит владельцу. ADR спеку не правит.

**В-2. Тест-страж границ вне обычного потока задачи.** К delivery-lead вместе с tester. Как оформить `tests/arch/boundaries.test.ts`: отдельной задачей шага 0 или первым пунктом тестов B-01. Нужно ли явно зафиксировать, что к тесту-стражу не применяется правило «тест должен падать до реализации» (его заменяют образцы нарушителей, раздел 9.3).

## 12. Источники

Проверено 2026-09-28.
